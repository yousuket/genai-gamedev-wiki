## 概要

- 個人開発でも企画を文章にしておくと、迷ったときの判断基準になり、スコープ（作る範囲）の膨張を防げます。
- この記事では2種類の文書を扱います。
  - **1ページ企画書**: 企画の核を1枚にまとめたもの。最初に作る
  - **GDD**（Game Design Document、ゲームデザインドキュメント）: 仕様を詳しく書いた、開発中に更新し続ける文書
- どちらもコピーして使える Markdown テンプレートを載せています。
- Markdown でリポジトリに置いておけば、AIコーディングツールに読ませる「仕様書」としても使えます。

## なぜ短く書くのか

EA（当時）のデザイナー Stone Librande は GDC 2010 の講演「One-Page Designs」で、従来の長いGDDはほとんど読まれないと指摘し、注釈付きの図などで設計を1ページにまとめる方法を提案しました（[GDC Vault](https://gdcvault.com/play/1012356/One-Page)、[Game Developer の紹介記事](https://www.gamedeveloper.com/design/video-one-page-designs)）。講演では、1ページに収めようとすると問題を本当に理解する必要があり、設計も簡潔になるという利点が語られています。

また、Tim Ryan は1999年の記事で、企画の最初の段階の文書（ゲームコンセプト）は1〜2ページに収めるよう勧めています（[The Anatomy of a Design Document, Part 1](https://www.gamedeveloper.com/design/the-anatomy-of-a-design-document-part-1-documentation-guidelines-for-the-game-concept-and-proposal)）。

## 2つの文書の違い

| 項目 | 1ページ企画書 | GDD |
|---|---|---|
| 目的 | 何を作るかを決める・人に伝える | どう作るかを決める・記録する |
| 作る時期 | 企画の最初、プロトタイプの前後 | プロトタイプで手応えを得たあと |
| 分量 | 1ページ | 必要な分だけ。章ごとに分けてもよい |
| 更新 | 方針が変わったときだけ | 開発中ずっと |
| 読む人 | 自分、協力者、パブリッシャー、友人 | 自分、協力者、AIコーディングツール |

Tim Ryan の記事では、ゲームコンセプトの項目として、1文の売り文句（Introduction）、プレイヤー視点での説明（Description）、主な特徴（Key Features）、ジャンル、プラットフォームなどを挙げています。下のテンプレートもこれを参考にしています。

## 1ページ企画書テンプレート

````markdown
# （仮タイトル）

## 一言で
（1文で。「〇〇が△△するゲーム」。例: 魔法の組み合わせで押し寄せる敵を捌く、1プレイ20分のサバイバー系アクション）

## プレイヤー体験
（二人称で2〜3文。「あなたは〜する。〜すると〜になる」）

## 狙う楽しさ
- 主: （例: Challenge — ぎりぎりで生き残る緊張感）
- 副: （例: Discovery — 魔法の組み合わせを見つける）
（MDA の8分類から2〜3個）

## コアループ
（動詞を3つ程度、矢印でつなぐ）
例: 避ける → 拾う → 選ぶ → （避けるに戻る）

## メタループ
（1プレイの外側で何が進むか）

## 主な特徴（3つまで）
1.
2.
3.

## 参考にする作品と違い
| 作品 | 似ている点 | 違う点 |
|---|---|---|
|  |  |  |

## 基本情報
- ジャンル:
- プラットフォーム:
- 1プレイの長さ / 全体のボリューム:
- 想定価格:
- 開発期間の目標:

## やらないこと
（スコープ外にするものを明記する。例: オンライン対戦、ボイス、ストーリーモード）

## 最大のリスク
（一番不確かな点と、それを確かめる方法）
````

「やらないこと」を書いておくと、開発中に機能を足したくなったときの歯止めになります（[スコープの決め方](/getting-started/scope/)）。狙う楽しさの分類は [MDAフレームワーク](/design/mda/)、ループの書き方は [コアループ](/design/core-loop/) を参照してください。

## GDDテンプレート

GDDは最初から全部を埋める必要はありません。決まったところから書き、決まっていない項目は「未定」と明記します。

````markdown
# （タイトル） ゲームデザインドキュメント

- 最終更新: YYYY-MM-DD
- 版: 0.1
- 1ページ企画書: （リンク）

## 1. 概要
- 一言で:
- 狙う楽しさ（MDA）:
- ターゲット（普段どんなゲームを遊ぶ人か）:

## 2. コアループ
（図またはリストで。1周の所要時間の目安も書く）

## 3. メタループ・進行
- 1プレイの流れ:
- アンロック・成長要素:
- クリア条件 / 終わり方:

## 4. 操作
| 入力 | キーボード/マウス | ゲームパッド | 動作 |
|---|---|---|---|
|  |  |  |  |

## 5. ゲームの要素
### 5.1 プレイヤー
### 5.2 敵・障害
### 5.3 アイテム・カード・スキル
（数値はここに書かず、パラメータ表へのリンクにする）

## 6. レベル・ステージ
- 構成（手作り / 手続き生成 / 組み合わせ）:
- 難易度の上げ方:
- チュートリアルで教えること（順番）:

## 7. バランス
- 数値の目標（例: 初見のボス勝率 30%）:
- パラメータ表: （スプレッドシートや CSV へのリンク）
- シミュレーション: （スクリプトの場所）

## 8. UI・画面遷移
（画面一覧と遷移図）

## 9. アート・サウンドの方針
- 画風・参考画像:
- 使う生成AIツールと用途:
- 素材の権利確認: （利用規約・ライセンスを確認したか）

## 10. 技術
- エンジン / 言語:
- 対象プラットフォーム:
- セーブデータ:

## 11. スコープとマイルストーン
| マイルストーン | 内容 | 目標日 |
|---|---|---|
| プロトタイプ | コアループ1周 |  |
| バーティカルスライス | 1ステージ分を製品品質で |  |
| デモ |  |  |
| 発売 |  |  |

## 12. やらないこと

## 13. 未決事項
- [ ]

## 14. 変更履歴
| 日付 | 変更内容 | 理由 |
|---|---|---|
|  |  |  |
````

**バーティカルスライス**とは、ゲームの一部分（1ステージなど）だけを、完成品と同じ品質まで作ったものです。制作にかかる時間の見積もりや、PV・ストアページ用の素材作りに使えます。

## 運用のコツ

- **図を使う**: Librande の講演のとおり、画面遷移やループは文章より図のほうが伝わります。Mermaid 記法を使えば、Markdown の中にテキストで図を書けます（GitHub では図として表示されます。[GitHub Docs](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams)）。
- **数値は分ける**: 数値を GDD に直接書くと、ゲームのデータと食い違いやすくなります。パラメータ表へのリンクにします（[バランス調整](/design/balancing/)）。
- **日付を入れる**: Librande は印刷版に日付を入れて更新を追えるようにすることを勧めています。Git で管理するなら変更履歴は自動で残りますが、「なぜ変えたか」は文書側に書いておくと後で役立ちます。
- **プレイテストの結果を反映する**: テストで方針が変わったら、1ページ企画書まで戻って書き直します（[プレイテスト](/design/playtesting/)）。

## AIの活用ポイント

- **AIへの仕様書として使う**: リポジトリに `docs/gdd.md` などとして置き、AIコーディングツールに「GDDの5.2節に沿って敵を実装して」と指示できます。仕様が文書にあるほど、AIの出力が企画からずれにくくなります（[AI駆動の開発ワークフロー](/dev-env/ai-workflow/)）。
- **穴埋めの質問役にする**: テンプレートと書きかけの企画を渡し、「未記入や矛盾している項目を挙げ、決めるべきことを質問して」と頼むと、抜けを見つけやすくなります。
- **要約・変換**: GDD から1ページ企画書の案を作らせたり、逆に1ページ企画書から GDD の章立てを起こさせたりできます。
