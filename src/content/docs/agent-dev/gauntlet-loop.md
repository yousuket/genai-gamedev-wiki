## 概要

Gauntlet Loop は、Matt Shumer 氏が Claude of Duty（プロンプト1本、約5.5万行のブラウザFPS）で使った進め方に、後から付けた名前です。作る役と批評役を別のエージェントにして、批評役に実物と見比べさせ、勝つまで、あるいは人が止めるまで回し続けます。
この記事では、定義、Claude of Duty での使われ方と数字、効く理由と限界、3D FPS 以外のゲームに当てはめる手順、コピーして使えるプロンプトのひな形、失敗しやすい点を説明します。
最後に、この手法が苦手な「遊んで面白いか」を、人が決める部分として整理します。

## Gauntlet Loop とは

### 名前の由来

Shumer 氏は2026年7月25日（UTC）に Claude of Duty のデモとプロンプトを公開しました。2日後の7月27日（UTC）に、そのプロンプトの投稿を引用して「これを正式に Gauntlet Loop と呼ぶ」と書き（[X投稿](https://x.com/mattshumer_/status/2081830214384886228)）、同日に解説記事 [How to Run a Gauntlet Loop](https://somethingbig.ai/gauntlet-loop) を公開しています。投稿は、エージェント自身（人ではなく）が目標を部品に分け、部品ごとに専門の作り手と、容赦のない目隠しの批評役を付け、実世界の同等品より良いときだけ合格にする、という内容です。
Anthropic の公式用語ではなく、作者による命名です。Claude of Duty の時点では名前はなく、プロンプトを書いたあとに、手法として整理されました。

### 中身

作者の解説記事から、要素を5つに整理します。

| 要素 | 内容 |
|---|---|
| 1. 目標だけを渡す | 作り方（構成、分担、手順）は指定しない。「行き先だけ渡して、道は選ばせる」と作者は書いている |
| 2. 実物と比べる基準を置く | 「すごく良く」は基準にならない。実在のゲームの画面のように、並べて比べられるものを置く。到達できなくてもよい。基準が分からないときは、基準探しも作業に含める |
| 3. 部品に分ける | 個別に改善し、個別に判定できる最小の単位に分ける。分け方は司令役のエージェントに決めさせる |
| 4. 作る役に採点させない | 批評役は新しいコンテキストで起動し、目標、基準、規則、実物の出力だけを渡す。作る役の履歴や説明は渡さない。自分側と基準のどちらが自分の出力かを伏せて、良い方を選ばせる |
| 5. 区切りを置かない | 「3ラウンドで終了」とは書かない。止めるのは、気に入ったとき、改善が小さくなったとき、使ってよい計算量を使い切ったとき |

補助として、長い実行では進捗を見せるHTMLページ（または `workbench.md`）をエージェントに更新させ、スマートフォンから眺める方法と、各ラウンドの終わりに、全体を見て整合を取る新しいエージェントを1体置く「平滑化パス」が紹介されています。作者は、核はあくまで「分ける、作る、判定する、繰り返す」だと書いています。
実行環境は、ファイルを開き、コードを動かし、画面を撮り、サブエージェントを起動できるエージェント環境（Claude Code や Codex）が前提です。チャットへの貼り付けでは同じ結果にならないと明記されています。

### Anthropic の公式ブログの型との対応

Anthropic の公式ブログ [A harness for every task: dynamic workflows in Claude Code](https://claude.dev/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code/)（2026年6月2日）は、Claude が自分で多数のサブエージェントを動かす「動的ワークフロー」の使い方を紹介しています。この記事に Gauntlet Loop という言葉は出てきません。ただ、並べられている型のいくつかは、Gauntlet Loop の要素と同じ形です。

| 公式ブログの型・説明 | Gauntlet Loop の要素 |
|---|---|
| 敵対的な検証（adversarial verification）: 生成した各エージェントに、別のエージェントが、基準に照らして出力を検証する | 部品ごとに、作る役と別の批評役を置く（要素3、4） |
| 完了まで繰り返す（loop until done）: 固定の回数ではなく、停止条件を満たすまでエージェントを生成し続ける | 区切りを置かない（要素5）。ブログの例の停止条件は「新しい発見がない」など。Gauntlet Loop は「基準に勝つ、または人が止める」 |
| 同じ文脈の中で作業すると起きる「自己優遇バイアス」（自分の結果を好んで評価する）に、別々のコンテキストの別のエージェントで備える | 作る役に採点させない（要素4） |
| 好みが絡む探索（デザインなど）では、レビュー役に基準を渡し、満たしたと判断するまで続ける | 実物と比べる基準を置く（要素2） |
| 大量に分けて並列に走らせる（fan-out） | 部品に分ける（要素3） |

対応が確認できるのは、表の範囲までです。ブログは、基準が「実在の製品」であることや、目隠しの A/B 比較には触れていません。また、ブログは並べ替えの節で「ペアでの比較は絶対評価より信頼できる」と述べています。Gauntlet Loop の「どちらが良いか選ぶ」形と方向は同じですが、ブログが述べているのは並べ替えの文脈です。

## Claude of Duty では、どう使われたか

### プロンプトの構造

プロンプトは [prompt.md](https://github.com/mshumer/Claude-of-Duty/blob/main/prompt.md) の約150語、3段落です。書かれているのは、目標、サブエージェントへの分担、目隠しで実物と比べる厳しい批評役、止めない指示、Three.js と `/loop` と `ultracode` の指定だけです。設計書、機能の一覧、ゲームのルールはありません。契約ファイル [ARCHITECTURE.md](https://github.com/mshumer/Claude-of-Duty/blob/main/ARCHITECTURE.md)（ディレクトリの所有者、禁止事項、イベント名）が、並列のエージェントがぶつからないための取り決めです。誰が書いたかは公開資料では確認できません。詳しくは [Claude of Duty の事例](/cases/claude-of-duty/) にあります。

### 採点の推移

README（2026年9月時点）によると、11の独立した批評役が、ゲームの画面を実物の Call of Duty と比べて10点満点で採点しました。

| 項目 | 結果 |
|---|---|
| 採点の推移 | 3.59、4.14、4.05、5.05（最後は最適化の後） |
| 目隠しの A/B 比較 | すべての批評役が、すべてのラウンドで、実物を選んだ |
| 判定の内訳 | 2枚が「CLOSE（近い）」、残りは「AMATEUR（素人）」 |
| 作者の評価 | 目標には届いていない。手、素材の質感、遠くの敵、間接光、フレームレートが弱点 |

README の数字は、ラウンドごとの内容までは書いていません。時間は、解説記事に「何時間も」とあるだけで、具体的な値と費用は公開されていません。

### 並列と逐次の比較

README の「Process note」には、分け方についての記録があります。

| 方法 | 点数の変化 | 画面を壊す欠陥の数 |
|---|---|---|
| 6人が各ディレクトリを担当する並列ラウンドを3回 | +0.46 | 60 → 47 → 66 |
| 結合している関心事ごとに担当1人で、順番に直す1パス | +1.00 | 66 → 26 |

理由は、トーンマップ、空、間接光が1つの結合した仕組みなので、分担した担当者が互いの前提を壊し続けたためと書かれています。解説記事は「最小の単位に分ける」と勧めていますが、この記録は、分けすぎると逆効果になる例です。分ける単位は、ディレクトリではなく、結合の強さで決めます（[並列エージェント](/agent-dev/parallel-agents/)）。

もう1つの記録は、批評役の指摘が原因を取り違えた例です。3ラウンド続けて、武器が「テクスチャなし」と指摘されました。実際は、反射が強すぎて拡散色が弱かったことが原因で、「明るすぎる」という指摘に応えて色を暗くしていたことが、悪化を招いていました。直し方は、指摘とは逆でした。

### 終わらなかった理由と限界

- 終了条件が「実物に勝つ」で、勝てなかった。作者は、止めた時点でもまだ改善が続いていたと書いています。基準は到達できなくてもよい、という設計どおりに動きました
- 作者は、README の自己評価で Call of Duty に届いていないと明言しています
- 批評役が見るのは静止した画面で、実プレイの性能は見えません。静止カメラの計測では94fpsだったのに、実プレイは12〜17fpsで、700ms超の停止が起きていました。測定の道具（`tools/` の撮影、画像差分、フレーム時間の分布）を先に用意した理由です
- 遊びの設計（ミッション、進行、バランス）は、プロンプトにも README の評価にも含まれていません

## なぜ効くのか、どこで効かないのか

### 効く理由

作者の説明と、公式ブログから、根拠が確認できる原則は次のとおりです。

| 原則 | 根拠 |
|---|---|
| 実物と比べる基準を置く | 作者は、基準を最重要と書く。「ちょっとAIにしては良い」で止まらず、方向が決まる |
| 作る役に説明させず、出力だけを見せる | 作者は、作る役は自分の判断の理由を覚えているので、もっともらしく説明するのが得意だと説明する。公式ブログの「自己優遇バイアス」も同じ問題 |
| 部品を小さくする | 「ゲームを良くして」より「この木を、参照画像の木に並ぶように」の方が、繰り返し攻められる（作者） |
| 区切りを置かない | 基準が高ければ、まだ詰める差が必ず残る。終わりは人か、予算が決める（作者） |

作者以外の事例でも、同じ原則が使われています。

- [THE LONG SILENCE](/cases/oneshot-long-silence/): 24時間の `/goal` に、独立した判定役を置き、Starfield のような宇宙ゲームの画面と見比べさせた。判定役のプロンプトを書き換えて条件を緩めることを禁じている（作者のX投稿）
- [Starfall](/cases/oneshot-starfall/): Shumer 氏のプロンプトを、基準を Homeworld に替えて使った。批評役のスコアは公開されていない
- [fable51-worlds](/cases/oneshot-fable51-worlds/): 設計書型の長いプロンプトだが、独立したレビュー役を置き、「作る役は自分の成果を採点しない」とREADMEに書く

### 費用

| 事例 | 費用 | 出典 |
|---|---|---|
| Claude of Duty | 公開されていない | README、Issue #30 に質問があるが回答なし |
| Starfall | 約633ドル（最初の実行。出力460万トークン、キャッシュ読み取り8億3,720万トークン） | [README](https://github.com/e01-ai/starfall) |
| Union Square（fable51-worlds） | 約33ドル、約2時間、約800万トークン | 作者の Hacker News のコメント（2026年9月2日） |

Starfall では、費用の大半が、長い実行で積み上がった文脈のキャッシュ読み取りでした。批評役を増やしてラウンドを重ねるほど、読み直す量が増えます。費用の考え方は [コスト管理](/agent-dev/cost-management/) にあります。公式ブログも、動的ワークフローは多くのトークンを使うので、複雑で価値の高い作業に向く、通常のコーディングに5人の審査役は要らない、と書いています。

## 自分のゲームで使う手順

3D FPS の画質に限らず、「出力を検査でき、直せる」対象なら使えます。作者も、ゲーム以外（Webサイト、文章、バックエンドなど）に使えると書いています。次は、ゲームの各対象に当てはめる、この記事の提案です。

### 1. 目標と、比べる実物を決める

| 対象 | 比べる実物の例 | 批評役に見せるもの |
|---|---|---|
| 2Dアクションの見た目 | 目標にする既存作のスクリーンショット、自分で描いた完成イメージ | ゲーム画面のスクリーンショット |
| 2Dパズルの盤面 | 読みやすいと感じる既存のパズルの画面 | 盤面のスクリーンショット、手数ごとの画面 |
| UI | 使いやすいと感じるアプリの画面 | 画面遷移のスクリーンショット、実行するタスク |
| ドット絵 | 手本の絵と、自分で決めた制約（解像度、色数） | 絵の拡大画像。色数や解像度は、スクリプトで機械的に検査する |
| 音 | 手本の音源。ただし聞き比べは人が行う | ラウドネス、無音区間、音割れなどの測定値 |
| レベル | 狙うクリア時間、クリア率の表 | ボットが走った結果のログ |

基準が分からないときは、作者の勧めどおり、基準探しも作業に含めます（「この作業で、実物のスクリーンショットに当たる比較や測定は何か」を調べさせる）。
参照に使う画像は、比べるためだけに使い、成果物には混ぜません（後述）。

### 2. 評価の観点と、採点の形式を決める

観点は、5項目以内に絞ります。形式は、次のどれかを選びます。

- どちらが参照かを伏せた A/B 比較で、勝ち負けを出す（Claude of Duty の形式）
- 観点ごとに0〜10点を付ける。毎回、前回の点も見せて、下がった観点を報告させる
- 数値の目標範囲に対して、合格か不合格かを出す（バランス、性能、音量）

どの形式でも、「差が最も大きい点を、場所つきで1〜3件」と出させると、作る役が直せます。好みだけの指摘は、挙げさせません。

### 3. 作る役と批評役を分ける

- 作る役は、部品ごとに1つ。結合している部品（光、色調、影など）は、1人にまとめて順に直す
- 批評役は、毎回新しいコンテキスト（新しいサブエージェント）で起動する。渡すのは、目標、基準、規則、実物の出力だけ。作る役の説明やコードは渡さない
- A/B 比較では、ファイル名を `a.png` と `b.png` のように付け替え、どちらが参照かは司令役だけが知るようにする
- 批評役に編集させない。使えるツールを絞る

Claude Code のサブエージェントは、独自のコンテキストウィンドウ、システムプロンプト、使えるツールを持ち、要約だけを返します。`tools` で許可するツールを絞れます（[Create custom subagents](https://code.claude.com/docs/en/sub-agents)、2026年10月時点）。`.claude/agents/gauntlet-critic.md` の例です。

```markdown
---
name: gauntlet-critic
description: 画面を基準と見比べ、差の大きい点を挙げる批評役。編集はしない
tools: Read, Glob
---

あなたは厳しい批評役です。作る側ではありません。
渡された画像だけで判断し、コードや作業の経緯は読みません。
a.png と b.png のどちらが良いかを選び、選ばなかった方が劣る点を、位置つきで最大3件挙げてください。
好みだけの指摘は挙げません。
```

### 4. 回す回数、時間、費用の上限を決める

作者は「区切りを置かない」と勧めていますが、上限は人が持ちます。作者自身も、止める条件に「使ってよい計算量を使い切ったとき」を挙げています。次を決めておきます。

- 部品ごとの最大ラウンド数
- 全体の時間と、費用の上限
- 先に、小さい範囲（部品1つ）で回し、1ラウンドの費用を見る。公式ドキュメントも、大きな作業の前に小さな範囲で試すことを勧めています（[Orchestrate subagents at scale with dynamic workflows](https://code.claude.com/docs/en/workflows)）

### 5. 終了条件を決める

| 条件 | 例 |
|---|---|
| 基準に勝つ | 批評役が、自作側を選んだ |
| 点数が目標以上 | 全観点が7点以上 |
| 改善が小さい | 2ラウンド続けて、点が0.3点以内しか動かない |
| 上限に達した | 6ラウンド、または2時間 |
| 人が止める | 進捗の画面を見て、気に入った |

### 6. 人が確認するところ

進捗のページを数ラウンドごとに見る、実際に遊ぶ（見た目の合格と遊びの良さは別）、批評役の指摘が原因を取り違えていないか計測で確かめる、費用の速度を見る、の4点です。

### Claude Code での実行

Claude Code の公式ドキュメントで確認できる、実行の道具は次のとおりです（2026年10月時点）。

| 機能 | 内容 | Gauntlet Loop での使い方 |
|---|---|---|
| `/goal` | 完了の条件を渡すと、各ターンの後に別の小さなモデルが条件を確認し、満たされるまで続ける。条件は4,000文字まで。評価するモデルは会話に出た内容だけを見る。`or stop after 20 turns` のような回数の条件を入れられる。`/goal` で状況（経過時間、ターン数、トークン使用量）、`/goal clear` で解除（[Keep Claude working toward a goal](https://code.claude.com/docs/en/goal)） | 「終わらせない条件」と上限を書く。批評役の判定を会話に出させる |
| `/loop` | 一定の時間間隔でプロンプトを再実行する。間隔を省くと Claude が間隔を選ぶ。定期のタスクは作成の7日後に失効する（[Run prompts on a schedule](https://code.claude.com/docs/en/scheduled-tasks)） | 「条件を満たすまで」ではなく「時間ごと」の再実行。条件で回すなら `/goal` |
| サブエージェント | 独立したコンテキストと、制限したツールで動く作業者 | 批評役、作る役 |
| `isolation: worktree` | サブエージェントを専用の worktree で動かす | 作る役が同じファイルを触る場合の隔離（[parallel-agents](/agent-dev/parallel-agents/)） |
| `ultracode` | プロンプトに入れると、Claude が動的ワークフローを書いて多数のサブエージェントを動かす。`/effort ultracode` で、セッション全体を有効にできる。トークンの消費は増える | 作者が大規模な実行で勧めている |

`/goal` の使い方の例です。

```text
/goal reports/critic-latest.json の全部品が「合格」で、npm run verify が終了コード0で終わっていること。または、30ターンで止める。
```

`/goal` の評価役は、ファイルを自分では読みません。批評役の判定をファイルに保存するだけでなく、会話の中に出力させます。また、サブエージェントが動いている間は、そのターンの評価が後回しになります（同ドキュメント）。

## プロンプトのひな形

この記事のために書いたひな形です。`（ ）` の部分を、自分のゲームに置き換えて使います。作者の解説記事のように、設計の細部は書かず、目標、基準、分け方の任せ方、批評役の条件、終わらせない条件の5つだけを書きます。

### 1. 2Dアクションの見た目を磨く

```text
目標: （ゲーム名）の見た目を、docs/reference/ の画像に並ぶ水準まで磨く。遊びのルールと操作は変えない。
分け方: 画面を、個別に直して判定できる部品（背景の層、主人公、敵、エフェクト、HUDなど）に分ける。分け方は任せる。結合している部品（色調、光、影など）は、1人でまとめて順に直す。
部品ごとに、作る役と批評役を1組置く。批評役は毎回新しいコンテキストで起動する。
批評役に渡すもの: 目標、参照画像、npm run shot で撮った現在の画面。作る役の説明、コード、履歴は渡さない。
批評役の仕事: ファイル名を a.png と b.png に付け替えた2枚を見て、良い方を選ぶ。どちらが参照かは、司令役だけが知る。自作側が負けたら、差が最も大きい点を位置つきで最大3件挙げる。好みだけの指摘は挙げない。
作る役の仕事: 指摘を直し、npm run verify を通してから、もう一度批評役に回す。
制約: 参照画像の絵や素材を、ゲームにコピーしない。参照画像は docs/reference/ から出さない。批評役のプロンプトを変えて条件を緩めない。
進捗: docs/progress.html に、部品ごとの画面の推移と判定を並べて更新する。
終わり方: 回数の区切りは置かない。批評役が全部品で自作側を選ぶか、私が止めるまで続ける。ただし、全体で（2）時間か（20）ドルを超えたら、止めて報告する。
```

### 2. ゲームバランスを検証する

```text
目標: （ゲーム名）の（序盤の5ステージ）の難しさを、docs/balance-target.md の目標範囲に収める。
基準: docs/balance-target.md の表（ステージごとの想定クリア率、平均クリア時間、詰まりやすい箇所の数）。これが比べる実物の代わりになる。
作る役: data/balance.json の数値だけを調整する。ステージの構成やルールは変えない。
検証役: 毎回新しいコンテキストで起動する。固定の乱数 seed で、ボットに各ステージを（1000）回遊ばせ、クリア率、平均時間、負けた原因の内訳を表にする。作る役の説明は読まない。
批評役: 検証役の表だけを見て、目標範囲を外れた項目を、外れ幅の大きい順に最大3件挙げる。ボットの限界（人と動きが違う）で説明がつきそうな項目には、その旨を書く。
作る役は、指摘を直して、もう一度検証役に回す。同じ項目が3ラウンド続けて外れたら、数値の調整では難しいとして、理由を報告して止まる。
終わり方: 全項目が目標範囲に入るか、10ラウンドに達するまで。
人が確認すること: 最後に、私が実際に遊んで感想を書く。ボットの結果は、その入口にする。
```

### 3. UIの使いやすさを検証する

```text
目標: （ゲーム名）のメニューと設定画面を、初めて見る人が迷わず使える状態にする。
基準: docs/reference/ の（使いやすいと感じたゲームの画面）、および docs/tasks.md のタスク（「音量を半分にする」「セーブして終了する」など5つ）。
批評役: 初めてこのゲームを見る人の役。毎回新しいコンテキストで起動し、渡されるのは、画面のスクリーンショット（npm run shot-ui で撮る）とタスクの文面だけ。作る役の説明は渡さない。タスクごとに、次にどこを操作するか、操作の理由、迷った箇所、必要だった手数を書く。
作る役: 批評役が迷った箇所を、文言、配置、大きさ、色の面から直す。画面の機能は削らない。
2枚目以降のラウンドでは、前回と同じタスクを新しい批評役にもう一度解かせ、手数が減ったか比べる。
制約: 参照画像の配置や絵をコピーしない。
終わり方: 5つのタスクすべてで、批評役が迷わず、基準の画面と同じかそれ以下の手数で終わるか、8ラウンドに達するまで。
人が確認すること: 私が、スマートフォンとゲームパッドでも触る。
```

## 失敗しやすいところ

| 失敗 | 起きること | 対策 |
|---|---|---|
| 批評役が甘くなる | 作る役が採点すると、自分に甘くなる（公式ブログの自己優遇バイアス）。批評役を同じ文脈で動かすと、同じことが起きる | 批評役は、毎回新しいサブエージェント。説明は渡さず、出力だけ見せる |
| 批評役が条件を緩められてしまう | 司令役が、終わらせるために批評役の基準を書き換える可能性がある（筆者の推測） | THE LONG SILENCE の作者は、判定役のプロンプトを書き換えることを、プロンプトで禁じた |
| 厳しすぎて終わらない | 判定が最後まで満足せず、手動で止めるまで走る（THE LONG SILENCE は24時間走って未完了） | 回数、時間、費用の上限を、先に書く |
| 費用が膨らむ | Starfall は約633ドル。キャッシュ読み取りが大半 | 小さく試す。`/goal` の状況表示でトークン使用量を見る |
| 指摘が原因を取り違える | Claude of Duty の武器の例では、指摘に従うほど悪化した | 指摘は症状として受け取り、計測で原因を確かめる。点が下がったら、元に戻す |
| 見た目だけが良くなる | 遊びのルール、進行、バランスは、批評役の観点に入らない。Starfall は公開後に、操作や縮尺の問題が多く見つかった | 遊びの観点は、別に決め、人が遊んで確かめる |
| 参照の入手と権利 | 既存ゲームの映像や画像を、成果物に混ぜてしまう | 下記 |

### 参照の入手と権利

Claude of Duty の基準は、実際の Call of Duty の画面でした。比べるためだけに見る使い方です。Starfall は、Homeworld の「アート、音声、コード、商標を一切使わない独立したオマージュ」と書いています。自分のゲームでも、次の運用を勧めます（筆者の意見）。

- 参照画像は、比較専用のフォルダに置き、ゲームのビルドに入れない。ソースを公開するなら、リポジトリにも置かない
- 参照を、作る役に見せない。批評役だけが見る。コピーが紛れ込む経路を減らせる
- 絵柄や素材そのものを、成果物に写させない。基準は「質の水準」で、模倣の元ではない
- 公開する素材は、自分で作ったものか、使用許諾のあるものだけにする（[著作権](/legal/copyright/)）

## 手触りと楽しさは、人が決める

Gauntlet Loop が得意なのは、画面に出て、基準と並べられる性質です。

| 得意なこと | 苦手なこと |
|---|---|
| 見た目の質、一貫性、破綻の発見 | 遊んで面白いか |
| 性能、フレーム時間、数値で測れること | 手触り（反動、被弾、ジャンプの感覚） |
| 部品どうしの整合（平滑化パス） | 原因の特定（指摘は症状のみ） |
| 数値の目標への収束（バランス、性能） | 人にとっての分かりやすさの最終確認 |

Claude of Duty の評価は、画質と技術に集中していて、遊びの設計は対象外でした。Starfall も、公開後の修正の多くは操作と可読性でした。THE LONG SILENCE のREADMEは、描画と検証の記述が中心で、7つの共鳴器を集める遊びが楽しいかは書かれていません。
ここは、人が遊んで決める部分です。操作の遅延や、反動、被弾の感覚を数値にして直す方法は [ゲームフィール](/agent-dev/game-feel/)、批評役と測定の道具を作る方法は [検証ループ](/agent-dev/verification-loop/)、人に遊んでもらう方法は [プレイテスト](/design/playtesting/)、数値の調整は [バランス調整](/design/balancing/) にあります。

使い分けの目安は、次のとおりです。見た目を限界まで詰める段階は Gauntlet Loop に任せます。遊びを決める段階は、自分で触って決めます。そのあと、決めた遊びの上でもう一度 Gauntlet Loop を回し、見た目と性能を整えます。
