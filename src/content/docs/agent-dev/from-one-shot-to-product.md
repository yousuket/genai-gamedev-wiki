## 概要

ポン出しで動くものが出た後は、フェーズに分けて進めます。この記事では、各フェーズの目的、人の仕事、エージェントの仕事、プロンプト例、完了の目安を示します。
捨てて作り直す判断の基準と、リポジトリと履歴の扱いも説明します。
全体像は [コーディングエージェントでゲームを作る：全体像](/agent-dev/overview/) にあります。
プロンプト例は、この記事のために書いた例です。

## フェーズの一覧

| フェーズ | 目的 | 完了の目安 |
|---|---|---|
| 0 ポン出し | 素材として動くものを得る | ビルドが通り、画面が出て、30分遊べる |
| 1 方向決め・スコープ縮小 | 残す、捨てる、足すを決める | 残すものが3行で言え、企画書が1ページある |
| 2 縦切り | 一部分を製品品質まで仕上げる | 説明なしで他人が5分遊べる |
| 3 仕様化 | 動くものを文書にする | 仕様と実装が一致し、完了条件が書かれている |
| 4 反復 | 機能追加と調整を回す | 1機能ごとに、完了条件を満たして、コミットされている |
| 5 品質 | 壊れず、速く、誰でも遊べる | テスト、性能、アクセシビリティの合格ラインを満たす |
| 6 出荷準備 | ストアと配布の形に整える | 配布物、ストア素材、開示の整理がそろっている |
| 7 運営 | 出した後の更新を回す | 報告から修正までの流れが決まっている |

## フェーズ0 ポン出し

- 目的: 動くものを素材として得る。ここで作り込まない
- 人の仕事: 何を作らせるかを決め、確かめる手段（ビルド、スクリーンショット）を一緒に渡す。プロンプトと、使ったモデル、日付を記録する
- エージェントの仕事: 実装と自己検証
- 完了の目安: ビルドが通り、画面が出て、30分遊べる

```text
ブラウザで動く、1画面の見下ろしアクションを作ってください（Three.js、Vite、画像・音声ファイルなし）。
- 操作は WASD と、マウスによる狙い撃ち。敵が押し寄せ、60秒生き延びたらクリア
- npm run build が通ること
- headless ブラウザで3枚スクリーンショットを撮り、自分で見て、明らかなずれを直すこと
- 最後に、動作確認の結果と、未実装の点を報告すること
```

終わったら、コミットして `oneshot-v0` のタグを付けます。ポン出しの結果は、後で比べる基準になります。

## フェーズ1 方向決め・スコープ縮小

- 目的: 何を残し、何を捨て、何を足すかを決める
- 人の仕事: 30分遊び、「残す・捨てる・足す」を3行で書く。1ページ企画書を作る（[企画書テンプレート](/design/game-design-doc/)）
- エージェントの仕事: コードの構造の説明、捨てる機能の削除、企画書の穴を質問する
- 完了の目安: 残すものが3行で言え、企画書が1ページある

削るのは、エージェントが得意な作業です。増やすより、減らすほうが、確かめやすいからです。
企画書は、エージェントに質問させて作ります。Claude Code の公式ドキュメントは、最小のプロンプトから始めて、エージェントに詳しく質問させ、最後に SPEC.md に書かせる方法を勧めています（[Best practices](https://code.claude.com/docs/en/best-practices)、2026年9月時点）。

```text
このゲームの1ページ企画書を作りたいです。まず、私に質問してください。
- 遊ぶ人、1プレイの長さ、狙う楽しさ、最大の不安を聞くこと
- 一度に質問するのは3つまで
- 質問が尽きたら、docs/one-pager.md に書いてください
現在のコードは、src/ にあります。まだ変更しないでください。
```

## フェーズ2 縦切り

- 目的: 一部分（1ステージ、1ミッション）を、製品と同じ品質まで仕上げる。全体の仕上がりの見本にもなる
- 人の仕事: 品質の基準を示す（参照するゲーム、スタイルガイド）。仕上がりを遊んで判断する
- エージェントの仕事: 実装、スクリーンショットによる自己点検、批評役のサブエージェントによる見直し
- 完了の目安: 説明なしで他人が5分遊べる

批評役は、Claude of Duty で使われた方法です。作った本人とは別のエージェントに見せると、思い込みの影響が減ります（[事例](/cases/claude-of-duty/)）。ただし、Claude Code の公式ドキュメントが指摘するとおり、指摘を探すよう頼まれた批評役は、作業が適切でも、何か報告します。すべてに応じると、作り込みすぎになるので、正確さと、決めた要件に関わる指摘だけを挙げさせます。

```text
ステージ1を、製品として出せる品質に仕上げてください。基準は docs/style.md と refs/ の画像です。
1. 実装する → スクリーンショットを撮る
2. 別のサブエージェントに、基準と見比べて劣る点を5つ挙げさせる。好みではなく、基準との差だけを挙げさせること
3. 直す
これを3周したら、残った指摘を一覧にして報告してください。
```

## フェーズ3 仕様化

- 目的: 動くものを、文書にする。以降の作業の「正」にする
- 人の仕事: 意図と、完了の条件を決める
- エージェントの仕事: 現状のコードから、仕様の下書きを起こす
- 完了の目安: 仕様と実装が一致し、機能ごとに完了の条件がある

先に長い仕様を書くより、動くものから起こすほうが、手戻りが少なくなります。書き方と、テンプレートは [仕様書駆動](/agent-dev/spec-driven/) にあります。

```text
現在の実装を読み、SPEC.md の下書きを作ってください。
- 実装で確認できたことだけを書く。推測は「推測」と明記する
- 機能ごとに、確かめ方（コマンドか、画面か、人が遊ぶか）を付ける
- 仕様に無い挙動を見つけたら、別の一覧にする
```

## フェーズ4 反復

- 目的: 機能追加と調整を、小さな単位で回す
- 人の仕事: 遊んで判断し、次の指示を書く。手触りを数値で伝える
- エージェントの仕事: 機能実装、テスト追加、修正
- 完了の目安: 1機能ごとに、完了の条件を満たして、コミットされている

回し方の決まりは3つです。

1. 1機能を1コミットにする。依頼の前に、自分の変更をコミットしておく
2. 結びつきの強い部分は、1つの依頼で、1つの担当にまとめる。Claude of Duty では、担当を分けた並列作業は、結びついた仕組みの前提を壊し、不具合が増えました。順番に進めた作業では、不具合が減りました（[README](https://github.com/mshumer/Claude-of-Duty)）。独立した作業だけを並列にします（[並列エージェント](/agent-dev/parallel-agents/)）
3. 席を離れる作業には、終わりの条件をつける。Claude Code の `/goal` は、条件を満たすまで作業を続けさせ、ターンごとに別のモデルが達成を判定します（[Keep Claude working toward a goal](https://code.claude.com/docs/en/goal)、2026年9月時点）

```text
/goal TODO.md の「ステージ2」の項目がすべて完了し、npm test と npm run build が通り、
tools/shot.mjs のスクリーンショットが shots/stage2/ に保存されている。または20ターンで止める
```

## フェーズ5 品質

- 目的: 壊れず、速く、誰でも遊べるようにする
- 人の仕事: 合格ラインを決める。実機で遊ぶ
- エージェントの仕事: テスト、性能計測、修正
- 完了の目安: 決めた合格ラインを、コマンド1つで確認できる

| 観点 | やること | 参考 |
|---|---|---|
| ロジックのテスト | 数式、進行、セーブをテストにする。乱数は固定して結果を再現する | [AI駆動の開発ワークフロー](/dev-env/ai-workflow/) |
| 画面の回帰 | 決まった場面のスクリーンショットを撮り、差分を比べる | 下記 |
| 性能 | 中央値ではなく、下位パーセンタイルと最悪フレームを測る | 下記 |
| アクセシビリティ | 操作の割り当て変更、字幕、音量の個別調整、色だけに頼らない表示 | 下記 |
| 検証の流れ | テストとスクリーンショットを1つのコマンドにまとめる | [検証ループ](/agent-dev/verification-loop/) |

Claude of Duty は、次の3つの知見を残しています（README、2026年9月時点）。

- 中央値では問題が見えなかった。固定カメラの計測は 94 fps でしたが、実際の操作では最大で 1 秒を超える停止がありました。フレーム時間の分布を測るスクリプトで原因（シェーダーの遅延コンパイル）が見つかりました
- 画面の記録に再現性が必要だった。前の場面の影響が残り、同じ操作でも結果が変わったため、場面ごとにページを作り直す方法に変えました。その後、画像の差分が「動いていない」ことの検査として使えるようになりました
- 乱数は決まった関数から取る。`ARCHITECTURE.md` には、ゲームと見た目で `Math.random()` を使わないという規則がありました。再現性のためです

アクセシビリティの最低限は、Game Accessibility Guidelines の基本項目が使えます（[Basic](https://gameaccessibilityguidelines.com/basic/)）。操作の割り当て変更、字幕、効果音と音声とBGMの音量の個別調整、色だけに頼った情報伝達を避ける、読みやすい初期の文字サイズなどが載っています。エージェントに、これらを一覧にして、実装と点検を任せられます。

```text
tools/profile.mjs を作ってください。実際の操作（スクリプト）で60秒間動かし、
フレーム時間の中央値、95・99パーセンタイル、最悪値を出力すること。
中央値だけで判断せず、100ms を超えるフレームの原因を、時刻とともに一覧にしてください。
```

## フェーズ6 出荷準備

- 目的: 配布とストアの形に整える
- 人の仕事: ストアの文面、価格、PVの判断。AI利用の開示の判断
- エージェントの仕事: ビルド、素材の書き出し、依存ライブラリのライセンス一覧、文面の下書き
- 完了の目安: 配布物、ストアの素材、開示の整理がそろっている

ブラウザゲームを itch.io に出すなら、`index.html` を含む ZIP を上げます。展開後のファイルは1,000個まで、全体で500MBまで、1ファイル200MBまで、参照は相対パスにする必要があります（[itch.io Docs](https://itch.io/docs/creators/html5)、2026年9月時点）。
Steam のコンテンツアンケートは、プレイヤーが目にするAI生成コンテンツを、事前生成とゲーム中の生成に分けて開示することを求めています（[Steamworks](https://partner.steamgames.com/doc/gettingstarted/contentsurvey)、2026年9月時点）。どこにAIを使ったかを、記録から起こせるように、[ポン出しの記録](#リポジトリと履歴の扱い) を残しておきます。
販売先の選び方は [ストアの選び方](/monetization/platforms/) と [ウィッシュリスト](/monetization/wishlists/) 、PVは [トレーラーの構成](/trailer/structure/) と [Steamトレーラー](/trailer/steam-trailer/) 、規約は [プラットフォームのAIポリシー](/legal/platform-policies/) と [生成AI素材の著作権](/legal/copyright/) を参照してください。

```text
配布用のビルドを作り、次を確認する npm run release:check を作ってください。
- dist/ に index.html があり、ファイル数が1,000以下で、合計が500MB以下
- 絶対パスの参照が無い
- 依存ライブラリと、そのライセンスの一覧を LICENSES.md に出力する
```

## フェーズ7 運営

- 目的: 出した後の更新を、決まった流れで回す
- 人の仕事: 何を直し、何を直さないかを決める。プレイヤーとの対話
- エージェントの仕事: 報告の再現、修正、リリースノートの下書き、CIの見守り
- 完了の目安: 報告から修正までの流れが決まっている

報告は1件ずつイシューにし、エージェントに再現するテストを書かせます。Claude Code の `/loop` を使うと、CIの結果を一定間隔で確認させ、失敗を直させることもできます（[Run prompts on a schedule](https://code.claude.com/docs/en/scheduled-tasks)、2026年9月時点）。

## 捨てて作り直す判断の基準

| サインを見たら | 判断 |
|---|---|
| 同じ不具合を2回直させて、まだ直らない | 会話をリセットし、学んだことを入れた、より具体的なプロンプトで頼み直す（公式ドキュメントの推奨） |
| 1つの変更が、想定外の複数ファイルに波及する | 結びつきが強すぎる。その部分を、1つの担当に集め、構造を見直す |
| 壊れたかを確かめる手段がない | 先に検証を作る。作れない構造なら、作り直す |
| 構造を、自分もエージェントも説明できない | 構造の地図（ARCHITECTURE.md）を作る。作れなければ、作り直す |
| コアループそのものを変えたい | コードより仕様が変わる。別ブランチで、縦切りからやり直す |
| 性能の原因が、設計にある | 該当する部分を、再設計する |

戻し方は、軽い順に4段階です。

1. `/rewind`（会話とコードを、前の時点に戻す）
2. Git で該当のコミットを戻す
3. 該当のモジュールを書き直す
4. 仕様、テスト、スタイルガイドを持ち込み、最初から作り直す

`/rewind` は、Claude Code が直接編集したファイルだけを戻します。Bash コマンドによる変更と、サブエージェントによる変更は、戻せません。恒久的な履歴として Git を使い続けます（[Checkpointing](https://code.claude.com/docs/en/checkpointing)、2026年9月時点）。
同じプロンプトを別の作者が使って、別のシューティングを作り直した例もあります（[Decrypt](https://decrypt.co/374560/dumbest-ai-prompt-claude-beat-careful-game-design)）。

作り直しても、捨てるのはコードだけです。仕様、プロンプト、テスト、検証のスクリプト、スタイルガイド、決定の記録は、次に持ち込みます。

## リポジトリと履歴の扱い

```text
mygame/
  CLAUDE.md            # エージェントへの指示（AGENTS.md でもよい）
  SPEC.md              # 仕様
  TODO.md              # 作業の一覧
  docs/
    oneshot.md         # ポン出しのプロンプト、モデル、日付
    style.md           # スタイルガイド
    decisions/         # 決定の記録（捨てた理由を含む）
  src/
  tools/               # shot.mjs、playtest.mjs、profile.mjs
  tests/
  shots/               # スクリーンショット（Git LFS か .gitignore）
```

- main は、常にビルドが通る状態にします。実験は `exp/` のブランチで行い、採用するものだけ取り込みます
- ポン出しの直後に `oneshot-v0`、縦切りの完了時に `vertical-slice` のタグを付けます
- 並行して試すときは、Git のワークツリーで作業場所を分けます（[worktrees](https://code.claude.com/docs/en/worktrees)）
- 大きなバイナリは、Git LFS で管理します（[AI駆動の開発ワークフロー](/dev-env/ai-workflow/)）
- 捨てる判断をしたら、理由を `docs/decisions/` に1行で書きます。同じ失敗を、次のエージェントが繰り返さなくなります
