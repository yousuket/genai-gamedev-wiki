## 概要

- コーディングエージェントへの依頼を、場面別の「型」にして紹介します。初期生成（ポン出し）、機能追加、バグ修正、見た目の調整、バランス調整、リファクタリング、性能改善、テスト作成、レビュー、方針を決める前の相談の10種類です。
- どの型にも共通するのは、目的・範囲・制約・確認方法を書くことです。エージェントは「動いたように見えた」時点で作業を止めるため、確認方法を渡すかどうかで結果が大きく変わります。
- 記事中のプロンプトは、このWikiのために書いた例です。プロジェクトに合わせて固有名詞と数値を置き換えて使ってください。
- 毎回書く前提（コマンド、規約）は [プロジェクトの指示ファイル](/agent-dev/project-instructions/) に移し、確認の仕組みは [検証ループ](/agent-dev/verification-loop/) で用意します。

## 依頼の基本形

Claude Code の公式ベストプラクティスは、精度の高い指示ほど修正の回数が減るとして、対象ファイルの指定、既存パターンの参照、症状の説明などを勧めています（[Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)、2026年9月時点）。ゲーム開発では、次の5点を毎回意識すると型を作りやすくなります。

| 要素 | 書くこと | 例 |
|---|---|---|
| 目的 | どんな体験・結果にしたいか | 敵に近づかれたときに焦りを感じさせたい |
| 範囲 | 触ってよい場所と触らない場所 | `src/enemies/` と `tuning.ts` のみ。シーン定義は触らない |
| 制約 | 技術、数値、性能、依存 | 追加ライブラリなし。60fpsを維持 |
| 確認方法 | 実行コマンド、見る画面、テスト | `npm run verify` が通る。スクリーンショットで確認 |
| 完了の条件 | どうなれば終わりか | 敵5体同時でエラーなし、HUDが重ならない |

同じ公式ガイドは、確認の手段（テスト、ビルド、スクリーンショットとの比較）を渡すと、エージェントが結果を読んで直す流れを自分で回せるようになると説明しています。

## 悪い例と良い例

| 場面 | 悪い例 | 良い例 |
|---|---|---|
| 手触り | ジャンプを気持ちよくして | ジャンプの滞空時間を0.55秒、最高点を3.2マスにする。値は `tuning.ts` の `player.jump` に置く |
| バランス | 敵が弱いので強くして | ステージ3のクリア率をシミュレーションで測ると80%。目標は50%。敵HPと出現間隔のどちらを変える案がよいか、変更前に3案を数値つきで出す |
| バグ | 動かないので直して | 再現手順、出たログ、期待する動きの3点を書く（後述） |
| 見た目 | もっとかっこよくして | 参照画像を貼り、「HUDの余白を8pxに」「被弾時に画面端を赤く0.2秒」のように差分を指定する |
| 性能 | 重いので軽くして | 戦闘シーンで p95 が40ms。目標は20ms未満。計測は `npm run perf`。見た目は変えない |

悪い例の共通点は、エージェントが自分で「直ったか」を判定できないことです。良い例は、数値か確認コマンドのどちらかが必ず入っています。

## 1回の依頼の大きさ

| 大きさ | 目安 | 進め方 |
|---|---|---|
| 小 | 差分が1文で言える。1〜2ファイル | 計画なしで直接頼む |
| 中 | 1機能。数ファイルにまたがる | 先に計画を出させ、確認してから実装。1機能を1コミットにする |
| 大 | 複数機能、新しいサブシステム | 仕様書に分け、機能ごとに別セッションで実装する |

公式ガイドにも「差分を1文で説明できるなら計画は省く」という趣旨の目安があります。大きな機能は、エージェントに質問させて仕様（`SPEC.md`）を書かせ、実装は新しいセッションで始める流れが紹介されています。長い会話の扱いは [長期プロジェクトのコンテキスト管理](/agent-dev/context-management/) を参照してください。

## 前提や制約を先に書かせる

依頼の直後にコードを書かせず、前提を先に出させると、勘違いを実装前に潰せます。

```text
実装の前に、次を箇条書きで答えてください。コードはまだ書かないでください。
1. 変更するファイルと、変更しないファイル
2. 置いている仮定（不明点は推測で決めず、質問に回す）
3. 合わせる既存のパターン（例: 既存の敵クラスの作り方）
4. 完了を確かめる方法（実行するコマンド、見る画面）
質問がある場合は、選択肢つきでまとめて聞いてください。
```

大きな機能では、逆に質問攻めにさせる方法もあります。

```text
ダッシュ機能を作りたいです。実装の前に、私に質問してください。
操作感、既存の回避との関係、エッジケース、見た目の演出について、
自明でない部分を中心に聞き、聞き終えたら docs/specs/dash.md にまとめてください。
```

Claude Code では、計画だけを作らせる「プランモード」（`Shift+Tab` で切り替え）も使えます。

## 場面別の型

### 1. 初期生成（ポン出し）

型: ゲームの姿、進め方、確認できる仕組み、品質の見方の4ブロックに分けます。

```text
Three.js と TypeScript（Vite）で、ブラウザで遊べる見下ろし型のウェーブサバイバルを作ってください。

# ゲーム
- 1プレイ3〜5分。プレイヤーは移動のみで、武器は自動発射。敵が波状に押し寄せる。HPが0でゲームオーバー。
- 画像・音声ファイルは使わない。見た目は図形、効果音は Web Audio で生成する。

# 進め方
- 最初に docs/SPEC.md へ仕様と完了条件を書き、その後に実装する。
- 数値（速度、HP、出現間隔）は src/tuning.ts に集約する。
- 乱数は seed を渡せる自作関数を使い、Math.random() は使わない。

# 確認できる仕組み
- URL に ?debug=1&seed=N を付けると window.__game で状態を読める。
- npm run verify で、ヘッドレスブラウザの起動、60秒のボットプレイ、スクリーンショット保存、コンソールエラー0件の確認まで行う。
- verify が通るまで直してから報告する。

# 品質
- 完成後、別のサブエージェントに批評役を頼み、docs/reference/ の目標画像と見比べさせて、指摘を3つ直す。
```

Claude of Duty の元プロンプトは、Call of Duty 水準という目標、要素ごとにサブエージェントへ分担させる指示、実際のゲームと見比べる厳しい批評役の3点が中心です（[prompt.md](https://github.com/mshumer/Claude-of-Duty/blob/main/prompt.md)、2026年9月時点）。上の例は、その骨格に「確認できる仕組み」を明示して再現しやすくした形です。ポン出しの結果とその後の進め方は [ポン出し（一発生成）の実際](/agent-dev/one-shot/) と [事例: Claude of Duty](/cases/claude-of-duty/) を参照してください。

### 2. 機能追加

型: 既存の似た機能を指し、範囲と完了条件を書きます。

```text
ダッシュ機能を追加してください。
- 既存の「回避」（src/player/dodge.ts）と同じ構成で作る。状態は PlayerState に追加する。
- Shift で発動。0.2秒で3マス進み、クールダウンは1.5秒。数値は tuning.ts の player.dash に置く。
- ダッシュ中は敵との接触ダメージを受けない。
- 変更するのは src/player/ と tuning.ts のみ。
- 完了の条件: クールダウンと無敵時間のユニットテストが通ること、npm run verify が通ること。
```

### 3. バグ修正

型: 再現手順、実際の動作とログ、期待する動作の3点セットに、「まず再現するテストを書く」を添えます。公式ガイドも、症状と場所と「直った状態」を伝える書き方を勧めています。

```text
バグを直してください。
再現手順: ステージ2で敵を10体以上倒したあと、ポーズして再開する。
実際の動作: 敵の動きが止まり、コンソールに次のエラーが出る。
  TypeError: Cannot read properties of undefined (reading 'position') at Spawner.update (spawner.ts:88)
期待する動作: 再開後も敵が動き続ける。
まず、この不具合を再現する失敗テストを書き、それが通るように直してください。
原因を直し、エラーの握りつぶし（try/catch で隠すなど）はしないでください。
```

### 4. 見た目の調整

型: 参照画像を渡し、「差」を数値と場所で指定して、スクリーンショットで確かめさせます。

```text
添付の参照画像に近づけてください。差は次の3点です。
1. HUDのHPバーを左上に移動し、画面端からの余白を16pxにする。
2. 被弾時に画面の四隅を赤く0.2秒光らせる（不透明度は最大0.4）。
3. 敵の色を #d94f4f に統一する。
変更のたびに npm run shot でスクリーンショットを撮り、参照画像と見比べて、残っている差を箇条書きで報告してください。
```

### 5. バランス調整

型: 目標の数値、測り方、変えてよいパラメータを渡します。詳しい手順は [バランス調整](/design/balancing/) を参照してください。

```text
ステージ3が難しすぎます。目標は「初見のクリア率50%前後」です。
- 測定: npm run sim -- --stage 3 --runs 2000 --seed 1 の結果（clearRate）で判断する。現状は 0.18。
- 変えてよいもの: src/tuning.ts の enemy.hp、spawn.interval のみ。
- 変えないもの: プレイヤーの性能、他のステージ。
まず変更案を3つ、予想される clearRate つきで出し、実際に3つとも測定して、結果の表を報告してください。採用はこちらで決めます。
```

### 6. リファクタリング

型: 挙動を変えないための固定手段（テスト、スクリーンショット比較）を先に決めます。

```text
src/game.ts（1,800行）を分割してください。
- 挙動は一切変えない。分割の前後で npm run verify の出力とスクリーンショットが一致すること。
- 分割単位は「入力」「スポーン」「衝突判定」「HUD」。各ファイルは400行以内を目標にする。
- 1モジュールごとにコミットし、各コミットで verify を通す。
- 新機能の追加や名前の変更はしない。
```

### 7. 性能改善

型: 計測方法と目標値、「見た目を変えない」条件をセットで渡します。

```text
戦闘シーンのカクつきを減らしてください。
- 計測: npm run perf（frame time の p50 / p95 / p99 と、最悪フレームを出力する）。
- 現状: p95 が42ms、最悪フレームが310ms。目標: p95 が20ms未満、最悪フレームが50ms未満。
- 平均fpsだけで判断しない。最悪フレームの原因を、コード上の根拠つきで先に特定する。
- 見た目は変えない。スクリーンショット比較（npm run imagediff）で差分0を保つ。
```

### 8. テスト作成

型: テストする対象と観点、避けたいこと（モックの多用など）を指定します。

```text
src/combat/damage.ts のテストを書いてください。
- 観点: 防御が攻撃を上回る場合、会心、ダメージの下限(1)、端数の丸め。
- 期待値は仕様（docs/specs/combat.md）から決める。今のコードの出力をそのまま期待値にしない。
- モックは使わず、実際の関数を呼ぶ。
- 書いたテストが本当に失敗しうるか確認するため、実装を一時的に壊して、失敗することを見せてください。
```

### 9. レビュー依頼

型: 書いたエージェントとは別の、新しい文脈でレビューさせ、指摘の基準を絞ります。公式ガイドは、修正を実装した会話とは別のサブエージェントに差分を見せる方法を紹介しています。一方で、指摘を無条件に全部直すと過剰な設計になりやすいとも述べています。

```text
サブエージェントで、直近のコミット差分を docs/specs/dash.md と照らしてレビューしてください。
見るのは、仕様の未実装、テストのない分岐、仕様範囲外の変更の3点です。
好みの問題（命名、書き方）は報告しないでください。指摘は、該当ファイルと行、直し方の案つきで出してください。
```

### 10. 方針を決める前の相談

型: 実装をさせず、選択肢と判断基準を出させます。

```text
敵AIの実装方針を相談したいです。コードはまだ書かないでください。
条件: 同時に最大80体、ブラウザで60fps、実装は1週間以内。
「ステートマシン」「ビヘイビアツリー」「単純な追跡＋群れ回避」の3案を、実装量、挙動の面白さ、デバッグのしやすさ、今回の条件への適合で表にして比較し、推奨を1つ選んでください。
選んだ理由と、その案が失敗する条件も書いてください。
```

## うまくいかないとき

- 同じ指摘を2回しても直らないときは、会話に失敗した試行が溜まっています。公式ガイドは、その場合は会話をクリアして、学んだことを織り込んだ新しい依頼で始め直すことを勧めています。
- 同じ注意を何度も書いているなら、[指示ファイル](/agent-dev/project-instructions/) に移します。
- 手触りのように数値で言えない指摘は、[ゲームの手触りをエージェントと詰める](/agent-dev/game-feel/) の手順で、言葉を数値に変えてから依頼します。
- 各モデルで実際にどんなプロンプトが使われたかは [モデル別の事例](/cases/prompts-by-model/) を参照してください。
