## 概要

エージェントに任せた開発は、速く進む一方で、人が書くときとは違う種類の失敗が起きます。
この記事では、見た目だけ立派で中身が空、巨大ファイルの肥大化、同じバグの往復、頼んでいない機能の追加、テストの書き換え、依存パッケージの増殖、破壊的な変更、性能の劣化、コンテキストの劣化、手戻りの10種類を、「兆候→原因→対策」で整理します。
出典は、Anthropic の公式ドキュメントとエンジニアリング記事、Claude of Duty のリポジトリ、公開されている研究や事故の報告です。

## 10の失敗の一覧

| # | 失敗 | 最初の一手 |
|---|---|---|
| 1 | 見た目だけ立派で中身が空 | 実際に遊べるかを、スクリプトで操作して確認する |
| 2 | 巨大ファイルの肥大化 | ファイルの行数に上限を設け、リンターで検出する |
| 3 | 同じバグの往復 | 2回直して直らなければ、`/clear` して再現手順つきで頼み直す |
| 4 | 頼んでいない機能の追加 | 範囲を指示に明記し、差分を見る |
| 5 | テストを書き換えて通す | テストを編集禁止にする |
| 6 | 依存パッケージの増殖 | 新規依存を禁止し、`package.json` の差分を見る |
| 7 | 破壊的な変更 | 作業前にコミットし、回帰テストを用意する |
| 8 | 性能の劣化 | 中央値ではなく、p99 とカクつきを測る |
| 9 | コンテキストの劣化 | 節目で `/clear` し、進捗をファイルに書く |
| 10 | 手戻り | 計画を先に作り、小さく区切ってコミットする |

## 1. 見た目だけ立派で中身が空

**兆候**: スクリーンショットは良いのに、遊ぶと動かない。ボタンを押しても何も起きない。エージェントは「完成しました」と報告する。

**原因**: エージェントは、確認手段がないと、見た目やコードの形で「できた」と判断します。Anthropic の長時間エージェントの記事では、機能を通しで確かめずに完了と印を付ける傾向と、後半に「すでにかなり進んだ」と見て完了を宣言する傾向が報告されています。単体テストや `curl` は通っても、機能が端から端まで動いているとは限りませんでした。Claude of Duty の README でも、作者が「届かなかった点」として、マネキンのような敵、ノイズに見える表面、ブロック状の手を挙げています。

**対策**:
- 完成の条件を「操作して確かめられる形」で書く。「敵が倒れる」ではなく「スクリプトで移動して発砲し、敵の体力が減ること」
- ブラウザ自動化（Playwright など）で、実際に操作して結果を撮る。Anthropic の記事では、ブラウザ操作のツールを明示的に使わせると、コードだけでは見えないバグを見つけて直せるようになったと報告されている
- 機能を一覧にして、合否をファイルに残す。同じ記事では、機能一覧を JSON にして、エージェントに変更を許す欄を合否だけにする方法が紹介されている
- Claude of Duty は、移動と発砲を自動で試す簡易テスト（`tools/playtest.mjs`）を用意している

詳しい進め方は [検証ループ](/agent-dev/verification-loop/) を参照してください。

## 2. 巨大ファイルの肥大化

**兆候**: 1つのファイルが何千行にもなる。修正のたびに、エージェントがそのファイルを丸ごと読み込む。似た処理があちこちにコピーされている。

**原因**: エージェントは、既存のファイルに追記する方が手軽なため、新しいファイルに分けずに足し続けがちです。筆者が Claude of Duty のリポジトリ（2026年9月29日時点）を数えたところ、最大のファイルは `src/world/dressing.js` の2,269行で、2,000行を超えるファイルが2つありました。GitClear の2024年までの調査でも、コピー＆ペーストされたコードの割合が2021年の8.3%から12.3%に増え、リファクタリング（コードの移動）に当たる変更の割合が25%から10%未満に減ったと報告されています。

**対策**:
- 行数の上限をリンターで検査する。ESLint の `max-lines` ルールが使える

```js
// eslint.config.js
export default [
  { rules: { 'max-lines': ['error', { max: 400, skipBlankLines: true, skipComments: true }] } },
];
```

- 指示ファイルに「1ファイル400行まで。超えそうなら分割案を先に出す」と書く（[プロジェクト指示ファイル](/agent-dev/project-instructions/)）
- 定期的に整理の作業を回す。Claude Code の `/goal` は、完了条件が満たされるまで作業を続ける機能で、公式の例に「大きなファイルを、それぞれが行数の予算に収まるまで分割する」が挙がっている
- Carlini 氏の C コンパイラの実験では、重複したコードをまとめる専任のエージェントを置いている

## 3. 同じバグの往復

**兆候**: 「直しました」「まだ直っていません」を何度も繰り返す。直すたびに別の場所が壊れる。

**原因**: 修正に失敗した試行が会話に積み重なり、コンテキストが失敗のやり取りで汚れます。Claude Code の公式ベストプラクティスは、同じ問題で2回以上直してもらったなら、コンテキストが失敗した方法で散らかっているので、`/clear` して、学んだことを入れた具体的なプロンプトで始め直すことを勧めています。原因を再現できないまま推測で直している場合も多くあります。

**対策**:
- 症状を再現する手順（または失敗するテスト）を先に作らせる
- 「症状を隠さず、根本原因を直す」と指示し、エラー文と再現手順を貼る
- 2回直して直らなければ `/clear` し、これまでの失敗を「試したこと」として書き足して頼み直す
- 巻き戻したいときは `/rewind`（チェックポイント）を使う。ただしチェックポイントは、Claude のファイル編集ツールでの変更だけを記録し、Bash 経由の変更は対象外なので、Git のコミットが要る
- Carlini 氏の実験では、行き詰まったエージェントが「失敗した方法」と「残りの作業」の一覧を自分で書き続けていた

## 4. 頼んでいない機能の追加

**兆候**: 依頼していない設定画面、デバッグ用のキー、ログ機能が増えている。1つのバグ修正で、周辺のコードまで書き換わっている。

**原因**: モデルには、依頼の範囲を広げる傾向があります。Anthropic のプロンプトガイドは、Opus 4.5 と 4.6 に、余計なファイルや抽象化、頼まれていない柔軟性を足す傾向があると説明し、Opus 5 についても、頼まれていない手順を足したり、作業の範囲を自分で判断して変えたりすることがあると説明しています。

**対策**: 範囲を指示に書きます。公式のガイドに例がある指示を、ゲーム向けに書き換えた例です（この記事のために書いた例です）。

```text
依頼された変更だけを行ってください。
- 頼まれていない機能、設定項目、デバッグ用の機能を足さない
- バグ修正のついでに、周辺のコードを整理しない
- 一度きりの処理のために、汎用のヘルパーや抽象化を作らない
- 依頼が間違っていると思ったら、1文で伝えたうえで、依頼どおりに進める
```

- 計画モードで先に変更するファイルを確認する。差分を1文で言えるほど小さい変更なら、計画は不要
- 変更後に `git diff --stat` で、変更されたファイルの数と量を見る
- 別のサブエージェントに差分を見せる場合は、「正しさと要件に関わる問題だけを報告する」と指示する。公式のベストプラクティスは、指摘を探す役は、健全な変更にも何か指摘をするので、全部に応えると過剰な設計になると注意している

## 5. テストを書き換えて通す

**兆候**: テストが全部通ったのに、ゲームは動かない。テストの期待値が、いつの間にか変わっている。テスト用の値をそのまま返す実装になっている。

**原因**: 「テストを通す」が目的になると、一般的な解ではなく、通す近道を取ることがあります。Anthropic は Claude 4 の発表で、ショートカットや抜け道を使いやすい作業では、新モデルの発生率が Sonnet 3.7 より65%低いと説明しています。この説明は、以前のモデルでこの傾向が目立ったことを示しています。プロンプトガイドにも、テストを通すことに集中しすぎて一般的な解を作らなくなる場合の指示例があります。

**対策**:
- 仕様を表すテストを編集禁止にする。Claude Code は、`permissions.deny` に `Edit(パス)` を書くと、そのパスの編集を拒否する

```json
{
  "permissions": {
    "deny": ["Edit(tests/spec/**)"]
  }
}
```

- 指示に「テストが間違っていると思ったら、編集せずに報告する」と書く。Anthropic の長時間エージェントの記事でも、「テストを削除したり編集したりしてはならない」と強く指示している
- テストを書くセッションと、実装するセッションを分ける。公式のベストプラクティスにも、片方がテストを書き、もう片方が通るコードを書く分担が挙がっている
- Carlini 氏は、エージェントが自律で動くほど、検証役が完璧に近くないと「間違った問題を解く」と述べ、テストの作り込みに最も時間をかけたと報告している

## 6. 依存パッケージの増殖

**兆候**: 小さなゲームなのに `node_modules` が巨大になる。`package.json` に、知らないパッケージが並んでいる。存在しないパッケージ名のインストールに失敗する。

**原因**: エージェントは、必要になるたびにパッケージを足します。さらに、存在しないパッケージ名を「それらしく」出力する現象（パッケージのハルシネーション）が研究で報告されています。USENIX Security 2025 で発表された調査では、16のモデルが書いた57.6万件のコードを分析し、実在しないパッケージの割合が、商用モデルで少なくとも5.2%、オープンソースのモデルで21.7%でした。攻撃者が、その名前を先に登録して悪意のあるコードを配る危険もあります（スロップスクワッティングと呼ばれます）。

**対策**:
- 指示に「新しい依存を足さない。必要なら理由を書いて聞く」と書く。Claude of Duty の設計書は、依存を `three` だけに固定し、CDN からの取得や外部ファイルも禁止している
- 完了の前に `package.json` と `package-lock.json` の差分を見る
- 新しい依存を許すときは、パッケージ名、公開元、直近の更新日を人が確認してからインストールする

## 7. 破壊的な変更

**兆候**: 新機能を足したら、以前は動いていた機能が壊れた。ファイルやセーブデータが消えた。

**原因**: エージェントは、明示された範囲の外の副作用を見落とします。Carlini 氏の実験では、終盤に、新機能を実装するたびに既存の機能を壊すようになったと報告されています。人が書いたコードでも起きますが、変更量が多い分、気づきにくくなります。

より深刻な例として、2025年7月に、Replit のAIエージェントが、コードの凍結を指示されていたにもかかわらず、利用者の本番データベースを削除した事案が報じられています。エージェントは、復旧は不可能だと説明しましたが、実際にはロールバックできたとされています（[The Register](https://www.theregister.com/2025/07/21/replit_saastr_vibe_coding_incident/)）。

**対策**:
- エージェントに作業させる前に、自分の変更をコミットする。1機能ごとにコミットする
- 回帰テストを CI（自動実行）に入れ、コミットが既存機能を壊さないようにする。Carlini 氏は、実験の終盤にこの仕組みを入れて対処した
- 見た目が変わらないはずの変更（性能改善など）では、スクリーンショットの差分を検査する。Claude of Duty は、1ピクセルでも動いたら失敗にするツール（`tools/imagediff.mjs`）を使い、最適化前後で画面が完全に同じであることを確かめている
- 本番のデータや認証情報を、開発用のエージェントに渡さない。作業は worktree など隔離した場所で行う（[サブエージェントと並列開発](/agent-dev/parallel-agents/)）

## 8. 性能の劣化

**兆候**: 開発中は軽いのに、実機で重い。ときどき数百ミリ秒止まる。見た目を良くするたびにフレームレートが下がる。

**原因**: エージェントは、見た目を良くする作業で描画の負荷を増やします。しかも、計測の方法が甘いと、問題に気づけません。Claude of Duty の README には、具体的な記録があります。

- 静止したカメラのベンチマークでは94fps と出たのに、実際のプレイ（Retina の解像度）では12〜17fps で、728〜1,236ミリ秒の停止が起きていた。原因は、34個以上のシェーダーがフレームの途中で遅れてコンパイルされていたこと
- 見た目を良くする作業で三角形の数が590万から1,130万に増え、最適化でその約半分を取り戻した

**対策**:
- 性能の予算を、設計書に書く。Claude of Duty は、フレームごとのメモリ確保の禁止、品質ごとのパーティクル数の上限などを設計書に書いている
- 中央値ではなく、下位パーセンタイル（p95、p99）と最悪のフレームを測る。次のコードは、フレーム間隔から p50・p95・p99 を出す最小の例です

```js
const times = [];
let last = performance.now();

export function tick(now) {           // requestAnimationFrame のコールバックの先頭で呼ぶ
  times.push(now - last);
  last = now;
}

export function report() {
  const sorted = [...times].sort((a, b) => a - b);
  const q = (p) => sorted[Math.min(sorted.length - 1, Math.floor(sorted.length * p))];
  return { p50: q(0.5), p95: q(0.95), p99: q(0.99), worst: sorted.at(-1) };
}
```

- シェーダーを、最初のフレームの前に先にコンパイルしておく。Claude of Duty は、この対策（プリウォーム）で、プレイ中のコンパイルを34〜35回から0回にした
- 実機に近い条件（解像度、ブラウザ）で測る。計測の設計は [ブラウザゲームの技術選定](/agent-dev/web-game-stack/) も参照

## 9. コンテキストの劣化

**兆候**: 会話が長くなるにつれて、指示を忘れる、同じ質問を繰り返す、ミスが増える。

**原因**: Claude Code の公式ベストプラクティスは、ほとんどの推奨事項が「コンテキストウィンドウはすぐに埋まり、埋まるほど性能が落ちる」という制約に基づいていると説明しています。研究でも、Chroma が18のモデルで調べた「コンテキストの腐敗」の報告（2025年7月）で、入力が長くなるにつれて、単純な課題でも性能が不均一に低下すると示されています。Anthropic の長時間エージェントの記事は、圧縮（コンパクション）だけでは、次のセッションに十分明確な指示が渡らないことがあると報告しています。

**対策**:
- 関係のない作業に移るときは `/clear` する
- 進捗をファイルに書かせる。同じ記事では、進捗の記録ファイルと Git の履歴を、新しいセッションの最初に読ませる方法が紹介されている
- 調べ物はサブエージェントに任せ、要約だけを受け取る
- 指示ファイルは200行未満にする。長いと、重要な指示が埋もれる

詳しくは [コンテキスト管理](/agent-dev/context-management/) を参照してください。

## 10. 手戻り

**兆候**: 実装が終わってから「そういう意味ではなかった」と気づく。大きな機能を一度に頼んで、途中で止まり、半分だけ実装された状態になる。

**原因**: 方向が違うまま、大きく作り始めているからです。Anthropic の長時間エージェントの記事では、エージェントが一度に多くをやろうとして、実装の途中でコンテキストを使い切り、機能が半分だけ実装された状態で次のセッションに引き継がれる例が挙がっています。Claude of Duty でも、批評役の指摘に従って3ラウンド調整した結果、指示とは逆の修正が正解だったことが後から分かっています（[サブエージェントと並列開発](/agent-dev/parallel-agents/)）。

**対策**:
- 調べる、計画する、実装する、コミットするの順に分ける。公式のベストプラクティスは、差分を1文で言えるほど小さい変更なら計画を省いてよいとしている
- 仕様と完成の条件を先に書く（[仕様駆動の進め方](/agent-dev/spec-driven/)）
- 一度に頼む機能は1つにする。Anthropic の記事では、1回に1機能だけに取り組ませる方法で、一度に多くをやろうとする問題に対処している
- 動く最小の版（縦に薄い一通りの流れ）を先に作る。作る範囲の決め方は [スコープの決め方](/getting-started/scope/) を参照

## 予防のためのセット

次の4点を最初に整えると、上の失敗の多くを防げます。

| 用意するもの | 防げる失敗 |
|---|---|
| 指示ファイル（範囲、上限、禁止事項） | 2, 4, 6 |
| 編集禁止のテストと、実際に操作して撮る確認スクリプト | 1, 5, 7 |
| 計測のスクリプト（p99、スクリーンショットの差分） | 7, 8 |
| こまめなコミットと、`/clear` の習慣 | 3, 7, 9, 10 |
