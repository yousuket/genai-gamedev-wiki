## 概要

ポン出しとは、1回のプロンプトで、動くゲームを一気に作らせることです。
この記事では、2026年9月時点で公開されている事例をもとに、ポン出しで作れるもの、作れないもの、ジャンル別の到達点を整理します。
Claude of Duty を具体例にして、ポン出しで足りる場合と足りない場合の判断基準も示します。
事例の詳細は [事例: Claude of Duty](/cases/claude-of-duty/) にあります。ここでは要点と、限界の整理に絞ります。
プロンプト例は、この記事のために書いた例です。

## ポン出しとは何か

「1プロンプト」には3つの意味があり、事例を読むときに区別が要ります。

| 種類 | 意味 | 例 |
|---|---|---|
| 1回の応答 | モデルが1回返した文章だけでゲームができる | 小さなミニゲームの単一ファイル |
| 1回の指示、長い作業 | 人が書くのは1回だが、エージェントが実行と検証を繰り返して長時間動く | Claude of Duty |
| 短い指示を数回 | 最初の指示の後、数ターンだけ軌道修正する | 最初の生成の後で数回だけ直して公開するデモ |

Claude of Duty は2番目です。README も、複数のエージェントが役割を分けて作業したと説明しています（[README](https://github.com/mshumer/Claude-of-Duty)）。
この記事で「ポン出し」と呼ぶのは、主に2番目です。人の入力は1回でも、裏ではエージェントが何度もビルドし、画面を見て、直しています。

## 2026年時点で作れるもの

2026年7月24日に Anthropic が Claude Opus 5 を公開しました。モデルIDは `claude-opus-5`、料金は入力100万トークンあたり5ドル、出力25ドルです（[Introducing Claude Opus 5](https://www.anthropic.com/news/claude-opus-5)、2026年9月時点）。公開直後から、このモデルとエージェントを組み合わせたポン出しの事例が相次ぎました。

| 種類 | 事例 | 規模と条件 |
|---|---|---|
| 3Dシューティング | Claude of Duty（Matt Shumer 氏） | Three.js、約5.5万行、11のサブシステム、画像や音声のファイルなし |
| 3D宇宙探索 | The Long Silence（Anshu 氏） | Opus 5 を24時間続けて動かして作成。README には17項目の操作テストが載っている |
| 3Dのリアルタイムストラテジー | [Starfall](/cases/oneshot-starfall/)（Mike Luan 氏） | 作者の投稿では、費用は632.65ドル、出力は460万トークン。[リポジトリ](https://github.com/e01-ai/starfall)（MIT）は2026年7月28日に公開されている |
| ゲームジャム規模のゲーム | Cursor Vibe Jam 2026 の応募作 | コードの90%以上をAIが書くことが条件で、945作品が応募された |

出典は、Claude of Duty が [README](https://github.com/mshumer/Claude-of-Duty)、The Long Silence が [README](https://github.com/achimala/TheLongSilence) と [作者の投稿](https://x.com/anshuc/status/2081801966158811506)、Starfall が [作者の投稿](https://x.com/mikeluan123/status/2081716631986983093)、Vibe Jam が [公式ページ](https://vibejam.com/) と [主催者の投稿](https://x.com/levelsio/status/2050213288609235424) です。Starfall の数字は作者本人の申告です。

作れる中身には、共通点があります。

- 描画、物理、AI、音声など、公開されている実装例が豊富な部品を、大量に組み合わせる
- 画像や音声のファイルを使わず、コードから生成する（Claude of Duty の README は、すべてのテクスチャ、メッシュ、アニメーション、音を実行時にコードから作ると説明しています）
- 実行して確かめられる部分を、エージェントが自分で直す

Vibe Jam の審査員を務めた Tim Soret 氏は、今年の応募作の質が前年より大きく上がり、本物のゲームに近いものもあると評価しています（[主催者による整理](https://levels.io/vibe-jam-2026-winners-quality)）。

## Claude of Duty を分解する

### プロンプトは何を決めていたか

公開されているプロンプトは3段落です（[prompt.md](https://github.com/mshumer/Claude-of-Duty/blob/main/prompt.md)）。要素に分けると、次の5つです。

| 要素 | 内容 |
|---|---|
| 目標 | 最新の Call of Duty の水準の一人称視点シューティング。テクスチャから物理まですべて、最高品質にする |
| 分業 | サブエージェントを展開し、項目ごとに担当させる |
| 批評役 | 別のサブエージェントが、見た目を厳しく審査する。基準に達しなければ続ける |
| 終了条件 | 本物の Call of Duty と並べて、ブラインドで比べる |
| 技術の指定 | Three.js を使う |

マップの広さ、武器の種類、敵の動き、操作は指定されていません。これらはすべて、モデルが選んだ結果です。
プロンプトにも、画像や音声のファイルを使わないという指示はありません。それでも成果物にファイルがないのは、エージェントが外部素材を持ち込まず、コードで作ったためと考えられます（推測です）。

### 何ができたか

README に載っている数字です（2026年9月時点）。

| 項目 | 内容 |
|---|---|
| 規模 | 約5.5万行、11のサブシステム |
| マップ | 約120×120mの市場の通り。入れる建物がある |
| 敵 | 骨格付きの兵士。経路探索、状況の知覚、遮蔽物の利用、倒れたときの物理演算 |
| 操作 | 移動、射撃、照準、リロード、スプリント、しゃがみ、ジャンプ、体を傾ける |
| 性能 | 最適化後、Retina 解像度で 28〜30 fps（中央値）。最悪フレームは 66〜82 ms |
| 批評家の採点 | 10点満点で 3.59 → 4.14 → 4.05 → 5.05 |
| ブラインド比較 | すべての批評家が、すべての回で、本物の Call of Duty を選んだ |

作者自身が README で、目標は達成できていないと書いています。手が板状のブロックにしか見えないこと、近くで見ると素材が手続き生成のノイズに見えること、敵がマネキンに見えることが挙げられています。

### 作り方の教訓

README の「Process note」には、作り方の教訓が2つあります。

- 並列より、1担当ずつ順番に。6つのエージェントが別々のディレクトリを担当する並列作業を3回繰り返しても、点数は合計 0.46 しか上がらず、画面を台無しにする不具合は 60 → 47 → 66 と、むしろ増えました。トーンマッピング、空、間接光は1つに結びついた仕組みで、担当が分かれると互いの前提を壊したためです。結びついた部分ごとに担当を1つだけ置き、順番に作業させると、点数は 1.00 上がり、不具合は 66 → 26 に減りました
- 検証の指標の選び方。固定カメラの計測では 94 fps と出ていたのに、実際の操作では 12〜17 fps で、最大で 728〜1236 ms の停止が起きていました。シェーダーの遅延コンパイルが原因でした。中央値ではなく、分布と、遅い瞬間の原因を測るスクリプトで見つかりました

また、エージェントの間の取り決めは `ARCHITECTURE.md` に書かれていました。担当ディレクトリ、サブシステム同士のやり取りに使うイベントの名前、守るルール（乱数は決まった関数から取る、毎フレームでメモリを確保しない、など）です。仕様を文書にして渡す方法は [仕様書駆動](/agent-dev/spec-driven/) で扱います。

### 同じプロンプトで、別の人が作ると

James Altucher 氏は同じプロンプトを使い、Operation Blackout というシューティングを作りました。Leon Lin 氏は、20項目に分けた詳細なプロンプトを書き、Cursor 上で Opus 5 を使って Dust Corridor を作りました。どちらもブラウザで動くゲームになりました。Decrypt は、追試の作品には、Shumer 氏の作品で行われた本物との並べた比較はされていないと指摘しています（[Decrypt](https://decrypt.co/374560/dumbest-ai-prompt-claude-beat-careful-game-design)、2026年7月28日）。

同じ記事は、一人称視点シューティングの実装が公開リポジトリに大量にあるため、モデルはそれを組み合わせたのではないかという見方も紹介しています。この見方は、次の節の「独自性」に関わります。

## ポン出しの限界

事例から見える、弱い領域を整理します。

| 弱い領域 | 何が起きるか | 根拠 | 次にやること |
|---|---|---|---|
| コンテンツの厚み | 仕組みは多いが、遊べる場所・敵・目的が少ない | Claude of Duty は1つのマップ。README に目的や進行の記述はない | [ポン出しから製品まで](/agent-dev/from-one-shot-to-product/)の縦切り |
| バランス | 難易度、経済、成長の数値は、遊ばないと分からない | 批評家は見た目を採点したが、遊びの調整は採点していない | [バランス調整](/design/balancing/) |
| 手触り | 見た目は動いていても、操作の気持ちよさは別 | 手の見た目、武器の見え方が最後まで課題だった | [ゲームフィール](/agent-dev/game-feel/) |
| 長く遊べる設計 | 1回目は驚くが、繰り返し遊ぶ理由がない | 進行や報酬の設計はプロンプトになく、README にもない | [コアループ](/design/core-loop/) |
| 性能 | 実機で重い、途中で止まる | 初期は 12〜17 fps、最大 1 秒超の停止 | 性能計測を検証手段に入れる |
| 独自性 | 典型的な出来になりやすい | 公開実装が多い分野の再構成という見方がある（Decrypt） | [独自性を出す](/agent-dev/differentiation/) |

The Long Silence の README は、地面の材質や船体の一部に、画像生成モデルと Blender で作った素材を使っていると説明しています。コードだけで作るポン出しに、素材づくりの工程を足した例と読めます（推測です）。
Steam のコンテンツアンケートは、開発作業を効率化するAIツールの利用は開示の中心ではないとし、プレイヤーが目にするAI生成コンテンツ（事前生成とゲーム中の生成）を開示の対象にしています（[Steamworks](https://partner.steamgames.com/doc/gettingstarted/contentsurvey)、2026年9月時点）。素材を足す判断は、権利と開示の面でも重要です。

## ジャンル別の到達点

確認できた事例のある領域と、事例をこの記事で確認していない領域を分けて書きます。

| ジャンル | 到達点 | 根拠 |
|---|---|---|
| 3Dシューティング | 動いて、見た目も整う。手触りと性能が課題 | Claude of Duty の README |
| 宇宙探索 | 手続き生成の宇宙、目的つきの進行まで動く | The Long Silence の README（7つの装置に同調すると先が開く） |
| リアルタイムストラテジー | 動く。ただし公開後の数日間に、表示の破綻や操作の不具合が数多く直されている | [Starfall](/cases/oneshot-starfall/) |
| ゲームジャム規模 | 応募作の質が上がっている | Vibe Jam 2026 |
| パズル、放置、カード、ローグライク | 事例はこの記事では確認していない。ルール中心でアセットが少ないので、骨格まで作りやすいと推測する | [生成AIと相性の良いジャンル](/genres/ai-friendly/) の整理 |
| ノベル、アドベンチャー | 事例は確認していない。文章の質とキャラクターの一貫性は人が担う部分が大きいと推測する | 同上 |

「推測」と書いた領域は、この記事では事例を確認できていません。実際に試して、結果を [事例集](/cases/) と照らしてください。

## ポン出しで足りる場合、足りない場合

| ポン出しで足りる | ポン出しでは足りない |
|---|---|
| 技術検証、企画の当たりを見る | ストアで売る |
| ゲームジャムの提出物、自分用 | 数時間以上遊んでもらう |
| 友人に見せるデモ | 他の作品と区別される必要がある |
| 素材（コードの土台）として使う | 遊びの調整が価値になる |

迷ったときは、次の5つに答えます。

1. 遊ぶ人は、自分以外に何人いるか（1人なら足りることが多い）
2. 遊ぶ時間は何分か（5分を超えるなら、進行の設計が要る）
3. 「他にもある」と言われて困るか（困るなら独自性の作業が要る）
4. 触って気持ちいいことが価値か（そうなら、手触りの調整が要る）
5. お金を受け取るか（受け取るなら、品質、性能、ストア対応まで要る）

3つ以上が「要る」なら、ポン出しは出発点で、[ポン出しから製品まで](/agent-dev/from-one-shot-to-product/) の手順に進みます。

## ポン出しのプロンプトの書き方

Claude of Duty の事例が示すのは、細かい仕様よりも、「目標」「批評役」「終了条件」を渡したことの効果です。一方、Lin 氏のように項目を細かく書いた例も動くものになっています。どちらが優れているかは、この事例だけでは分かりません。
自分で試すときは、次の要素を入れます。

```text
ブラウザで遊べる、1画面のローグライク・アクションを作ってください。
- 目標: 1回5分で終わる。倒した敵の数と生存時間で評価する
- 技術: Three.js と Vite。画像・音声のファイルは使わず、コードで生成する
- 分業: 描画、敵AI、UI、音は別のサブエージェントに任せる。全体の統合は自分で担当する
- 検証: 変更のたびに npm run build を通し、headless ブラウザで3枚スクリーンショットを撮って確認する
- 批評: 完成前に、別のサブエージェントに画面を見せ、既存の同種ゲームと比べて劣る点を5つ挙げさせる
- 終了条件: 批評役の指摘が、性能・操作・視認性のどれにも残らなくなったら終える。ただし最大2時間
```

期限を入れているのは、際限なく続けさせないためです。長く動かすほど費用がかかります。Homeworld 風の事例の作者は、約630ドルを使ったと投稿しています。
