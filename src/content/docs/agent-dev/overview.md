## 概要

このカテゴリは、Claude Code のようなコーディングエージェントにゲームの実装を任せる前提で、「一発で作らせた後にどう進めるか」を扱います。
この記事では、チャットにコードを貼る方法との違い、開発の流れの全体図、人とエージェントの役割分担、カテゴリ全体の読み方、1日の作業例をまとめます。
読者は、コードは書けるがゲーム制作は初めてのエンジニアを想定しています。
記事中のプロンプト例は、この記事のために書いた例です。

## チャットにコードを貼るのと何が違うか

チャット型のAIは、貼られたコードを読んで、コードの断片を返します。それを動かして、エラーを貼り直すのは人の仕事です。
コーディングエージェントは、この往復の大半を自分で回します。Claude Code の公式ドキュメントは、その仕組みを「コンテキストを集める」「行動する」「結果を検証する」の3段階の繰り返しと説明しています（[How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)、2026年9月時点）。

| 観点 | チャットにコードを貼る | コーディングエージェント |
|---|---|---|
| 見えるもの | 貼った断片だけ | プロジェクト全体（ファイル、Git の状態、指示ファイル） |
| ファイルの変更 | 人がコピーして貼り替える | エージェントが直接読み書きする |
| 実行 | 人が実行して結果を貼る | ビルド、テスト、開発サーバーの起動までエージェントが行う |
| 失敗したとき | 人がエラーを貼って再依頼する | エージェントが出力を読み、直して、もう一度実行する |
| 1回の依頼の規模 | 関数やファイル単位 | 機能単位から、数時間かかる作業まで |
| 作業の分担 | なし | サブエージェントに調査やレビューを任せられる |

ゲーム開発での違いが最も出るのは、「動かして確かめる」部分です。
ブラウザゲームなら、エージェントは開発サーバーを起動し、ヘッドレスブラウザで画面を撮り、その画像を見て直せます。「テストを直して」という依頼ひとつで、エージェントは次のような手順を自分で進めます。

1. テストを実行して、失敗を確認する
2. エラー出力を読む
3. 関係するソースを検索して読む
4. コードを直す
5. もう一度テストを実行する

同じ公式ドキュメントに、この流れが例として載っています。ゲームでは、手順の最後に「画面を撮って確認する」「スクリプトで操作して確認する」が加わります。

### 事例: Claude of Duty のプロンプトは短く、作業は長い

Claude of Duty は、Matt Shumer 氏が 2026年7月に公開した、ブラウザで動く一人称視点シューティングです。
プロンプトは3段落で、ゲームの仕様はほとんど書かれていません。それでも約5.5万行のゲームが出来たのは、複数のエージェントが、実行と検証を繰り返す仕組みの上で作業を続けたからです（[リポジトリ](https://github.com/mshumer/Claude-of-Duty)、[prompt.md](https://github.com/mshumer/Claude-of-Duty/blob/main/prompt.md)）。
リポジトリの README には、「ゲームよりも、検証用の道具（ハーネス）のほうが面白いかもしれない」という趣旨の記述があります。画面を撮るスクリプト、画像の差分を検出するスクリプト、フレーム時間を測るスクリプトなどです。
詳しくは [事例: Claude of Duty](/cases/claude-of-duty/) にまとめています。

このカテゴリの前提は、次の1点です。エージェントの実力は、モデルの賢さだけでなく、「確かめる手段」を渡せているかで決まります。

## エージェントが得意なことと苦手なこと

ゲームには2つの品質があります。「正しく動く」と「遊んで面白い」です。

- 正しく動くかどうかは、テスト、ビルド、スクリーンショット、操作スクリプトで確かめられます。エージェントに任せられます。
- 遊んで面白いか、触って気持ちいいかは、確かめる方法が人の感覚しかありません。人が決めます。

Claude of Duty では、この2つの間を「批評家役のサブエージェント」が埋めようとしました。実際のゲーム画面と見比べて10点満点で採点させたところ、点数は 3.59 から 5.05 まで上がりました。しかし、ブラインド比較では、どの批評家も、どの回でも本物を選びました（README、2026年9月時点）。
エージェントの採点は、直す方向を見つける助けにはなります。「完成」の判定には使えません。

## 開発の流れの全体図

ポン出し（1回のプロンプトで、動くものを一気に作らせること）を起点に、次の7段階で進めます。

```text
ポン出し → 方向決め → 縦切り → 仕様化 → 反復 → 品質 → 出荷（→ 運営）
```

| 段階 | 目的 | 人の仕事 | エージェントの仕事 |
|---|---|---|---|
| ポン出し | 素材として動くものを得る | 何を作らせるか決め、検証手段を渡す | 実装、自己検証 |
| 方向決め | 何を残し、何を捨てるか決める | 遊んで、残す・捨てる・足すを決める | コードの整理、不要部分の削除 |
| 縦切り | 一部分を製品品質まで仕上げる | 品質の基準を示す | 実装、批評役による見直し |
| 仕様化 | 動くものを文書にする | 意図と完了条件を決める | 現状から仕様の下書きを起こす |
| 反復 | 機能追加と調整を回す | 遊んで判断し、次の指示を書く | 機能実装、テスト追加 |
| 品質 | 壊れず、速く、誰でも遊べるようにする | 合格ラインを決める | テスト、性能計測、修正 |
| 出荷 | ストアに出せる状態にする | ストア文面、PV、価格の判断 | ビルド、素材の書き出し、下書き |

「仕様化」が縦切りの後にあるのは、動くものを見るまで、本当に決めたいことが分からないからです。先に長い仕様を書くより、動くものから仕様を起こすほうが手戻りが少なくなります。
各段階の詳細は [ポン出しから製品まで](/agent-dev/from-one-shot-to-product/) にあります。

## 人の役割とエージェントの役割

ゲーム制作には、ディレクター（何を作るか、どの方向に進むかを決める人）とデザイナー（ルールや体験を設計する人）の役割があります。
エージェント前提の開発では、この2つが人の担当になります。実装は、ほとんどをエージェントが担当します。

| 判断・作業 | 担当 | 例 |
|---|---|---|
| 何を作るか、誰に遊ばせるか | 人 | 「1回5分で終わるサバイバー系」 |
| 面白さの判断 | 人 | 遊んで「ここが退屈」と感じる |
| 世界観、題材、独自の視点 | 人 | 自分の仕事の経験を題材にする |
| 手触りの最終調整 | 人 | 「重力を20%下げて」と数値で伝える |
| 何を捨てるか | 人 | 半分の機能を削る |
| 実装 | エージェント | 移動、当たり判定、UI |
| 検証の仕組みづくり | エージェント | スクリーンショット撮影、操作スクリプト |
| 数値の外出しと調整用UI | エージェント | デバッグ用スライダー |
| 調査と比較 | エージェント | 「同種のゲームの操作方法を5本調べて」 |
| データの量産 | エージェント | 敵の一覧、アイテム表 |
| 量産物の取捨選択 | 人 | 10案から3案を選ぶ |

境目は、「正解を確かめる手段があるか」です。手段があれば、エージェントに任せます。なければ、人が決めます。
独自性がどこから生まれるかは [ポン出しの先で独自性を出す](/agent-dev/differentiation/) で詳しく扱います。

## 始める前に用意するもの

- Git のリポジトリ。エージェントは一度に多くのファイルを変えるので、作業前にコミットしておきます（[AI駆動の開発ワークフロー](/dev-env/ai-workflow/)）
- 指示ファイル（`CLAUDE.md` や `AGENTS.md`）。起動コマンド、テストコマンド、守るルールを書きます（[AIコーディングツール](/dev-env/ai-coding-tools/)）
- 確かめる手段。最低限、ビルドが通ること、画面のスクリーンショットを撮れることを揃えます
- 権限の設定。長い作業を任せるなら、許可するコマンドを決めておきます

ブラウザゲームの最小構成の指示ファイル例です。

```markdown
# プロジェクト
- ブラウザ向け3Dゲーム。Three.js と Vite、素材ファイルは使わない
- 仕様は SPEC.md、作業の一覧は TODO.md

# コマンド
- 起動: npm run dev
- ビルド: npm run build（変更のたびに通ること）
- 画面確認: node tools/shot.mjs（スクリーンショットを shots/ に保存）

# ルール
- 1回の依頼で変更するのは1機能だけ
- ゲームの数値は src/config.js に置く
- 変更したら、ビルドとスクリーンショットで確かめてから報告する
```

## 1日の作業の流れの例

個人開発で、休日の1日にポン出しから縦切りの入口まで進める例です。時間は目安です。

| 時間 | やること | 担当 |
|---|---|---|
| 9:00 | 1ページ企画書を書く。エージェントに質問させて穴を埋める | 人＋エージェント |
| 10:00 | ポン出し。確かめる手段（ビルド、スクリーンショット）も一緒に作らせる | エージェント |
| 11:00 | 遊ぶ。30分遊んで、残す・捨てる・足すを3行で書く | 人 |
| 12:00 | 昼休み。エージェントに「捨てる」部分の削除を任せる | エージェント |
| 13:00 | 削った状態で遊び直し、コアループを1つ決める | 人 |
| 14:00 | コアループの周りを作り込む。1機能1コミットで進める | エージェント |
| 16:00 | 友人に触ってもらう。黙って見る | 人 |
| 17:00 | 気づきを TODO.md にまとめ、エージェントに優先順位案を出させる | 人＋エージェント |
| 17:30 | 翌日に回す作業を「完了の条件つき」で書いておく | 人 |

10:00 のポン出しには、たとえば次のように頼みます。

```text
ブラウザで動く、1画面のアクションゲームを作ってください。
- Three.js と Vite を使い、画像・音声ファイルは使わない（図形と WebAudio で作る）
- 操作: WASD で移動、マウスで狙って撃つ
- 敵が押し寄せ、60秒生き延びたらクリア
- npm run build が通ること
- headless ブラウザでスクリーンショットを3枚撮り、目で見て、明らかなずれを直すこと
- 作業の最後に、動作確認の結果と、未実装の点を報告すること
```

11:00 の「遊ぶ」は、エージェントに代わってもらえません。ここで感じた退屈さや違和感が、以降の作業の起点になります。

昼休みの間に作業を進めさせる場合は、終わりの条件を先に書いておきます。Claude Code の `/goal` は、条件が満たされるまで、ターンごとに別のモデルが達成を判定しながら作業を続けさせる機能です（[Keep Claude working toward a goal](https://code.claude.com/docs/en/goal)、2026年9月時点）。
