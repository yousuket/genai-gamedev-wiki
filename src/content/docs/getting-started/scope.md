## 概要

スコープとは「そのゲームで何を作り、何を作らないか」という範囲のことです。
個人開発の未完成の原因で多いのは、技術力不足よりもスコープの広げすぎです。
この記事では、スコープを決める手順、生成AIで作業量が減る部分と減らない部分、そして最初の1本の規模の目安を説明します。

## なぜスコープが最重要なのか

ゲームの作業量は、要素の数に対して足し算ではなく掛け算で増えがちです。

- 敵を1種類増やすと、グラフィック・アニメーション・効果音・バランス調整・テストがそれぞれ増える
- ステージを1つ増やすと、配置・難易度調整・通しプレイの確認が増える
- 機能を1つ増やすと、既存の機能との組み合わせで不具合が生まれる

個人で大きなヒットを出した作品も、多くは「狭く深く」作られています。

| 作品 | 開発体制と期間 | 出典 |
|---|---|---|
| 8番出口 | 個人開発。構想6か月、実作業3か月。短期間で作るために遊びを絞り込んだと開発者が振り返っている | [GameBusiness.jp](https://www.gamebusiness.jp/article/2024/12/09/23720.html)、[4Gamer.net](https://www.4gamer.net/games/751/G075133/20241203035/) |
| Stardew Valley | Eric Barone氏が約4年かけて1人で開発。音楽・アート・プログラム・デザインを独学した | [公式プレスキット](https://www.stardewvalley.net/press/) |

8番出口のように遊びを1つに絞れば数か月で作れる一方、Stardew Valleyのように要素の多いゲームは1人で数年かかります。
最初の1本では前者の考え方を取るのが現実的です。

## スコープを決める手順

### 1. コアを1文で書く

「プレイヤーが何を繰り返し、何を目指すゲームか」を1文で書きます。
例: 「迫ってくる敵の群れを自動攻撃で倒し、レベルアップ時の強化の選択で生き延びる」

この1文に関係しない要素は、最初の候補から外します。
コアループの考え方は[コアループ](/design/core-loop/)で詳しく扱います。

### 2. 制約を先に決める

| 制約 | 決め方の例 |
|---|---|
| 期間 | 「3か月で発売」のように締め切りを先に置く |
| 作業時間 | 平日1時間・週末5時間なら、週10時間 × 12週 = 約120時間 |
| プレイ時間 | 最初の1本なら30分〜2時間程度のボリュームを想定する |
| プラットフォーム | まずはPC（Steam / itch.io）かブラウザの1つに絞る |
| 人数 | 1人。外注する場合は、その範囲を最初に決める |

締め切りを先に決め、そこに入る範囲だけを作る考え方を「タイムボックス」と呼びます。

### 3. 要素を3つに分ける

| 分類 | 意味 | 例 |
|---|---|---|
| 必須 | これがないとゲームが成り立たない | コアループ、1通りのクリア条件、タイトル画面 |
| あると良い | 余裕があれば入れる | 追加のキャラクター、実績、複数の難易度 |
| 作らない | 今回は入れないと明言する | オンライン対戦、長編ストーリー、多言語ボイス |

「作らない」リストを書き出しておくと、制作中に思いついた機能をそこに移すだけで判断が済みます。

### 4. バーティカルスライスで見積もりを確かめる

1ステージ分を製品に近い品質で作り（バーティカルスライス）、かかった時間を計ります。
「1ステージに20時間かかった。残り時間は100時間」なら、作れるのは多くて5ステージです。
現実には調整やバグ修正にも時間がかかるので、見積もりの1.5〜2倍を見込んでおくと余裕が生まれます。

## AIで作業量が減る部分・減らない部分

生成AIを使うと、作業の一部は大きく短縮できます。
ただし、ゲーム制作全体がそのまま速くなるわけではありません。

| 作業 | AIで減るか | 理由 |
|---|---|---|
| 定型的なコード（UI、セーブ、入力処理など） | 減りやすい | 既存の実装例が多く、AIが下書きしやすい |
| 仮素材・アイデアの試作 | 減りやすい | 画像・効果音・テキストの叩き台をすぐ作れる |
| 大量のテキスト（アイテム説明、会話の下書き） | 減りやすい | ただし内容の一貫性の確認は必要 |
| 画風のそろったアセット一式 | あまり減らない | 1枚ずつは速く作れても、統一感をそろえる手直しに時間がかかる |
| ゲームの手触り（操作感、演出のタイミング） | 減らない | 実際に遊んで細かく調整するしかない |
| バランス調整 | 減らない | 判断の根拠はプレイテストの結果 |
| 不具合修正と通しテスト | 一部のみ減る | AIの書いたコードも含めて、動作確認は人間が行う |
| 宣伝・コミュニティ対応 | 一部のみ減る | 文章の下書きは速くなるが、継続的な発信は人間の作業 |
| 権利・規約の確認 | 減らない | ツールごとの利用条件を読み、記録する必要がある（[AIツールの商用利用条件](/legal/tool-terms/)） |

GDCの2026年の業界調査でも、生成AIを使う人の用途は調査・ブレインストーミング（81%）、メールなどの日常業務とコーディング支援（各47%）、プロトタイピング（35%）が上位でした（[GDC 2026 State of the Game Industry](https://gdconf.com/article/gdc-2026-state-of-the-game-industry-reveals-impact-of-layoffs-generative-ai-and-more/)）。
プロの現場でも、AIは「考える・下書きする・試す」作業から使われていることが分かります。

:::caution
AIで「作る」速度が上がると、要素を足したくなる誘惑も強くなります。
要素を1つ足すと、テスト・調整・不具合修正という「減らない作業」も一緒に増えます。
AIで浮いた時間は、要素を増やすよりも、プレイテストと磨き込みに回すのがおすすめです。
:::

## 最初の1本の目安

初めてゲームを作る人の場合、次のどれかから始めると完成まで届きやすくなります。

| 選択肢 | 規模 | 向いている人 |
|---|---|---|
| 古典ゲームの再現 | 数日〜数週間 | エンジンの使い方から覚えたい人 |
| ゲームジャムへの参加 | 数日〜1週間 | 締め切りがあると進む人 |
| 小さな有料・無料作品 | 1〜3か月 | 1本目からストアに出してみたい人 |

- **古典ゲームの再現**: [The 20 Games Challenge](https://20_games_challenge.gitlab.io/challenge/) は、PongやFlappy Birdから始めて、Breakout、Space Invaders、Pac-Man、Super Mario Bros.のように段階的に難しくしていく練習メニューを公開しています。
- **ゲームジャム**: 決められた期間とお題でゲームを作るイベントです。日本語圏では unityroom の [Unity 1週間ゲームジャム](https://unityroom.com/unity1weeks) が定期的に開催されています。海外のジャムは [itch.io のジャム一覧](https://itch.io/jams) で探せます。
- **小さな作品**: 「コアループ1つ・プレイ時間30分〜2時間・ステージ数は少なめ」を目安に、ストアページ公開までを一通り経験します。

1本目の目標は「売れること」より「企画から公開までを一度通すこと」に置くと、2本目以降の見積もりが格段に正確になります。

## AIの活用ポイント

- **「作らない」リストの作成に使う**: 企画をAIに渡し、「1人・3か月で作るなら削るべき要素」を挙げさせます。自分では削りにくい要素を客観的に見直すきっかけになります。
- **作業の分解と見積もりの叩き台**: 機能ごとにタスクを分解させ、抜けている作業（設定画面、セーブ、ローカライズなど）を洗い出します。時間の見積もりそのものはAIに任せず、バーティカルスライスの実測値で判断します。
- **AIの出力をそのまま採用しない**: AIは要素を追加する提案を出しがちです。提案は「あると良い」か「作らない」リストに振り分けてから検討します。
- **AI利用の記録を残す**: どの素材・どのコードにどのツールを使ったかを記録しておくと、後で[プラットフォームのAIポリシー](/legal/platform-policies/)に沿った開示をするときに困りません。

AIとの企画の進め方は[AIを企画の壁打ちに使う方法](/design/ai-brainstorming/)、作業の流れ全体は[AI駆動の開発ワークフロー](/dev-env/ai-workflow/)で扱います。
