## 概要

Claude of Duty は、Matt Shumer 氏が2026年7月25日に公開したブラウザ向けの一人称視点シューティング（FPS）です。「最新のCall of Dutyと同水準のFPSを作れ」という短いプロンプトを Claude Code に渡し、Claude Opus 5 がサブエージェントを大量に動かして作りました。約5.5万行のコードで、画像・3Dモデル・音声ファイルは1つもなく、すべてコードから生成されます。
公開直後はX上で「偽物では」と疑われましたが、作者がプロンプトとコードをMITライセンスで公開しました。READMEが自己評価を「Call of Dutyには届いていない」と書いていることも、参考にされる理由です。
この記事では、何ができたか、プロンプトの構造、エージェントの運用、限界、同じ手法を自分で試す手順を説明します。

| 項目 | 内容 |
|---|---|
| 作者 | Matt Shumer 氏（X: @mattshumer_） |
| 公開日 | 2026年7月25日（UTC）。デモ動画のX投稿、リポジトリ公開、プロンプト公開の順で同日 |
| モデル | Claude Opus 5（作者のX投稿で「Claude Opus 5 one-shotted this game」と述べている） |
| ツール／エージェント | Claude Code、サブエージェントの大量並列、`/loop`、`ultracode`（作者の解説記事による） |
| ジャンル・規模 | ブラウザFPS。約5.5万行、11サブシステム、Three.js r180（WebGL2）、実行時の依存は `three` のみ |
| 公開場所 | [GitHub: mshumer/Claude-of-Duty](https://github.com/mshumer/Claude-of-Duty)（MIT）。公式のホスティング版はなく、`npm install` と `npm run dev` で自分のPCで動かす |

## 何が作られたか

舞台は約120m四方の市場通りです。建物は壁に厚みがあり、入れる室内があり、数百個の小物（プロップ）が置かれています。READMEによると、内容は次の11サブシステムです（2026年9月時点）。

| サブシステム | できること |
|---|---|
| render | HDRパイプライン、カスケードシャドウマップ、GTAO（画面空間の環境遮蔽）、TAA（時間方向のアンチエイリアス）、ブルーム、モーションブラー、AgXトーンマップ |
| materials | 19種類の表面（コンクリート、レンガ、錆びた金属、木、布、ガラスなど）をGPUで生成。継ぎ目なくタイルする |
| sky | 大気散乱、時刻の変化、体積フォグと光の筋 |
| world | 市場通り、モジュール式の建物キット、入れる室内 |
| physics | 物理ライブラリなしの自前実装。BVH（空間分割構造）、カプセル型キャラクターコントローラー、ラグドール、多層の弾丸貫通 |
| player | 移動の状態機械（スライド、乗り越え、リーン） |
| weapons | コードで作る銃、ADS（照準）、スプリング反動、リロード、弾道（飛翔時間と落下） |
| fx | GPUパーティクル、弾痕、曳光弾、爆発 |
| ai | スキニングされた敵兵、ナビメッシュ、知覚、遮蔽物の利用、死亡時のラグドール |
| ui | HUD（照準、ヒットマーカー、ミニマップ、コンパス、キルフィード） |
| audio | Web Audioでの音声合成。銃声、リバーブ、立体音響、遮蔽 |

操作はWASDで移動、マウスで視点、左クリックで射撃、右クリックでADS、`R` でリロード、`Shift` でダッシュ、`Ctrl` でしゃがみ、`Space` でジャンプ、`Q`/`E` でリーンです。
GitHub上の履歴は2コミットで、最初のコミットが185ファイル・71,270行の追加です（ロックファイルやツール類を含むため、作者が言う約5.5万行とは数え方が違います）。テクスチャもメッシュも音も実行時にコードで作るので、リポジトリにアセットはありません。物理エンジンまで自前実装になっているのは、ARCHITECTURE.md が新しいnpm依存の追加を禁じているためと考えられます。

## プロンプトの中身

プロンプトは [prompt.md](https://github.com/mshumer/Claude-of-Duty/blob/main/prompt.md) に全文が公開されています。英語で約150語、3つの段落だけです。全文の転載は避け、書かれている内容を役割で4つに分けて整理します（3つ目の段落に、終了条件と技術指定の両方が入っています）。

| 役割 | 内容 |
|---|---|
| 1. 目標と品質の基準 | 「最新のCall of Dutyと同水準のFPS」「完璧に」「テクスチャから物理まですべてAAA品質」 |
| 2. 分担と批評役 | サブエージェントに分担させる。各項目を `/loop` で回し、別のサブエージェントが見た目を確認する。この批評役は「とても厳しく」、AAAに見えなければ続けさせる |
| 3. 終了条件 | 実際のCall of Dutyと並べて、どちらが良いかを目隠しで比較させる。批評役全員が感嘆するまで止めない |
| 4. 技術と実行方式 | Three.jsで作る。`/loop` で回し続け、「fan out sub-agents and ultracode」で締める |

書かれていないものが重要です。設計書、機能一覧、アセット一覧、アーキテクチャ、ゲームルールは1つも指定していません。指定しているのは「目標」「品質の基準（実物との比較）」「分担して批評役を置く」ことだけです。Shumer氏は解説記事で、実装方法まで指示すると、モデルの判断を人間の判断で置き換えてしまうと述べています（[Gauntlet Loop の解説](https://somethingbig.ai/gauntlet-loop)）。

Shumer氏はこの型を後日「Gauntlet Loop」と名付けました（[X投稿](https://x.com/mattshumer_/status/2081830214384886228)）。解説記事では、次の考え方が中心です。

- 実物のスクリーンショットなど、確認できる基準を置く。「すごく良くして」は基準にならない
- 目標を、個別に改善・判定できる最小の単位に分けるのは、司令役のエージェントに任せる
- 作る役と評価する役を分け、評価役には作る役の説明を渡さず、実際の出力だけを見せる
- 「3ラウンドで終了」のような区切りを置かない

## 進め方（エージェントの運用）

### 全体像

Shumer氏は解説記事で、Claude Codeにプロンプトを1本渡し、その後は触らず、Claudeが何時間も動いて大量のサブエージェントを生み出した、と述べています。実行時間の正確な値は公開されていません。大規模な実行では `/effort` で `ultracode` を選ぶよう勧めています。費用は上がりますが、良い結果が出やすいとのことです。

### 契約ファイル ARCHITECTURE.md

並列に動くエージェント同士がぶつからないよう、リポジトリには [ARCHITECTURE.md](https://github.com/mshumer/Claude-of-Duty/blob/main/ARCHITECTURE.md) があります。冒頭に「全エージェントはコードを書く前に読むこと。これが唯一の連携手段」と書かれています。内容は次のとおりです。

- 各サブシステムは自分のディレクトリだけを所有し、他のディレクトリは編集しない
- 他のサブシステムのモジュールをimportせず、実行時に `ctx.get('fx')` のように取得する
- 新しいnpm依存を追加しない。外部の画像・モデル・音声も使わない
- 乱数は `Math.random()` を使わず、シード付きの `ctx.rng` を使う（画面キャプチャを再現可能にするため）
- フレームごとにメモリを確保しない。作ったものは破棄する
- 変更後は必ずビルドが通り、スクリーンショットが撮れること
- 共通部分（`src/core/`、`tools/` など）は司令役が所有する
- サブシステム間のイベント名と、表面の種類（コンクリート、金属、木など12種）の共通語彙を表にして固定する

品質の下限も書かれています。のっぺりした面を作らない、一様な照明にしない、まっすぐで綺麗すぎるものを作らない、すべての行動に重みを付ける、の4点です。
誰がこのファイルを書いたかは、公開資料では確認できません。Issue #28 で、どのファイルが事前に用意されたものか質問が出ていますが、2026年9月29日時点で回答はありません。Shumer氏は「プロンプトは1本」と述べており、解説記事（Matt Paige 氏のSubstack）は「Claudeが最初にアーキテクチャの契約を自分で書いた」と説明しています。後者は二次情報です。

### 批評役と比較の仕組み

READMEによれば、11人の独立した批評役（エージェント）がゲームの画面を実物のCall of Dutyと比較して10点満点で採点しました。スコアの推移は3.59、4.14、4.05、5.05です。目隠しのA/B比較では、すべてのラウンドで全批評役が本物のCall of Dutyの画面を選びました。

### 測定用の道具

批評役の言葉を鵜呑みにしないため、`tools/` に測定用のスクリプトがあります。

| ツール | 役割 |
|---|---|
| `baseline.mjs` | 1シーンごとに新しいページで撮影し、毎回同じ画像になる（再現可能な撮影） |
| `imagediff.mjs` | ピクセル単位で比較し、1ピクセルでも違えば失敗として終了する |
| `profile.mjs` | 実プレイのフレーム時間の分布（p50/p95/p99）と、ヒッチ（引っかかり）の原因を出す |
| `playtest.mjs` | 移動と射撃を自動で行う動作確認 |

READMEは、この道具が「ゲーム本体より面白い部分」だと書いています。静止カメラの計測では94fpsと出ていたのに、実プレイでは12〜17fpsで、728〜1236msの停止が起きていました。34個以上のシェーダーが描画中に遅れてコンパイルされていたためです。シェーダーを起動時に先にコンパイルする処理（`prewarm.js`）で停止が消えました。

### スクリプト化された最適化ワークフロー

`tools/workflows/perf.js` には、性能改善を4フェーズ（時計依存の除去、検証ゲートの確立、最適化、測定）で進めるワークフローのスクリプトが入っています。各フェーズで担当ディレクトリごとにエージェントを並列に起動し、「見た目を1ピクセルも変えない」ことを画像比較で確認する設計です。ファイル内には「ユーザーの要求は文字どおり『1:1、100%同一』」という記述があります。これは、最適化の段階で人間から追加の要求があったことをうかがわせますが（推測）、公開資料からは同じセッションの中だったかは分かりません。

### 並列より逐次

READMEの「プロセスのメモ」に、興味深い記録があります。6エージェントが各ディレクトリを担当する並列の作業を3ラウンド行っても、スコアは+0.46にとどまり、画面を壊す欠陥はむしろ60から47、66へと増えました。トーンマップ、空、間接光は結合した1つの仕組みなので、分担したエージェントが互いの前提を壊したためです。結合している関心事ごとに担当を1人にして、順番に直す1パスでは、スコアが+1.00上がり、欠陥は66から26に減りました。
もう1つの記録は、エージェントが指示に逆らって正解にたどり着いた例です。批評役は3ラウンド続けて武器が「テクスチャなし」に見えると報告しました。実際には拡散反射が暗すぎ、鏡面反射が強すぎていました。それまでのラウンドは「明るすぎる」という指摘に対してアルベド（反射率）を下げ、拡散をさらに潰していました。正解は逆に上げることでした。

## 結果と限界

### 作者自身の評価

READMEの「Honest assessment」は、Call of Dutyには届いていないと明言しています（引用: "It does not."）。11のうち2枚のショットが「CLOSE（近い）」に達し、残りは「AMATEUR（素人）」のままです。弱点はREADMEに具体的に書かれています。

- 手: 指が板のようで、武器を握っているように見えない
- 素材: 近づくと、写真ではなくノイズに見える。コードでテクスチャを作る限界
- キャラクター: 遠くの敵がマネキンに見える
- 間接光: 近似で、本物のGIではない
- フレームレート: Retinaで28〜30fps

### 性能

Apple siliconのノートPC（1512×982、DPR 2、ultraプリセット）での実測は次のとおりです。

| 指標 | 最適化前 | 最適化後 |
|---|---|---|
| fps（p50） | 12〜17 | 28〜30 |
| fps（p99） | 4〜9 | 14〜17 |
| 最悪のフレーム | 728〜1236 ms | 66〜82 ms |
| プレイ中のシェーダーコンパイル | 34〜35回 | 0回 |
| 起動 | 約9〜12秒 | 3.7〜4.6秒 |

最適化の前段階で、美術の作り込みにより三角形数が590万から1130万に増えたことも書かれています。ワークフローの目標は「p99で60fps以上、どのフレームも30ms以下」でしたが、最終結果はそれに届いていません。他のPCでも重く、Issue #13 には、Core Ultra 7 搭載のノートPCで動作が固まるという報告があり、専用GPUでブラウザを動かすよう返信が付いています。

### 第三者の指摘

- 監査PR: 公開2日目に、エージェントによる監査で見つけたという欠陥の修正PRが9本（#4〜#12）出ています。ラグドールの手足が体に固定されていない、スポーン地点が木の幹の中、コンパスが向きによって空白になる、敵の回り込みが約20秒後に永久に無効になる、などです（#4・#5の投稿者は daxdax89）。2026年9月29日時点でいずれもマージされていません
- コスト: Issue #30 で使用トークン量が質問されていますが、回答はありません。時間、トークン数、費用の公式な数字は公開されていません
- 再現: 別の利用者が同じ型のプロンプトを一晩走らせ、セッション上限に3回当たったと書いています（Matt Paige 氏のSubstack。有料記事のため冒頭のみ確認）。これは別の実行で、リポジトリの結果ではありません

### ゲームとしての中身

READMEの機能一覧は、技術要素（描画、物理、AI、音）が中心です。ミッション、進行、武器の解放、モード選択は書かれていません。動くのは市場通り1面で、敵と撃ち合えます。「遊び」の設計はプロンプトに含まれておらず、画質の追求が目標だったため、ゲームとしての面白さやバランスは評価の対象になっていません。

### 二次情報との食い違い

| 二次情報の記述 | 一次情報（README、リポジトリ） |

| ブラウザだけで動き、インストール不要（baeseokjae） | 公式は `npm install` と `npm run dev` が必要。ホスティング版は第三者が立てたもの（Issue #13、PR #18 など） |
| コンピュートシェーダーのパーティクル（baeseokjae） | READMEは「GPU particles」とだけ書いている。WebGL2にはコンピュートシェーダーがない |

## 学べること

### 自分で試すなら

1. エージェント環境を使う。Shumer氏は、チャットへの貼り付けではなく、ファイルを開き、コードを動かし、画面を撮り、サブエージェントを起動できる環境（Claude CodeやCodex）が必要と書いています。詳しくは [AIコーディングツール](/dev-env/ai-coding-tools/) と [並列エージェント](/agent-dev/parallel-agents/) を参照してください
2. 基準を先に決める。実在のゲームのスクリーンショットなど、批評役が見比べられるものを用意します。基準が決まらないときは、基準探しも作業に含めるのが作者の推奨です
3. 短いプロンプトで始める。目標、基準、分担、批評役、終わらせない指示の5つだけを書き、設計は任せます。型は [プロンプトパターン](/agent-dev/prompt-patterns/) にも整理しています
4. 先に計測の道具を用意させる。スクリーンショット撮影、画像差分、フレーム時間の分布は、批評役の「良く見える」を数字で裏付ける手段です（[検証ループ](/agent-dev/verification-loop/)）
5. 契約ファイルを作らせる。ディレクトリの所有者、禁止事項、イベント名を固定してから並列に動かします
6. 進捗を見られるようにする。Shumer氏は、エージェントに進捗を出すHTMLページを更新させ、スマートフォンから見る方法を勧めています
7. 費用の目安を持つ。Opus 5の料金は入力100万トークンあたり5ドル、出力25ドルです（[Anthropic](https://www.anthropic.com/news/claude-opus-5)、2026年9月時点）。Claude of Duty の費用は公開されていませんが、同じ型のプロンプトで宇宙RTSを作った事例では約633ドルと公表されています（同カテゴリのStarfallの記事を参照）。費用の管理は [コスト管理](/agent-dev/cost-management/) にまとめています

### ポン出しの先で独自性を出すなら

Claude of Duty は「画質を実物に近づける」ことに特化した出力で、遊びの設計はありません。同じ手法で作った物は見た目が似通うので、次の順で独自性を足します。詳しい考え方は [ポン出しの先へ](/agent-dev/from-one-shot-to-product/) と [独自性の出し方](/agent-dev/differentiation/) にあります。

- コアループを決める。何を繰り返し、何が面白いのかを人間が決めます（[コアループ](/design/core-loop/)）。撃ち合い以外の目的、ミッション、進行を足す余地が大きいです
- 基準を別のものに変える。「Call of Duty」を「自分が作りたい映画の1シーン」「別ジャンルの実物」に置き換えるだけで、出力の方向が変わります。Shumer氏の型を宇宙RTSやFPS以外に当てはめた例が出ています
- 手触りを手で詰める。反動、被弾の反応、カメラの揺れなどは、批評役が画像で評価しにくい部分です（[ゲームフィール](/agent-dev/game-feel/)）
- 弱点を狙って直す。手、キャラクター、素材はREADMEが弱点と認めています。ここに別の手段（Blenderなど）を加えた例が、同カテゴリの The Long Silence です
- 性能の目標を決めて追う。p99で60fpsは未達でした。プロファイラの指標を目標にして修正を回します
- 絵作りをコードだけにこだわらない。アセットを外部から入れるなら、ライセンスの確認が必要です（[著作権](/legal/copyright/)）
