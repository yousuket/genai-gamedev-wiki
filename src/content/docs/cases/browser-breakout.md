## 概要

Les Orchard 氏が、自分の Claude Code の使い方を同僚に見せるために作った、Phaser 3 製のブロック崩しです。ゲーム自体に新しさはなく、作者も「ゲームは特に斬新ではない」と書いています。
価値は記録にあります。リポジトリには、指示ファイル（CLAUDE.md）、セッションごとのスラッシュコマンド、各セッションの仕様書・計画書・TODO・振り返りノート、Claude との会話ログの全文がコミットされています。
「一発生成のあとに、機能を1つ足すとき、何を頼み、どこでつまずくか」を、そのまま読める数少ない事例です。

| モデル | Claude Opus 4、上限に達してからは Sonnet 4（マルチボールのセッションの会話ログに切り替えの表示がある。2025年7月時点） |
| ツール／エージェント | Claude Code（スラッシュコマンド、CLAUDE.md）。Phaser 3、TypeScript、Vite |
| ジャンル・規模 | ブロック崩し。約4時間のコミット履歴、47コミット。パワーアップ（マルチボール）付き |

## 何が作られたか

- 上部に7段のレンガ、下部にマウスで動くパドル、20×20のボール、残機3、スコア、ゲームオーバーとクリア、ポーズ
- 内部解像度は768×1024で、ブラウザの大きさに合わせて拡大表示
- 速度、大きさ、間隔などをまとめた設定ファイル（GameConfig.ts）
- 追加機能として、レンガを壊すと10%の確率で落ちてくるパワーアップと、拾うとボールが倍になるマルチボール（ボール同士も跳ね返る）

作者のブログでは、パワーアップの追加は「反復的な開発の実演」のためで、土曜の午後にテレビを見ながら数時間で作ったと書かれています。

## プロンプトの中身

プロンプトはリポジトリに公開されています。構造は3段階です。

### 1. 最初の仕様は、遊びのルールを箇条書きで書いた短い文章

最初の仕様書の冒頭は、レンガ、パドル、ボール、残機、勝敗、得点を平易な文で並べた箇条書きです。最後に「Phaser と Vite を使い、TypeScript で書く」と技術を指定しています。専門用語はほとんどなく、ゲームを知っている人が口で説明する程度の粒度です。

### 2. 仕様の詰めは、AIに「1問ずつ質問させる」

ブレスト用のスラッシュコマンドには、次のように書かれています（リポジトリの `.claude/commands/session-02-brainstorm.md`）。

> Ask me one question at a time so we can develop a thorough, step-by-step spec for this idea.

Claude が1問ずつ質問し、作者が答えて、仕様書に反映していきます。「画面サイズは」「レンガの寸法と間隔は」「ボールの速度と、当たった位置による反射角は」といった問いに、作者は数値で答えています。たとえば、内部解像度768×1024、ボール20×20で毎秒250ピクセル、レンガ100×25で間隔10ピクセル、「すべての値は設定ファイルにまとめて、あとでゲームの手触りを調整できるように」と指定しています。

### 3. 計画と実行もコマンド化されている

- 計画のコマンドは、仕様書をもとに、小さな反復の塊に分け、それをさらに小さな手順に分けて、コード生成用のプロンプトの列として `plan.md` に書かせます。「孤立して使われないコードを残さない」という指示があります
- 実行のコマンドは、計画書を読んで準備が整っているか判断し、「進めながら `todo.md` を必ず更新」し、各段階ごとにコミットさせます
- 振り返りのコマンドは、実際に起きたことの要約、計画からのずれ、学び、改善案、対話の回数などを `notes.md` に書かせます

CLAUDE.md にも、このセッションの決まり（`docs/dev-sessions/日付-スラッグ/` に spec、plan、todo、notes を置く）が書かれています。詳しい指示ファイルの考え方は [プロジェクト指示ファイル](/agent-dev/project-instructions/) と [仕様駆動の進め方](/agent-dev/spec-driven/) を参照してください。

## 進め方（エージェントの運用）

コミット履歴（UTC）とセッションのログから読み取れる流れです。

| 時間 | 内容 |
|---|---|
| 17:58 | 初回コミット。続けて「ゲーム機能の思いつき（braindump）」「ブレスト」 |
| 18:36〜19:10 | 計画に沿って、土台→構造→ゲームオブジェクト→ゲームの仕組み→仕上げの順にコミット。約35分で遊べる形に |
| 19:13〜19:34 | 当たり判定のバグ修正が続く。上壁での跳ね返り、下端の通過、止まるボールなど。最後は「動いていた状態に戻す」コミットで整理 |
| 19:55 | GitHub Pages への公開設定 |
| 20:47〜21:05 | マルチボールの仕様、ブレスト、計画 |
| 21:06〜21:13 | 実装（設定、複数ボール、パワーアップ、発生、マルチボール、デバッグ用キー） |
| 21:15〜21:57 | 約40分間のバグ修正。ボールの出現位置、止まるボール、型エラー |

同じ流れで、機能ごとに新しいセッション（起動時にセッション用のフォルダを作る）を切っています。

### つまずきが会話ログに残っている

マルチボールでは、実装が終わったあとに、次のようなやり取りが続いています（会話ログより）。

1. パワーアップが動かない。直すと、今度は画像が未設定の「斜線の入った箱」が落ちてくる
2. 新しいボールが、元のボールの近くではなく画面中央に出る。Claude が仕込んだデバッグログの座標は「元のボールの近く」で正しい値を示していたが、作者は「ログがどうあれ、中央から出ているのは確かだ」と返した。Claude は「ログよりあなたを信じる」と答え、コードを読み直した
3. 作者の「生成のとき位置は正しく設定されているか」という質問がきっかけで、原因が見つかる。ボールの生成処理が中で `resetBall()` を呼び、渡された座標を無視して常に中央に置いていた
4. 次に、レンガの近くで生成されたボールが動かなくなる問題が出る。生成位置の衝突回避を足しても直らず、作者が「レンガの領域を避けなくてよい。元のボールがそこにいるなら、そこに出したい」と仕様の意図を言い直す
5. 最後に、作者が「`npm run build` を実行して、問題があれば直して」と頼み、TypeScript のビルドエラーが見つかって直る

## 結果と限界

- 結果: 仕様どおりの遊べるブロック崩しと、マルチボールが公開されています。作者は、思いつきを素早く入れて確かめる往復が「中毒性がある」と書いています
- 時間: 作者は「数時間」と書いています。コミット履歴では初回から最後まで約4時間です
- マルチボールの実装は8分ほどで済みましたが、動作の調整に約40分かかっています。生成は速くても、「思ったとおりに動くか」を確認して直す時間が支配的でした
- エージェントのデバッグログは、人が画面で見た結果と食い違いました。ログの値は正しく見えても、生成処理が座標を上書きしていた原因は、人の観察と質問から見つかっています
- 作者が取り組んでいるのは実演用の小さな範囲で、遊び手による評価や数値の記録はありません
- 使われたモデルは2025年7月時点のものです。会話ログでは、上限に達して途中でモデルが切り替わっています

## 学べること

### 自分で試すなら

- 仕様の入力は、遊びのルールの箇条書き数行から始められます。専門用語も、詳しい設計も要りません
- 「1問ずつ質問して」と頼むと、自分でも決めていなかった数値や場合分け（残機の扱いなど）が引き出されます
- リポジトリのスラッシュコマンドは、そのままコピーして自分のプロジェクトで使えます。ブレスト、計画、実行、振り返りの4つを分けるだけで、AIの作業に節目ができます
- セッションごとに、仕様・計画・TODO・ノートをフォルダで残しておくと、後から読み返せます。[コンテキスト管理](/agent-dev/context-management/) の実例としても読めます

### ポン出しの先で独自性を出すなら

- この事例に独自性のあるゲームデザインはありません。示しているのは、独自の機能を足すときの手順です。ルール（パワーアップ、ボールの倍増）を文章で決め、設定ファイルの数値として外に出し、動かして直します
- 作者は、ボール同士の衝突を「パドルやレンガと同じ反射のふるまいにする」など、判断の基準を1つ決めて、迷いを減らしています
- 仕様に書いていない場面（ボールが複数あるときの残機）は、会話の中で決め直し、その結論を仕様書に反映しています
- 進めるほど、独自のルールは仕様書に溜まります。ここに面白さの工夫を書き込んでいくのが、独自性を出す現実的な場所です。一般的な手順は [一発生成から製品まで](/agent-dev/from-one-shot-to-product/) と [独自性の出し方](/agent-dev/differentiation/) を参照してください
