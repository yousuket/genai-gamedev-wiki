## 概要

「地域クエスト」は、実在の市町村を旅するスマホRPGのシリーズです（岐阜クエスト、三重クエスト、愛知クエスト）。開発者の kiarina 氏は、2026年9月6日から、この3本を Cocos2d-x 3.17.2 から Unreal Engine 5.8 へ移しました。2026年10月1日に Zenn へ書いた記事が、この事例の出典です。
特徴は、ゲームを作り直さず、旧版の C++ と Lua と Cocos Studio の UI をそのまま動かしたことです。Cocos2d-x と同じ顔をした「互換ランタイム」を Unreal Engine の上に作りました。作業のほとんどは AI エージェント（Claude。モデルは Fable 5 と Opus 5）が行い、本人は方針と公開の判断、実機での承認操作を担当したと書かれています。

| 項目 | 内容 |
|---|---|
| 作者 | kiarina 氏（Zenn、GitHub: kiarina）。個人で運営。別に Unreal Engine のゲーム Tokyo Canvas を開発中（2026年10月15日発売予定と記事に記載） |
| 時期 | 着手は2026年9月6日。UE 版の公開は、岐阜が9月22日、三重が9月25日、愛知が9月28日 |
| モデル | Claude（Fable 5 と Opus 5）。ツール名（Claude Code など）は記事に書かれていない |

| 規模（作者の数えた値） | 岐阜は旧リポジトリで約19万行（6割が Lua、4割が C++）。三重は3,463ファイル・約18.6万行、愛知は5,753ファイル・約19.3万行。新しく書いたのは、岐阜で約1万2,600行 |

## 何が移されたか

地域クエストの最初の作品、岐阜クエストは2021年2月に出ました。3本とも同じ自前のRPGエンジンで動き、ゲームの中身は Lua、UI は Cocos Studio、マップは Tiled で作られています。収益は AdMob の広告とアプリ内課金です。後の作品ほど機能が増えています。
作者は「広告と課金があり、自前のサーバーとつながり、毎日遊んでくれている人がいる、現役のゲーム」だと位置づけています。つまり、新規に作るのではなく、運営中の製品を、ユーザーのセーブデータと課金の権利ごと移す仕事でした。

記事の最初に出てくる行数は、移す対象の規模です。3本ともコードだけで20万行近くあります。新しく書いた量（岐阜で約1万2,600行）が少ないのは、旧コードに手を入れず、互換ランタイム側に改変を寄せたからです。

## なぜ Unreal Engine だったか

2Dのスマホゲームなら Godot、Unity、Cocos Creator のほうが先に思い浮かびます。作者は Unreal Engine を選んだ理由を次のように挙げています。

- 開発が止まらなそうなこと。15年ほど前に Cocos2d-x を選び、開発の止まったエンジンの上でゲームを運営し続けるつらさを経験したため、これが一番大きい
- エンジンとエディタのソースが公開されていて、困ったときに最後まで自分で追える
- PlayStation、Xbox、Switch などへ広げられそう。アセットとプラグインが豊富。Epic Online Services を使いたい
- AI と Unreal Engine で開発するノウハウがあった。Tokyo Canvas の開発で、Unreal MCP を通して AI にエディタを操作させてきた

今回の方式では Unreal Engine の機能はほとんど使っていないとも書いています。必要だったのは「各プラットフォームでアプリとして動く土台」と「長く付き合える安心感」でした。エンジンの比較は [ゲームエンジンの選び方](/dev-env/engines/) にあります。

## 進め方

### 1. 作り直しを2日で捨てた

着手した9月6日の方針は、ゲームのロジックを Unreal Engine 側で作り直し、旧版の Lua のイベントを1つずつつなぐことでした。2日間で、最初のマップ、会話、通常攻撃の戦闘、仲間の加入、宝箱が動きました。ただし画面は旧版を真似た別物で、このペースでは終わらないと判断しています。地域クエストは数百のイベントを持ち、C++ 側にも戦闘の計算と状態遷移があり、「描画だけ差し替えればいい」作りではなかったからです。
3日目（9月8日）に、方針を「旧版の C++ をそのまま全部動かす。その下に、Cocos2d-x と同じ顔をした互換ランタイムを作る」へ変えました。その日のうちに旧版のコードがエディタ上でタイトル、フィールド、戦闘まで進み、夜には iPad と Pixel 6 で旧版のセーブデータを引き継いで起動しています。2日間の作り直しの試作は、翌日すべて削除しました。

### 2. 互換ランタイムの3つの方針

- 使われている分だけ作る。Cocos2d-x のすべてを再実装せず、旧コードと Lua が実際に呼ぶ API だけを作り込んだ
- 旧コードには手を入れず、改変は互換ランタイム側に寄せる。どうしても旧コードを直した箇所は、ファイルごとに理由を台帳へ書き、三重と愛知では台帳を patch として当て直した
- 外の世界との境界を1枚に絞る。描画、端末、音、HTTP、ネイティブ（広告、課金、トラッキング許可、位置情報）の5つのインターフェースだけで話す

境界を絞ったので、同じ旧コードを「Unreal Engine の中」と「描画しないコマンドラインのホスト」の両方で動かせました。ホストではサニタイザー（ASan と UBSan。メモリの不具合を検出する道具）をかけて旧コードを走らせ、エディタや実機より手前でメモリの不具合を拾っています。

### 3. Cocos Studio の UI がそのまま動いた

作者が一番大きいと書いているのがここです。メニュー、店、図鑑、ダイアログまで、画面のほとんどは Cocos Studio で作られていて、愛知だけで231ファイルあります。互換ランタイムは、配布用の .csb ではなく制作用の .csd（XML）を実行時に読み、入れ子の ProjectNode、plist のアトラス、フォント、アニメーションまで扱います。
見た目が合っているだけでは安心できません。Cocos Studio の UI は、見た目は正しいのに押せない、という形で崩れるからです。岐阜では、装備屋の行の当たり判定が CSD の 640x100 ではなく透明画像の 10x10 に潰れ、商品が選べませんでした。そこで、全 CSD を描画しないホストで読み込み、すべての Widget のサイズとタッチの設定を CSD の値と突き合わせるテストを作りました。愛知の231ファイルで、ずれは0です。画面を1つも開かずに、全画面の当たり判定を確かめられます。
落とし穴も1つありました。CSD の Visible 属性は編集画面の「目のアイコン」で、Cocos2d-x 3.17 は無視します。互換ランタイムがこれを見てノードを隠したため、旧版では見えていたものが隠れていました。愛知のデバッグ表示が欠けていたことで分かり、3作品とも直しています。

### 4. 稼ぐ部分を先に確かめた

動くことと、ストアに出して既存ユーザーへ届けられることは別です。作者は、方針を決める前に「広告と課金が両OSで成り立たなければ Unreal Engine をやめる」という判定条件を決め、最初に確かめたと書いています。

| 領域 | やったこと |
|---|---|
| 広告 | AdMob のバナーとリワード動画。iOS は Google Mobile Ads 13.9、Android は 24.9 |
| 課金 | 消費型と非消費型。Android は Play Billing 8、iOS は StoreKit。両ストアの sandbox と、製品版ビルドでのテスト購入で確認 |
| セーブ | 旧版のセーブとユーザー ID をそのまま読む。更新の初回に旧セーブを端末内へ退避し、メニューの「きゅうデータにもどす」で戻せるようにした |
| 更新 | 同じ bundle id、package 名の更新として配信。ストア版の旧版から、ストア経由で更新して続きから始まることを両OSで確認 |
| サーバー | 既存の API をそのまま使い、本番のサーバーで全 API を試した |

セーブの退避は役に立ちました。Pixel 6 での最初の確認で、退避なしで上書きした旧セーブが失われる事故があり、退避から戻せたと書かれています。

### 5. 実機の操作もAIが行った

Android（Pixel 6）は adb で、ビルドの入れ替え、タップ、スクリーンショット、ログの回収、デバッグコマンドの送信まで行いました。iOS（iPad Air 4）は Appium（XCUITest と WebDriverAgent）で画面の撮影とタップを行い、愛知では、[App Store](https://developer.apple.com/app-store/) から旧版を入れ直して [TestFlight](https://developer.apple.com/testflight/) で UE 版へ更新する試験も Appium で回しています。
作者が手を動かしたのは、人の承認が要る場面だけでした。購入の確認（購入シートのボタン、指紋認証）、OS のダイアログ（トラッキング許可、位置情報、「このコンピュータを信頼」）、広告が本当に出ているかの目視です。

### 6. 「どこまで動くか」を数字で追った

作者が任せて安心できた一番の理由として挙げているのが、自動テストで進捗が数字で見えたことです。置き換えたのはエンジンだけで、Lua、マップ、マスタ、サーバーは旧版と同じです。そこで、網羅すべきは「ゲームの中身」ではなく「ゲームが使うエンジンの機能」だと考えました。

- Lua からエンジンへの入り口は、C++ に登録された命令に限られる。三重で402件、愛知で477件
- これを台帳にして、テストで実際に呼ばれた命令をエンジンが数え、突き合わせた
- 通らなかった命令は、狙って通すか、「製品からは呼ばれない」「実機でしか起きない」などの理由を台帳に書いて閉じた

速く大量に回すほど、数え方の穴に気づきにくくなります。実際に2つありました。エラーをログから文字列で探していたが、旧版のエラーは日本語（「コルーチンでエラーが発生」）で出ていて拾えていなかったこと。命令を登録するマクロが2か所で定義されていて、計数を片方にしか入れていなかったことです。前者は、エラーが必ず通る1か所で数える形に変え、わざとエラーを起こして数えられることを確かめました。

### 7. デバッグコマンドで自動プレイし、16倍速で回す

テストは、ゲームに足したデバッグ用コマンドで動かしました。新規ユーザーで始めて、会話を送り、目的地へ歩き、戦闘をこなしてエンディングまで進むシナリオの自動プレイと、全特技、全道具、全敵パーティ、周回を1つずつ戦闘で試す機能単位のテストの2種類です。
最初はコンソールから1手ずつ押していて、1戦に1〜8分、シナリオの後半だけで約20時間かかりました。次の順で速くしています。

1. プレイヤーの操作の判断を、外からではなくエンジンの中で毎フレーム行う
2. エディタが裏にあっても60fpsで回す
3. 早送りは「1回の時間の刻みを大きくする」のではなく「1フレームにゲームの更新をN回呼ぶ」で作る（挙動が変わらない）
4. テストの一覧もエンジンの中で回す

速くしても結果が変わらないことは、同じテストを1倍と16倍で流し、フィールドを移った順番や使った特技が一致することで確かめました。作者によれば、3作品とも、新規ユーザーからエンディングまでの自動プレイと機能単位のテストで、Lua のエラーは0でした。16倍速で3作品を自動プレイする動画が記事に埋め込まれています（編集での早送りはなしと記載）。

### 8. 2作目、3作目が速かった理由

着手から公開までは、岐阜が16日、三重が5日、愛知が3日でした。2作目以降は、一番新しい作品の互換ランタイムを写して差分だけを足す形にしています。名前の付け替えは1回でまとめて行い、旧コードへの改変は台帳から patch として当て直し、作品ごとの差分（愛知は位置情報、画面の合成、扇形の描画が増えた）を先に洗い出しました。
3作品の共通ライブラリにはしていません。共通化すると、ある作品の修正が別の作品を壊さないかを毎回気にする必要があるためです。AI がいれば互換層を作品ごとに持っても手間は小さい、後の作品で見つけた不具合は前の作品の次の版へ入れる、というのが作者の考えです。

## 詰まったところ

記事の表から、原因と直し方を抜き出します。

| 問題 | 内容と直し方 |
|---|---|
| CSD の Visible 属性 | 編集画面の目のアイコンなのにノードを隠していた。3作品とも修正 |
| TArray に std::function を入れた | 1フレームにHTTPの応答が5件以上積まれると、配列の再配置で std::function が壊れて落ちる。std::vector に変更 |
| iOS 27 SDK と UIScene | Xcode 27 でビルドしたアプリは、UIScene に対応していないと iOS 27 で起動直後に落ちる。手元は iOS 26 だったため、App Review の却下で分かった |
| 広告 SDK と SQLite | エンジンが持つ SQLite が、広告 SDK の SQLite のシンボルを横取りして iOS の起動で落ちた |
| UE の iOS は ARC なし | Objective-C の autorelease のオブジェクトを持ち続けると落ちる |
| 画面の端まで描く | 旧版と違って切り欠きの下まで描くため、UI がカメラの穴や広告に重なった。UI だけを Safe Area の内側へ入れた |
| 旧版から眠っていた不具合 | アニメーションの添字が float の丸めで1つあふれて落ちる、など。旧版の不具合もまとめて直した |

「iOS 27 の落ち」は、手元の端末では再現せず、審査の却下で初めて分かった問題です。実機で確かめる範囲を、手元にある OS だけにしていると見落とす例になっています。

## 公開後

作者は、毎日、利用者数、クラッシュ、レビュー、問い合わせを見ていると書いています。記事の時点（2026年10月1日）の数字は次のとおりで、すべて作者の記述です。

- 移行は進んでいる。ストアの自動更新で少しずつ UE 版へ移り、岐阜では1日の利用者のうち UE 版が8〜9割になった。新規登録が不自然に増えていない（旧データを引き継げずやり直した人が目立たない）ことも毎日確認している
- クラッシュは少ない。[Google Play](https://play.google.com/console/about/) の記録（9月28日まで）では、岐阜の UE 版は2.0.0 で2件（それぞれ1人）のみで、その後の版は0件。三重の UE 版も0件
- 出たものもある。愛知では、特定の古い Android 端末1台で戦闘開始時に落ちるクラッシュと、旧版から続いていたクラッシュが1件ずつ。どちらも調査中
- 公開後に見つけて直した不具合。愛知で、iPhone の新規ユーザーがキャラクター作成で広告にボタンを隠されて始められなかった。2.0.1 で修正

[App Store](https://developer.apple.com/app-store/) の公開情報を確認すると（2026年10月5日時点）、現在の版は岐阜 2.0.3、三重 2.0.3、愛知 2.0.1で、作者の記述と矛盾しません。評価件数は岐阜 469、三重 59、愛知 68ですが、旧版からの累計で、UE 版だけの評価ではありません。UE 版の実機での動作やプレイ感は、確認できていません。

## AIと作者の分担

| 作者が決めた・やったこと | AIエージェントが行ったこと |
|---|---|
| Unreal Engine にすること、作り直さない方式への転換 | 旧コードの調査、互換ランタイムの実装 |
| 直す基準（問題が出たら直して出す。版は戻さない） | 自動テストの仕組みづくりと実行、台帳の管理 |
| 実機で人の承認が要る操作（購入の確認、OS のダイアログ、広告の目視） | 実機の操作（adb、Appium）、ビルド、署名、ストアへのアップロードと提出 |
| 公開の判断 | 公開後の監視の集計 |

記事には、プロンプトの全文や、AI に出した指示の文面は載っていません。このため、「どんなプロンプトで」の部分は、公開資料からは確認できません。

## この事例から学べること

ここからは、この Wiki の考えです。原文に書かれた内容とは分けて読んでください。

- 作り直しより、境界を引いて土台だけ替える。2日間の作り直しを捨てて方針を変えたことで、残りの作業は「互換ランタイムをどこまで作るか」という有限の問題になりました。同じ形の移植（エンジンの終了、ストアの要件変更への対応）は、個人開発でも起きます
- 「動いた」を数字にする。呼ばれた命令の台帳、全 Widget の当たり判定の突き合わせ、1倍と16倍の結果の一致のように、AI が自分で合否を読める基準があると、任せる範囲を広げられます。詳しくは [検証ループ](/agent-dev/verification-loop/) を参照してください
- 検証の仕組み自体も疑う。エラーを日本語のログで探せていなかった例のように、数える仕組みの穴は、わざと失敗させて確かめる必要があります
- 人の承認が要る場面と、AI が回せる場面を分ける。購入、OS の許可、広告の目視は人、それ以外の実機操作は adb と Appium、という分け方は、スマホゲームの検証にそのまま使えます（[広告と課金](/monetization/ads-and-iap/)）
- 先に撤退の条件を決める。「広告と課金が両OSで成り立たなければやめる」と最初に決め、一番危険なところから確かめています
- 実機は、新しい OS でも確かめる。手元の OS だけでは見つからない落ちがあります
- 費用の見方。この事例の費用は、API の従量課金ではなく、サブスクの利用枠の体感です。トークン数や金額は公開されていません（比較は [コスト管理](/agent-dev/cost-management/) を参照）

## AIの活用ポイント

次のプロンプトは、この事例の進め方をもとに、このWikiで作った例です。

- 移植の方針を決める段階で、作り直しと互換層のどちらが現実的かを見積もらせる

```text
このリポジトリを別のゲームエンジンへ移したい。
(1) ゲームロジックを作り直す案と、旧コードをそのまま動かす互換層を作る案について、
    実際に呼ばれている API の一覧と数、作業量の見込みを調べて比較して。
(2) 旧コードから外部（描画、音、通信、ストア SDK）へ出る口を列挙して。
```

- 検証の台帳を作らせる

```text
スクリプトからエンジンへ公開している命令を全部列挙して台帳にして。
テスト実行中に呼ばれた命令を数えて台帳と突き合わせ、
呼ばれなかった命令には「呼ばれる条件」か「閉じる理由」を書いて。
数え方が壊れていないか、わざとエラーを起こして確認して。
```

- 実機の確認を自動化する。Android は adb、iOS は Appium で、ビルドの入れ替え、タップ、スクリーンショット、ログの回収を任せ、購入の確認や OS のダイアログのような人の承認が要る場面だけを人に回す
- 2本目以降は、一番新しい作品を写して差分だけを足させる。直したところを台帳に書かせておくと、別の作品へ当て直せる
