## 概要

Claude Code の開発チームが、エージェントに渡す「ツール」をどう設計し、どう作り直してきたかを書いた記事です。失敗した案も含めて、4つの事例で説明されています。この記事は、その流れを落とさずに整理し、ゲーム制作に使う場合の考え方を加えます。

- 公開日: 2026年4月10日。著者: Thariq Shihipar 氏（Anthropic の技術スタッフ、Claude Code を担当）。読了時間: 7分
- 原文: [Seeing like an agent: how we design tools in Claude Code](https://claude.dev/blog/seeing-like-an-agent/)
- この記事で分かること: ツールを増やす基準と減らす基準、質問ツールが3回目で形になった経緯、ToDo を Task に置き換えた理由、検索の方式が変わった流れ、専用のサブエージェントで情報を足す手
- 原文はゲームに触れていません。「ゲーム制作での使いどころ」の節は、この Wiki の考えです。

用語を2つ補います。ツール（tool）は、エージェントがファイルを読む、コマンドを実行する、ユーザーに質問する、といった操作に使う、名前と引数を持った部品です。ハーネス（harness）は、モデルにツールを渡し、実行し、結果を返す外側の仕組みです。

## 問題設定: ツールは1つか、50個か

原文は、エージェントの作りにくい部分はツールの組み立てだと始めます。Claude は、ツール呼び出しを通してのみ動きます。bash のような汎用の道具を1つ渡す案もあれば、用途ごとに50個の専用ツールを渡す案もあります。どちらがよいかは、一般論では決まらないというのが出発点です。

### 難しい数学の問題を解く例え

原文は、難しい数学の問題を解くとき、どんな道具が欲しいかを考えるよう勧めます。

| 渡す道具 | 起きること |
|---|---|
| 紙 | 最低限は解ける。ただし手計算が限界になる |
| 電卓 | 速くなる。ただし高度な機能は、使い方を知らないと使えない |
| コンピューター | 最も速く強力。ただし、コードを書いて動かせる人でないと使いこなせない |

どれがよいかは、解く人の技能で決まります。モデルも同じで、ツールは「そのモデルの能力の形」に合わせて渡します。では、能力はどう知るのか。原文の答えは、出力を読み、試し、観察することです。これを、記事の題名にある「エージェントの視点で見る（see like an agent）」と呼んでいます。

この記事の残りは、この考えを実際にやってみた4つの事例です。いつツールを足すか、いつ外すか、その見分け方が、各事例の中に書かれています。

## 事例1: 質問のツール（AskUserQuestion）

### 目標

エージェントが、ユーザーに質問する力（elicitation と呼ばれます）を上げることが目標でした。Claude は、普通の文章でも質問できます。ただ、その質問に答えるのが、必要以上に時間のかかる作業になっていました。ユーザーとの間の摩擦を減らし、一度にやりとりできる情報量を増やすにはどうするか、が課題でした。

### 3つの試行

| 試行 | 内容 | 結果 |
|---|---|---|
| 1. 計画の終了ツールを拡張 | 計画を提出するツール（ExitPlanTool）に、質問の配列を渡せるようにした。実装は最も簡単 | Claude が混乱した。計画と、その計画への質問を、同時に求めているため。答えが計画と食い違ったらどうするか、ツールを2回呼ぶのか、が決まらない。破棄した |
| 2. 出力の書式を変える | 質問を、括弧つきの選択肢を持つ箇条書きの書式で出力させ、それを解析して画面に出す | 書式を出せることは多いが、確実ではなかった。余計な文を足す、選択肢を落とす、書式自体を捨てる、が起きた |
| 3. 専用のツールを作る | いつでも呼べるツールにして、特に計画モードで呼ぶよう促した。呼ばれたら、質問を表示するダイアログを出し、答えが返るまでエージェントの動きを止める | 採用された |

### 3回目が良かった理由

原文が挙げる理由は3つです。

1. 構造のある出力を、確実に得られた。選択肢を複数出させることも、確実にできた。
2. ユーザー側が組み合わせて使える。Agent SDK から呼ぶ、Skill の中で名前を挙げて呼ぶ、といった使い方ができた。
3. Claude 自身が、このツールを呼びたがった。原文は、どれだけよく設計したツールでも、Claude が呼び方を理解していなければ動かない、と書いています。

原文は、これが質問の最終形だとは考えていません。モデルが賢くなれば、それを支えるツールも変わるからです。次の事例が、それを示します。

## 事例2: ToDo から Task へ

### 最初の ToDo ツール

Claude Code の公開当初、モデルには ToDo のリストが要ると考えられました。作業の最初にリストを書き、終わったものを消していけば、軌道を外れにくいという発想です。そのために TodoWrite というツールを渡し、ToDo を書き込み、更新し、ユーザーにも見せました。

それでもモデルは、やるべきことを忘れることがありました。そこで、5ターンごとに、目標を思い出させるシステムのリマインダーを差し込みました。

### モデルが賢くなって起きたこと

| 変化 | 起きた問題 |
|---|---|
| モデルが良くなり、ToDo リストが窮屈になった | リマインダーが来るたびに、Claude は「リストを守らなければ」と受け取った。方針を変えるべきと気づいても、リストの変更をためらった |
| Opus 4.5 が、サブエージェントを格段にうまく使うようになった | サブエージェントどうしが、1つの ToDo リストをどう共有するのか、という問いが出た |

### 置き換え

TodoWrite は、Task ツールに置き換えられました。違いは目的です。ToDo は、モデル自身を軌道に乗せるためのものでした。Task は、エージェント同士が連絡を取るためのものです。依存関係を持てる、サブエージェントの間で更新を共有できる、モデル自身が変更も削除もできる、という性質があります。

原文の教訓は、モデルの能力が上がると、かつて必要だったツールが、いまは行動を縛る制約になりうることです。前提を定期的に見直す必要があります。もう1つ、対応するモデルを少数に絞り、能力の傾向が似たものにしておくと、この見直しが楽になる、という実務上の助言も書かれています。

## 事例3: 検索の窓口

原文は、最も影響の大きいツールは、Claude が自分で文脈を見つけるためのものだと書きます。

### RAG から Grep へ

| 段階 | 方式 | 問題 |
|---|---|---|
| 内部での初期 | RAG（検索拡張生成）。ベクトルデータベースにコードベースの索引を前もって作り、回答のたびに、関連する断片を探して Claude に渡す | 速くて強力だが、索引の作成と設定が要る。環境が違うと壊れやすい。そして、Claude が文脈を自分で見つけるのではなく、与えられている |
| 転換 | Grep ツールを渡す | Claude が自分でファイルを検索し、文脈を組み立てる |

原文の論理は単純です。Claude がウェブを検索できるなら、コードベースも検索できるはずです。モデルが賢くなるほど、適切な道具を渡すだけで、自分の文脈を組み立てるのがうまくなります。

### Skill と段階的な開示

Agent Skills を導入した時に、「段階的な開示（progressive disclosure）」が形になりました。これは、必要なときに、必要な分だけ読む設計です。Claude が Skill のファイルを読み、そのファイルが別のファイルを指し、Claude がそれを再帰的にたどります。原文は、Skill の典型的な使い方の1つが、検索能力の追加（API の使い方、データベースへの問い合わせ方の手順）だとしています。

1年の間に、Claude は「文脈を自分で作れない」状態から「複数の階層のファイルをたどって、必要な文脈に行き着く」状態になった、と原文は書きます。この技法は、いまでは、ツールを足さずに機能を足す手段として使われています。理由は次の事例にあります。

## 事例4: Claude Code Guide（専用のサブエージェント）

### ツールを増やさない理由

Claude Code のツールは、現在で約20個です。チームは、すべてが必要かを頻繁に見直します。新しいツールを足す基準は高く、ツールが1つ増えると、モデルが考える選択肢が1つ増えるからです。

### 課題と、3つの段階

課題は、Claude が Claude Code 自身の使い方に詳しくないことでした。MCP の追加方法や、スラッシュコマンドの意味を聞かれても答えられませんでした。

| 段階 | 内容 | 問題 |
|---|---|---|
| 案A | 情報をすべて、システムプロンプトに入れる | 質問されることが少ない内容なので、コンテキストを汚す（原文は context rot と呼ぶ）。主な仕事であるコードを書くことの邪魔になる |
| 案B | ドキュメントへのリンクを渡し、必要なときに読み込み、検索させる | 動くが、ユーザーが一文で得られる答えのために、大きなドキュメントの塊を文脈に取り込んでしまう |
| 案C | Claude Code Guide という専用のサブエージェントを作る | 採用された |

Claude Code Guide は、ユーザーが Claude Code 自体について尋ねたときに呼ばれます。サブエージェントが、自分のコンテキストの中でドキュメントを検索し、探し方と抜き出し方の詳しい指示に従い、答えだけを返します。メインのエージェントのコンテキストは、きれいなままです。

完全な解決ではない、とも書かれています。Claude に、Claude 自身の設定方法を聞くと、まだ混乱することがあります。それでも、新しいツールを足さずに、Claude の行動の範囲を広げられた点が成果です。

## 原文の結論

ツール設計は、科学であると同時に芸術でもあります。使うモデル、エージェントの目的、動く環境に強く依存します。助言は、頻繁に試す、出力を読む、新しいことを試す、そして、エージェントの視点で見ることです。

## 4つの事例から読み取れる設計の判断

原文の文章から、この Wiki が整理した表です。

| 判断 | 原文の事例での答え |
|---|---|
| ツールを足すか | 足す基準は高い。選択肢が増えると、モデルが考えることが増える（事例4）。足さずに済むなら、Skill や専用のサブエージェントを使う |
| 構造のある出力が要るか | 書式の指示より、ツールとして呼ばせるほうが安定する（事例1） |
| 古いツールを外すか | モデルが賢くなったら、前提を見直す。支えが、縛りに変わる（事例2） |
| 情報を渡すか、探させるか | 前もって渡すより、探せる道具を渡す（事例3） |
| 長いドキュメントをどこで読むか | メインの文脈に入れず、サブエージェントに読ませて答えだけ受け取る（事例4） |
| 設計の確かめ方 | モデルが呼びたがるか、出力は良いか、を実際に見る（事例1） |

## 公式ドキュメントで確認できる、いまの状態

原文の記述に関連して、Claude Code の公式ドキュメントで確認できたことです（2026年10月時点）。原文にはない情報です。

- ツールの一覧では、TodoWrite は、TaskCreate、TaskGet、TaskList、TaskUpdate に代わって、既定では無効と書かれています。さらに、Task 系のツールが既定で使えるのは、一部の古いモデル（Claude 3.x、Opus 4 から 4.7、Sonnet 4 から 4.6、Haiku 4.5）だけで、それ以外のモデルでは、既定では外されています。理由として、新しいモデルは、書かれたチェックリストがなくても多段階の作業を追えること、ツールの定義とリマインダーがコンテキストを使うことが書かれています（[Tools reference](https://code.claude.com/docs/en/tools-reference)）。原文の「前提を見直す」が、実際の設定に反映された例です。
- AskUserQuestion は、複数選択式の質問をする道具として載っています。選択肢のほかに、自分の文章で答える欄があります（同ページ）。
- 組み込みのサブエージェントに claude-code-guide があり、使うモデルは Haiku、使う場面は Claude Code の機能について聞かれたときです（[Create custom subagents](https://code.claude.com/docs/en/sub-agents)）。

## ゲーム制作での使いどころ

ここからは、この Wiki の考えです。原文は、Claude Code というエージェント自身の設計の話で、ゲームには触れていません。

### 検証用の窓口を、エージェントが使う道具として設計する

[検証ループ](/agent-dev/verification-loop/)では、ゲームの状態を外から読み書きできる口（`window.__game`）を作ります。この口は、エージェントにとっての道具です。事例1と事例4の考えを当てはめると、次の2案になります。

| 案 | 内容 | エージェントから見た問題 |
|---|---|---|
| 細かく分ける | `setPlayerX(x)`、`setPlayerY(y)`、`setHp(n)`、`spawnEnemy(...)` など、数十の関数 | 選択肢が多く、組み合わせ方を毎回考える。どの順で呼ぶか迷う |
| 少数に絞る | `snapshot()`（状態を1つの構造で返す）、`step(frames)`（固定刻みで進める）、`setInput(...)`（入力を与える）の3つ | 呼び方が少なく、返り値が構造を持つ。使い間違いが少ない |

後者は、検証ループの記事の `DebugApi` と同じ形です。設計した後は、事例1の教訓に従い、実際にエージェントに使わせて、呼び方を間違えないか、返り値を読み違えないかを確かめます。次の依頼で試せます。

```text
window.__game の API を、初めて見るエージェントとして使ってみてください。
コードは読まず、公開されている関数の名前と型だけを手がかりに、
「敵を3体出して、10フレーム進めて、プレイヤーの位置を報告する」を実行してください。
迷った点、間違えた呼び方、名前から意味が分からなかった関数を、最後に一覧にしてください。
```

迷った点が出たら、関数の名前と引数を直します。

### 仕様の曖昧な点は、選択式で聞かせる

事例1のとおり、質問は、選択肢のある構造で出させたほうが、ユーザーが答えやすくなります。ゲームの企画段階は、曖昧な点が多いので向いています。[プロンプトの型](/agent-dev/prompt-patterns/)の「前提や制約を先に書かせる」と組み合わせて、次のように頼みます。

```text
実装の前に、仕様で曖昧な点を、選択式の質問で聞いてください。
各質問に選択肢を2〜4つ付け、あなたのおすすめと理由も添えてください。
画面サイズ、操作方法（キーボードかタッチか）、セーブの有無、ゲームオーバーの条件を、必ず含めてください。
```

選択式の質問を出す道具が、Claude Code では AskUserQuestion にあたります。使われ方は、Claude の判断です。推測ですが、依頼に「選択式で聞いて」と書くと、呼ばれやすくなります。

### 作業の一覧は、途中で変えてよいと書いておく

事例2の「リストを守らなければと受け取る」問題は、自分で作る進捗ファイル（`docs/progress.md` など）でも起きます。指示ファイルに「一覧は目安である。作業中に必要なことが分かったら、項目を足す、変える、消す。変えたら、理由を1行書く」と書いておくと、方針を直すことをためらいにくくなります（[コンテキスト管理](/agent-dev/context-management/)、[指示ファイル](/agent-dev/project-instructions/)）。これは推測です。原文で確かめられているのは、リマインダーの差し込みがモデルを縛った、という点までです。

### 資料は、索引から辿れるように置く

事例3の段階的な開示を、プロジェクトの資料に当てはめます。仕様、数値の表、アセットの一覧を、すべて指示ファイルに入れる代わりに、`docs/INDEX.md` に「何がどのファイルにあるか」を1行ずつ書き、指示ファイルには「仕様は `docs/INDEX.md` から辿る」とだけ書きます。エージェントは、必要になったときに、必要な資料を開きます。事例3の「ファイルが別のファイルを指す」形です。

### エンジンの公式ドキュメントは、答えだけ返す係に調べさせる

事例4と同じ形を、自分のプロジェクトに作れます。Godot や Unity、Three.js のドキュメントは長いので、メインの会話で読ませると、コンテキストを大きく使います。調べものだけを担当するサブエージェントを作り、答えだけを受け取ります。`.claude/agents/engine-docs.md` の例です。

```markdown
---
name: engine-docs
description: エンジン（Three.js など）の使い方を、公式ドキュメントで調べて、答えだけを返す。実装はしない
tools: Read, Grep, Glob, WebFetch
model: haiku
---

あなたは調べもの専用の係です。コードは書きません。
質問に必要な部分だけをドキュメントから探し、次の形で返してください。
1. 答え（3文以内）
2. 該当するAPIの名前と、最小のコード例
3. 出典のURL
ドキュメントの本文は貼らないでください。
```

サブエージェントの `tools` と `model` は、公式ドキュメントで確認できる設定項目です（[Create custom subagents](https://code.claude.com/docs/en/sub-agents)）。調べものは Haiku で足りるかは、試して決めます。コンテキストの扱いは [コンテキスト管理](/agent-dev/context-management/)、サブエージェントの仕組みは [並列開発](/agent-dev/parallel-agents/) にあります。

## AIの活用ポイント

自分のゲームの道具や指示を、エージェントの視点で点検させるために、エージェント自身を使えます。

### 道具の使いにくさを聞く

```text
このリポジトリの npm scripts と、window.__game の API を、初めて見る作業者として眺めてください。
次の観点で、使いにくい点を挙げてください。
- 名前から何をするか分からないもの
- 似ていて、使い分けに迷うもの
- 呼び出しの順番が決まっているのに、どこにも書かれていないもの
- 失敗したとき、何が悪かったか分かる出力にならないもの
直し方は、名前の変更案と、まとめられる関数の案の2つで出してください。
```

### 指示ファイルの古い前提を探す

事例2の考えを、指示ファイルに当てます。

```text
CLAUDE.md を読んで、モデルが賢くなったために、いまは不要になった（または邪魔になっている）指示を探してください。
特に、手順を細かく縛っている指示、同じことを2回書いている指示、ファイルを見れば分かることを書いている指示を挙げてください。
削る案と、削った場合に起きそうな失敗を、1項目ずつ書いてください。削る前に、私に見せてください。
```
