## 概要

Claude Code の公式ブログの1本、Thariq Shihipar 氏による「Using Claude Code: Spending your effort」を、1本だけ取り上げて掘り下げます。原文は2026年9月25日公開、読了時間は8分です。
この記事で分かるのは、次の4点です。

- effort が、モデルの動きの何を変える値なのか（原文の説明）
- 同じ依頼を low から max まで流したとき、所要時間と出来がどう変わったか（原文の実験の数字）
- 難しい課題で、effort が効く失敗と効かない失敗はどう違うか（Terminal-Bench 3.0 の分析）
- 著者が普段使っている、effort を切り替える開発の流れと、4段階の使い分けの目安

原文はゲームに触れていません。ゲーム制作への当てはめは、後半の節で「Wiki の考え」として分けて書きます。連載の入口は [Claude Code 公式ブログ](/claude-blog/) です。

原文: [Using Claude Code: Spending your effort](https://claude.dev/blog/spending-your-effort/)

## 著者が確かめたかったこと

冒頭で著者は、最新のモデル（Opus 5.5 と Fable 5.1）は、Claude Code のプロンプトキャッシュ（同じ内容の再計算を省く仕組み）を壊さずに effort に反応する点が良いと述べています。そのうえで、ユーザーから「effort とは結局何か」「どの段階をいつ使うのか」「そもそもなぜ必要か」という質問が多く届いていた、と書いています。

そこで、評価（eval）を読み込み、普段の仕事で自分でも試しました。結論として、effort は「どれだけ確認し、どれだけ端のケースを試し、どれだけ自分の判断で動くか」を調整するつまみでした。ハードウェア、コードレビュー、セキュリティのように、確認と端のケースの検討が効く分野では、高い effort が良い結果につながっています。
普通のソフトウェア開発では、著者は「質問させる、低い effort で実装する、中身を見る、高い effort で検証する」という流れを使っています。この流れの詳細は、後の節で述べます。

## effort とは何か

原文の説明は、人に仕事を頼む場面にたとえるものです。

- 「12時間かけて」と頼まれたら、相手はとにかく全力でやってほしいのだと受け取る。
- 同じ仕事を「1時間で」と頼まれたら、条件を満たす最良の版をまず出し、あとは直していく前提だと受け取る。
- あるいは「これは最低3時間かかる」と断って、3時間かけて出すこともある。

effort は、モデルに「計算をどれだけ使ってよいか」の目安を渡す値で、頼む側が見積もる仕事の難しさとも関係します。どの段階でも、Claude は依頼を妥当にこなそうとします。高い effort で変わるのは、判断と確認のために、自分から取る行動が増えることです。

原文は「効果曲線」の図も載せています。Fable 5.1 と Opus 5.5 は、段階を1つ上げるたびに、ベンチマークの点数と使うトークン数が上がる、これまでで最良の曲線だとされています。図の注記によると、Terminal-Bench 3.0 の70タスク（GPU を使う4タスクは除外）を全モデルで同じに揃えています。Opus 5.5 の実行は約3週間後で、応答は128kトークンまで、GitHub や PyPI にはつながない条件でした。

## 3つの実験: 指示の細かさで差が変わる

著者は、Opus 5.5 で同じ依頼を複数の effort で流して、出来を見比べています。原文は「ごく簡単な例」と断っています。

### 実験1: 仕様が曖昧な作成依頼

「個人用のフィットネス・筋トレ記録アプリを作って」とだけ頼む実験です。

| effort | 所要時間 | 出来 |
|---|---|---|
| low | 1.5分 | 記録の一覧と、簡単なグラフだけ |
| medium | 4分 | （原文は時間のみ） |
| high | 11分 | （原文は時間のみ） |
| max | 67分 | 画面が作り込まれ、ヒートチャートまである |

原文の読みは、段階が上がるほど、細部が増えるだけでなく、Claude が途中で下す選択も増える、というものです。反復の出発点になる簡素な土台がほしければ low で足ります。1回で得られる最良の出来がほしければ max です。

### 実験2: ある程度決まっているデザインの探索

Claude Code の `/config` メニューを作り直す依頼です。どの段階でも、サブメニューと検索の改善という大筋は同じでした。

- low（1分）: 考えは伝わる、動かせるスケッチ。ただし Claude Code らしい見た目ではない。
- max（28分）: Claude Code そっくりのモックと、複数の操作フローの説明まで付く。

著者の判断は、フィードバックを返して直していくなら low のほうがずっと早く、max は最初から仕上がったものが出る、というものです。この課題では、Claude の発想を知る目的で low を使うほうが好みだと書いています。

### 実験3: 細かく指定した作成依頼

フィットネスアプリについて、Claude に詳しくインタビューさせて仕様を作り、その仕様を、別の effort で実装させました。すると、どの段階でも、見た目も実装もかなり似ました。違いは細部で、max では、いくつかの細部を単純にする作業に時間を使っていました。所要時間は low が16分、medium が22分、high が33分、max が79分でした。

ここで目を引くのは、実験1と実験3の low の差です。仕様が詰まっていないと、low は1.5分、max は67分で、出来も別物です。仕様を詰めたあとは、low と max は16分と79分で、出来は近くなります。つまり、effort の差が出るのは、モデルが自分で決める余地が大きいときです。

## 著者の開発の流れ

実験からの結論として、原文は、effort は「自分がどれくらい作業の輪の中にいたいか」で選ぶと述べます。low は速く出発点が返り、高い段階は多くの仕事をこなす反面、Claude が持ち主に代わって置く前提も増えます。実際に使っている流れは次の4ステップです。

1. 仕様を渡し、足りない点を、自分にインタビューさせる。
2. low で実装させる。
3. 要点を押さえているかを確かめ、必要なら low のまま直す。
4. high で、検証とテストをさせる。

## 難しい課題での効き方: Terminal-Bench 3.0

トイ・プロブレムは、どの段階でも解けます。解けるか解けないかの境目で何が起きるかを知るため、著者はコミュニティ由来のベンチマーク Terminal-Bench 3.0 を読みました。課題はセキュリティ、ハードウェア、ML、科学、ソフトウェア、運用、メディアに分かれ、原文が挙げる例は次のとおりです。

- 小さな FPGA に収まる8ビットのゲーム機を Verilog で作り、テスト用 ROM を描画する。
- Takens の埋め込み定理を Lean 4 で形式的に証明する。
- 専門家混合モデルのチェックポイント16個を1つに統合し、基準の出力を再現する。
- 企業の月次の EU 貿易統計の申告を、最初から最後まで実行する。
- ポスター画像を、編集できるレイアウトファイルとして作り直す。

著者は、普段の仕事よりずっと複雑で、規模の大きな課題が多かったと述べています。

### 隠れた端のケースが多い課題で効く

主な結論は、高い effort は、隠れた端のケースが多い課題で最も効く、です。例は html-js-filter で、ページに JavaScript をこっそり入れる手口を全部取り除く HTML サニタイザーを作る課題です。Fable 5.1 は、low で5回中1回、xhigh で5回中5回成功しました。

- low の1回は約2分。ほぼ1回でフィルターを書き、手で書いた1枚のページで試して終わる。
- high の1回は約33分。原文が追った実行では、最初の草稿を敵対的に自分でレビューし、使っているパーサーのソースを読んで不具合を確認し、きれいな入力が同じ出力になる多数のテストを回し、標準的な XSS のテスト集を流し、最後にランダムな文書を生成するファズ（fuzz）テストまで書いていた。

性能の最適化やセキュリティレビューのように、品質の要求が高く、複雑な作業では、この手間に見合うと原文は述べます。ただし、すべての作業に必要なわけではない、とも明記しています。

### 失敗の型は、effort で減るものと減らないものがある

全結果の図では、失敗の理由を並べています。要約すると、effort を上げると、端のケースの見落としによる失敗は減りますが、方針そのものが間違っている失敗は直りません。失敗の種類は、モデルの判定による近似で、図の注記にそう書かれています。

図の文字情報にある Fable 5.1 の数字（各370回の試行）は次のとおりです。

| 結果の種類 | low | max |
|---|---|---|
| 成功 | 140 | 214 |
| 自分のテストが見逃した不具合 | 40 | 14 |
| 不完全、または誤った修正 | 31 | 10 |
| 要件の読み違い | 45 | 26 |
| ドメインのルールを誤った | 32 | 24 |
| 誤った解釈を選んだ | 25 | 47 |

「テストが見逃した不具合」や「不完全な修正」が大きく減る一方、「誤った解釈を選んだ」はむしろ増えています。この表の分類を、原文の言う「端のケース」「方針」のどちらに割り当てるかは、原文のテキストには書かれていません。

### 効きやすい分野

分野ごとの合格率（Fable 5.1、低い段階から最上位の段階へ）は次のとおりです。低い段階は、各モデルの下位2設定をまとめ、最上位は上位3設定をまとめた値と、注記にあります。

| 分野 | 低い段階 | 最上位 |
|---|---|---|
| セキュリティ | 64% | 87% |
| ハードウェア | 34% | 75% |
| ML | 54% | 73% |
| 科学 | 41% | 61% |
| ソフトウェア | 43% | 56% |
| メディア | 18% | 30% |
| 運用 | 12% | 22% |

ハードウェアの伸びが最大で、ソフトウェア、メディア、運用は伸びが小さくなっています。

### Opus 5.5 の3つの具体例

low で落ち、high 以上で通った課題を、原文は3つ挙げています。いずれも、テストと端のケースの検討が違いを生んでいます。

- mvcc-lsm-compaction（ストレージエンジンの不具合修正）: 0/5 から xhigh で4/5。low（1回約1分）は、ビルドも再現も試す前にコードを編集し、新しいテストが元の不具合を検出できるかも確かめなかった。xhigh（約11分）は先にクラッシュを再現し、圧縮しない基準実装と比べるランダムなテストを書き、半端な修正でテストが失敗することも確かめた。
- cli-2ph-simplex（線形計画ソルバーの CLI）: 0/5 から high で5/5。low は1回で書き、小さな問題で試して、約1万トークンで終わった。最後に「大きな問題では遅いかも」と書いたが、確かめていない。high は、別の総当たり解法とランダムな問題で突き合わせ、大きな問題の時間を測り、遅すぎる場合やクラッシュを見つけて探索を作り直した。
- gsea-proteomics（遺伝子セット濃縮解析）: 0/5 から high で4/5。low は、もっともらしい前処理で1回だけ解析して報告した。high は、前処理を2通り試し、有意な処理群のリストが変わるのに気づいて、原因を調べてから正しい方を選んだ。

最後の例について、原文は、人が付いていれば Claude が前処理の方法を質問したかもしれないが、人がいない環境では、high のほうが成績が良い、と補足しています。

数字の前提として、注に、これらは社内の実行（1課題5回）で、Fable 5.1 では本番の安全対策を切った状態、セキュリティの課題はインターネット接続なしで行ったものとあり、公開リーダーボードや発表記事の数字とは一致しないとされています。

## 使い分けの目安（著者の経験則）

| effort | 向く場面（原文の例） |
|---|---|
| low | 速い返答がほしく、人が輪の中にいる作業。ブレインストーミング、スケッチ、易しい変更 |
| medium | 普段の開発の大半。新機能の実装 |
| high | 確認が大切、または端のケースが多い作業。既存のコードベースの不具合修正 |
| max | 人が付かず、難題を最後まで解かせたいとき。アプリの作成と検証を通しで行う、重要なソフトの脆弱性探し |

`/effort` で、会話の途中でも変えられます。著者は、この目安が読者の感覚と合うか、フィードバックを求めています。

## ゲーム制作での使いどころ

ここからは Wiki の考えです。原文はゲームには触れていません。

effort の差は、モデルが自分で決める余地の大きさで出る、という原文の観察を、ゲーム制作の場面に当てはめます。

| 場面 | 提案する設定 | 理由 |
|---|---|---|
| 「ブロック崩しっぽいものを作って」のような最初の試作 | low | 出来を見て指示を足す前提。67分かける理由がない |
| 仕様書を渡した機能の実装（敵の追加、メニュー画面） | low から medium | 仕様が固いほど、段階による差は小さい |
| 当たり判定のすり抜け、セーブデータの移行、特定のステージだけ落ちるバグ | high | 場合分けが多く、テストを自分で書いて確かめる動きが効く |
| ボスの行動パターンを乱数で動かすのに破綻しないか確認 | high 以上 | ファズ的な試行が効く領域 |
| 手触りの調整、見た目の好み | low | 人が遊んで決める工程で、早く返るほうが回しやすい |

流れは、原文の4ステップを、ゲームに置き換えて使えます（推測です）。

```text
1. /effort medium   # 仕様のたたき台を渡し、「足りない点を質問して」と頼む
2. /effort low      # 実装させ、自分で遊んで確かめる
3. /effort high     # 「敵の波を1000回、seed を変えて自動で回し、詰みや例外がないか確認して」
```

3の確認は、検証の仕組みがあって初めて意味を持ちます。ゲームの状態を外から読める口、乱数の seed の固定、スクリーンショットの撮影は [検証ループ](/agent-dev/verification-loop/) にあります。原文の high の実行が、ファズや総当たりとの突き合わせをしていたことは、検証用の道具を渡す価値の裏づけになります。

質問させて仕様を固める1の工程は、[仕様書駆動](/agent-dev/spec-driven/) の「受け入れ条件」の考え方とそのまま重なります。仕様を詰めるほど段階による差が小さくなる、という実験3の結果からは、実装の effort を下げて費用を抑える道が見えます（[コスト管理](/agent-dev/cost-management/)）。
手触りの調整は、人が遊ぶ時間が支配的なので、effort を上げても短くなりません（[手触りの詰め方](/agent-dev/game-feel/)）。この点は、実験2で low の返りの速さを好んだ著者の判断とも合います。

## AIの活用ポイント

effort を決める前に、AIに、仕事の「判断の余地」を見積もらせる使い方があります。

```text
次の依頼を、effort の low / medium / high のどれで流すのが妥当か、
理由と一緒に答えてください。判断の基準は次の2つです。
(1) 仕様が曖昧で、あなたが勝手に決める部分が多いか
(2) 見落としたときの被害が大きいか（セーブデータの破損など）

依頼: ダッシュ中に壁抜けが起きるバグを直す。再現手順は添付のとおり。
```

実装後の検証は、段階を上げて別のセッションで頼むと、見る目が変わります。

```text
/effort high
直前の変更に対して、次を実行してください。
- 修正前の状態でバグを再現するテストを先に書き、失敗することを確かめる
- 修正後に通ることを確かめる
- 壁の角、ジャンプ直後、ポーズ解除直後の3つの端のケースを足す
テストが何を保証しているかを、最後に3行で報告してください。
```

原文の mvcc-lsm-compaction の high の動き（再現してからテストを書き、半端な修正で失敗することを確かめる）を、ゲームの不具合修正に写した指示です（推測です）。
