## 概要

Claude Code の公式ブログの1本、Thariq Shihipar 氏による「The new rules of context engineering for Claude 5 generation models」を、1本だけ取り上げて掘り下げます。原文は2026年7月24日公開、読了時間は7分です。
この記事で分かるのは、次の4点です。

- Claude Code の開発チームが、なぜシステムプロンプトの80%以上を削ったのか
- 以前の常識6つ（規則、例、一括投入、繰り返し、CLAUDE.md への記憶、単純な仕様）が、何に置き換わったか
- システムプロンプト、CLAUDE.md、Skill、参照資料のそれぞれに、何を書くべきか
- 自分の指示を整理するための `/doctor`

「コンテキスト」は、モデルが1回の依頼で受け取る情報の全体を指します。自分が打つプロンプトはその一部で、残りは、システムプロンプト、Skill、CLAUDE.md、メモリなどから組み立てられます。この組み立ての設計を、原文は「コンテキストエンジニアリング」と呼んでいます。

原文はゲームに触れていません。ゲーム制作への当てはめは「ゲーム制作での使いどころ」にまとめ、Wiki の考えとして分けて書きます。連載の入口は [Claude Code 公式ブログ](/claude-blog/) です。

原文: [The new rules of context engineering for Claude 5 generation models](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/)

## 問題の置き方: 一般的な指示は書きにくい

原文はまず、プロンプトとコンテキストの違いを述べます。プロンプトは目の前の依頼に合わせて具体的に書けます。コンテキストは、多くの依頼にまたがって使われるので、そこまで具体的にはできません。利用者がどんな依頼を打つか分からないまま、一般的な指針をどう書くか。これが難しい点で、モデルの能力が変わると、さらに難しくなります。

直近で、チームは大きな変化に気づきました。Claude Opus 5 と Claude Fable 5 のようなモデルに対して、Claude Code のシステムプロンプトを80%以上削除しても、コーディングの評価で測れる性能の低下がなかったのです。

## 「縛りすぎ」だった（Unhobbling）

原文の見立てでは、システムプロンプトだけでなく、CLAUDE.md や Skill でも、Claude を縛りすぎていました。

社内で使ったときの記録を読むと、1回の依頼の中に、矛盾する指示が並ぶことがありました。たとえば、システムプロンプトは「ドキュメントは適切に残す」、別の指示は「コメントは書くな」と言う、という具合です。システムプロンプト、Skill、利用者の依頼が、お互いにぶつかっていました。

Claude は、利用者の意図を読み取って、正しい答えにたどり着けます。ただし、重なって衝突する指示がある場合は、どれを優先するかを、より慎重に考えなければなりません。原文の指摘は、過剰な指示が、モデルの考える手間を増やしていたことです。
かつては、最悪の事態を避けるために必要だった制約でも、いまは、周囲の文脈とモデルの判断に任せて削れる、と原文は述べます。

もう1つの背景は、道具が増えたことです。以前の Claude は、CLAUDE.md を、記憶、情報、指針の拠り所にしていました。いまは、メモリ、アーティファクト、Skill があり、セッションをまたいでコンテキストを読み込み、共有する新しい経路をモデル自身が作れます。

## 6つの「かつて」と「いま」

原文は、ベストプラクティスだったものの中に、神話になったものがあると言います。見出しの形で、6つを対にして示しています。

### 1. 規則を与える から 判断に任せる へ

Claude Code の公開当初は、ファイルを消すような最悪の事態を避けたかったので、強い指針をシステムプロンプトに書きました。コードについては、概略次のようなものでした（原文は英語の文をそのまま載せています。ここでは要旨だけ書きます）。

- コメントは原則書かない。
- 複数行のドキュメント文字列や、複数行のコメントブロックは書かない。
- 頼まれない限り、計画書や分析書のような中間の文書は作らない。

しかし、依頼の一部では、この指針は間違いになります。利用者がドキュメントの好みを持っている場合や、非常に複雑なコードの一部に複数行のコメントが必要な場合です。それでも、古いモデルでは、ガードレールがなければコメントが誤りになることが多く、トレードオフを受け入れていました。新しいモデルは判断が良く、明示の規則がなくてもこの種の決定をうまくこなします。

新しいシステムプロンプトで、同じ領域を扱う記述は、要約すると「周囲のコードに合うように書く。コメントの量、命名、言い回しをそろえる」という1行です。規則の列が、「周りに合わせる」という判断の基準に置き換わったことが分かります。

### 2. 例を与える から インターフェースを設計する へ

道具の使い方については、以前は、例を与えるのが第一の規則でした。最新のモデルでは、例が、モデルの探索の範囲を、その例の周りに狭めてしまうと分かりました。

代わりに、道具、スクリプト、ファイルの設計を考えます。モデルに渡す引数は何か、それをもっと表現力のあるものにできないか、という考え方です。原文の例は、ToDo 管理の道具です。状態を、pending、in_progress、completed の3値の列挙にしておくだけで、使い方の見当がつきます。「進行中は1つだけにする」という指示が、望む動きを決めています。
道具の設計は、連載の別の記事（[ツール設計](/claude-blog/tool-design/)）で詳しく扱います。

### 3. 全部を最初に入れる から 必要なときに読ませる（段階的開示）へ

Claude Code は、もともとコーディングに特化していたため、システムプロンプトに、コードレビューや検証のやり方を細かく書いていました。毎回は要らないものの、必要なときには決定的な情報です。

その後、Claude Code は、適切な文脈を適切なときに読み込むのが、とても上手になりました。そこで、検証とコードレビューを、それぞれ独立した Skill に分け、必要なときに呼ぶ形にしました。この段階的開示（progressive disclosure）は Skill に限りません。道具にも使っていて、一部の道具は「遅延読み込み」です。モデルは、使う前に ToolSearch で完全な定義を検索して取り込みます。この仕組みで、必要になるまでコンテキストを占めない道具（Task 系の道具など）を、多く持てます。

CLAUDE.md や Skill のファイルにも同じ考え方を使えます。原文が神話と呼ぶのは、これらを、遭遇しうるあらゆる慣行の中央の置き場にするべきだ、という考えです。「書いておかないと見つけてくれない」という心配が動機ですが、代わりに、適切なときに読み込めるファイルの木を作ることを勧めています。

### 4. 繰り返す から 道具の説明を簡潔にする へ

古いモデルは、指示を繰り返さないと聞かないことがあり、コンテキストの終わりの指示のほうをよく聞く傾向もありました。そのため、システムプロンプトの本文で道具に触れつつ、道具の説明にも指示を書く、という重複がありました。

いまは、この重複を削り、使い方は、システムプロンプトでなく、道具の説明にだけ書けるようになりました。

### 5. CLAUDE.md に記憶を置く から 自動メモリ へ

以前は、`#` のホットキーで、CLAUDE.md に自動で書き込むことを勧めていました。いまは、作業と利用者に関係のある事柄を、Claude が自動で保存します。原文はここまでを述べていて、自動メモリが何を保存するかの詳細は書いていません。

### 6. 単純な仕様 から 豊かな参照資料 へ

計画モード（plan mode）では、計画を Markdown のファイルで保存し、必要なときに参照させていました。長いプロジェクトでも、仕様をコードベースに置いて参照させるのが定石でした。

いまの Claude は、もっと複雑な参照資料も扱えます。

- Markdown の代わりに、アーティファクト機能で作った HTML の成果物を参照できる。
- コードの形の参照もある。仕様が、詳細なテストスイートや、別のコードベースにある、移植したい関数になる場合もある。
- ルーブリック（採点基準）も参照の一種。たとえば「良い API 設計とは何か」のような、自分の好みを書いておくと、動的ワークフロー（[動的ワークフロー](/claude-blog/dynamic-workflows/)）で、そのルーブリックを持った検証役のエージェントを複数起動して、好みに合うかを確かめさせられる。

## 実際の組み立て方: 4つの置き場所

原文は、6つの変化をまとめて、コンテキストの各部分で何をするかを述べます。

| 置き場所 | 役割と書き方（原文） |
|---|---|
| システムプロンプト | 製品の文脈（どの製品の中で、何をしているか）に結びつく。Claude Code では変更しない。自前のエージェントを作るなら、ここに最も時間を使う |
| CLAUDE.md | 軽くする。リポジトリの目的を短く書き、書く量の大半は、コードベース内の落とし穴（gotcha）に使う。ファイル構成を見れば分かる当たり前のことは書かない。検証のやり方のように独自の指示が複数あるなら、検証の Skill を作って、CLAUDE.md から参照する |
| Skill | 必要なときに情報を見つけるための軽い案内として扱う。大事な領域でなければ縛らない。長い Skill はファイルに分割する。自分、チーム、製品に固有の意見、知識、ベストプラクティスを書くと効く |
| 参照資料 | `@` でファイルを指定して取り込む。仕様、モック、コードベース全体でもよい。コードで書かれた資料が、モデルがよく知る言語で明確かつ精密な指示になるので好ましい |

落とし穴の例として原文は、型定義を1つの大きなファイルにだけ置く構成を挙げています。これは、ファイル構成を見ても分からない、そのリポジトリ特有の決まりです。

参照資料の例として、原文は、デザインの HTML モックが、文章による説明やスクリーンショットよりも、一般に良い結果を生むと書いています。

## 自分の指示を軽くする: `/doctor`

最後に、システムプロンプト、Skill、CLAUDE.md を、チームがやったように簡素にする試みを勧めています。これを自動で助けるのが新しいコマンド `claude doctor` で、Claude Code の中では `/doctor` です。上の考え方が、そこに組み込まれていると原文は述べます。より詳しい、新世代モデルへのプロンプトの書き方は、原文が言及する「Fable フィールドガイド」にあるとのことです。

## ゲーム制作での使いどころ

ここからは Wiki の考えです。原文は、ゲームには触れていません。

### 指示ファイルを削る

[指示ファイルの書き方](/agent-dev/project-instructions/) の長さの目安に照らして、半年前の書き方で足し続けた CLAUDE.md を見直します。原文の基準を当てはめると、残すかどうかは次のように判断できます。

| 書いてある内容 | 判断 |
|---|---|
| 「コメントは書くな」「TypeScript を使え」 | ファイルを見れば分かる。削る |
| 「`src/` に scenes、systems がある」 | 構成を見れば分かる。削る |
| 「ヒットストップは敵と自機の両方を止める」 | そのゲーム固有の決まり。残す |
| 「`.tscn` は手で編集しない。必ずエディタで」 | 落とし穴。残す |
| 「ダメージ計算は `damage.ts` の1か所だけ。他に書かない」 | 落とし穴。残す |
| 検証の手順が20行ある | Skill に分け、CLAUDE.md には1行だけ置く |

書き終えたら、`/doctor` で、見直しを助けてもらえます。

```markdown
# CLAUDE.md（ゲームの例。推測の書き方）
横スクロールのアクション。Phaser + TypeScript。
## 落とし穴
- ダメージ計算は `src/systems/damage.ts` のみ。値は `data/balance.json` から読む。
- ヒットストップは、敵と自機の両方を止める（片方だけだと手触りが崩れる）。
## 検証
- 変更したら `/verify` Skill を使う。
```

[コンテキスト管理](/agent-dev/context-management/) にある進捗ファイルのように、長い情報を別のファイルに分けて、必要なときだけ読ませるのが、原文の言う木構造にあたります。

### 参照資料をコードで渡す

- HUD やメニューの画面は、文章の説明よりも、HTML で作った静的なモックを渡すという手があります（原文のデザインの例を、ゲームの画面に当てはめた推測です）。
- ダメージ式やドロップ率のような数値のルールは、文章でなく、期待値を並べたテストにして渡します。テストが仕様になり、AIは、通るまで直せます（[バランス調整](/design/balancing/)）。
- 手触りの好みは、ルーブリックにして、検証役に渡す手があります。原文は、ルーブリックと検証役の組み合わせに触れていますが、ゲームの話はありません。批評役の使い方は [検証ループ](/agent-dev/verification-loop/) の「批評役のループ」にあります。

### 道具の設計で例を減らす

検証用の口（ゲームの状態を読み、操作を送る関数）を作るときは、使い方の例を並べるより、引数の名前と型で意図が伝わるように設計します。原文の ToDo の例が示すように、状態を列挙型にするだけで、使い方の見当がつきます。

## AIの活用ポイント

自分の CLAUDE.md を、AIに点検させるプロンプトの例です。

```text
CLAUDE.md を読み、次の基準で各行に「残す / 削る / Skill に移す」を付けてください。
- ファイルを見れば分かること → 削る
- このゲーム固有の決まりや落とし穴 → 残す
- 手順が複数行に及ぶ → Skill に移し、CLAUDE.md には参照を1行だけ残す
- 互いに矛盾する指示があれば、組で指摘する
結果は表にし、削る理由を1行で書いてください。
```

古い禁止事項を削ったあと、同じ依頼を前後で試して、出力が変わらないか確かめます。原文は、チームのやり方として評価で測っていますが、個人の制作では、よく頼む作業を3つ決め、削る前後で結果を見比べる方法が使えます（推測です）。

画面の参照を、HTML のモックにしてもらう使い方もあります。

```text
タイトル画面の説明を読み、1枚の HTML（CSS 込み、画像は使わない）でモックを作ってください。
解像度は 1280x720、ボタンは3つ、フォーカス時の表示も含めてください。
このモックは、実装時の参照として使います。
```
