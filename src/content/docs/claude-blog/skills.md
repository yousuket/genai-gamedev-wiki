## 概要

Claude Code の公式ブログの1本、Thariq Shihipar 氏による「Lessons from building Claude Code: How we use skills」を、1本だけ取り上げて掘り下げます。原文は2026年6月3日公開、読了時間は11分です。Anthropic 社内で、数百の Skill を使ってきた経験をまとめた記事です。
この記事で分かるのは、次の5点です。

- Skill が「Markdown ファイル」ではなく「フォルダ」だという見方
- 社内の Skill が分かれた9種類と、それぞれの例
- 作るときのコツ（当たり前を書かない、落とし穴の節、段階的開示、縛りすぎない、description の書き方ほか）
- 配り方（リポジトリに置く、プラグインの市場で配る）、組み合わせ方、使われ方の測り方
- 検証用 Skill が最も効果的だったという報告

Skill は、Claude Code が必要なときに読み込む、手順や知識のまとまりです。原文はゲームに触れていません。ゲーム制作への当てはめは「ゲーム制作での使いどころ」で、Wiki の考えとして分けて書きます。連載の入口は [Claude Code 公式ブログ](/claude-blog/) です。

原文: [Lessons from building Claude Code: How we use skills](https://claude.dev/blog/lessons-from-building-claude-code-how-we-use-skills/)

## Skill とは何か

原文の定義は、エージェントが見つけて使い、仕事をより正確に、より効率よくこなすための、指示、スクリプト、資料のフォルダです。よくある誤解は「ただの Markdown ファイル」というものです。実際には、スクリプト、素材、データなどを含められ、エージェントはそれらを見つけ、調べ、操作できます。Claude Code の Skill には、動的なフックの登録を含む、さまざまな設定項目もあります。

原文によれば、最も効果的な Skill は、この設定項目とフォルダ構造をうまく使っています。以降の内容は、すべてこの前提の上にあります。

## 9つの種類

社内の Skill を全部洗い出すと、9つの群にまとまりました。原文の主張は、よい Skill は1つの種類にきれいに収まり、欲張った Skill は複数にまたがってエージェントを迷わせる、というものです。この9種は決定版ではなく、自分の Skill 群に足りない種類を見つけるための枠組みだと位置づけられています。

| 種類 | 何をするか | 原文の例 |
|---|---|---|
| 1. ライブラリ・API の参照 | ライブラリ、CLI、SDK の正しい使い方。参照コードの断片と、避ける落とし穴の一覧を含むことが多い | 社内の課金ライブラリの落とし穴、社内 CLI の全サブコマンドと使いどころ、外向きの通信の出口の設定 |
| 2. 製品の検証 | コードが動いているかを試す、確かめる。playwright や tmux などの外部ツールと組み合わせる | 登録からメール確認、導入までを、ヘッドレスのブラウザで通す、決済の画面をテスト用カードで通して請求が正しい状態になるか確かめる、端末が必要な対話型 CLI の検証 |
| 3. データの取得と分析 | データや監視の基盤につなぐ。認証つきの取得ライブラリ、ダッシュボードの ID、よくある手順を含む | 登録から課金までの漏斗に必要なイベントの結合の仕方、2つのコホートの定着率の比較、監視基盤のデータソースの一覧 |
| 4. 業務とチームの自動化 | 繰り返しの手順を、1つのコマンドにする。結果をログに残すと、一貫性が保たれ、過去の実行を振り返れる | チケット、GitHub、Slack の履歴を集めた朝会の投稿、スキーマに沿ったチケット作成、週次のまとめ |
| 5. 雛形の生成 | 特定の機能の定型コードを作る。コードだけでは表せない自然言語の要件があるときに有効 | 新しいワークフローの雛形、移行ファイルの雛形と落とし穴、認証とログと配備の設定を組み込んだ新規アプリ |
| 6. コードの品質とレビュー | 組織内の品質を保ち、レビューを助ける。決まったスクリプトを入れて堅くできる。フックや GitHub Action から自動で呼ぶ手もある | 新しい目のサブエージェントに批評させ、指摘が些細になるまで直す、Claude が苦手な書式の強制、テストの書き方 |
| 7. CI/CD と配備 | コードの取得、反映、配備 | PR を見守り、不安定な CI を再実行し、競合を解き、自動マージを有効にする、段階的な配備と、悪化時の自動ロールバック |
| 8. 手順書（runbook） | 症状（スレッド、アラート、エラーの型）から、複数のツールをまたぐ調査を通し、構造化した報告を出す | 症状から調べる道具と検索の型を引く、アラートの取得と定番の確認、リクエストIDで、関連する全システムのログを集める |
| 9. インフラの運用 | 定期的な保守。破壊的な操作を含み、ガードレールが効く | 孤立したリソースを見つけ、通知し、猶予期間と確認を経て消す、依存関係の承認手順、費用の急増の原因調査 |

## 作るときの9つのコツ

種類を決めたあと、どう書くかです。原文の見出しの順に整理します。

### 1. 当たり前のことを書かない

Claude は、コードの書き方をすでに知っていて、コードベースも読めます。普段どおりにやることを繰り返す Skill は、コンテキストを使うだけで価値を足しません。知識中心の Skill では、Claude を普段の考え方から外へ押し出す情報に絞ります。

原文の好例は、フロントエンドのデザイン用 Skill です。社内のエンジニアが、利用者と一緒に Claude のデザインの好みを直す過程で作りました。Inter フォントや紫のグラデーションといった、ありがちなパターンを避けさせるものです。

### 2. 落とし穴（Gotchas）の節を育てる

どの Skill でも、最も情報密度が高いのは、落とし穴の節です。Claude がその Skill を使うときに、よく失敗する点から積み上げます。理想は、Skill を更新しながら、落とし穴を取り込み続けることです。原文の例は次の3つで、いずれも、コードを読んでも分からない事実です。

- ある表は追記専用で、欲しい行は、作成日時が最新のものではなく、版番号が最大のもの。
- ある項目は、API ゲートウェイでは `@request_id`、課金サービスでは `trace_id` と呼ぶが、同じ値。
- ステージング環境は、Stripe の Webhook が処理されなくても200を返す。本当の状態は、別の表で確認する。

### 3. ファイルシステムと段階的開示を使う

Skill はフォルダで、ファイルシステム全体が、コンテキストの設計であり、段階的開示の道具だと考えます。Skill に含まれるファイルを Claude に教えておくと、適切なときに読んでくれます。

最も簡単なのは、別の Markdown ファイルを指す方法です。関数の細かい署名や使用例は `references/api.md` に分ける、出力が Markdown ならひな形を `assets/` に置いてコピーさせる、といった具合です。原文の図では、SKILL.md が、状況ごとに別のファイルを指しています（たとえば、ジョブが滞留しているときは `stuck-jobs.md` を見る）。参照、スクリプト、例のフォルダを置くことで、Claude が効率よく動けます。

### 4. Claude を型にはめすぎない

Skill は繰り返し使うので、指示が具体的になりがちです。Claude は指示に忠実に従うため、やりすぎると、状況に合わせた対応ができなくなります。必要な情報は渡し、適応する余地を残します。原文の図の標語は、「手順を全部書かず、目標と制約を書く」です。

### 5. 初期設定を考える

利用者の文脈が必要な Skill があります。たとえば、朝会の投稿を Slack に出す Skill は、どのチャンネルかを聞く必要があります。

型としては、設定を、Skill のフォルダの `config.json` に保存します。設定がなければ、エージェントが利用者に聞きます（原文の図は、チャンネルの設定がなければ尋ねる書き方）。選択式の質問にしたいなら、AskUserQuestion ツールを使うように指示します。

### 6. description は、人向けでなくモデル向けに書く

セッションを始めるとき、Claude Code は、使える Skill すべての description の一覧を作ります。Claude は、この一覧を見て、「この依頼に合う Skill はあるか」を決めます。したがって、description は、要約ではなく、いつ発動するかの記述です。原文の図では、「babysit」のような発動の合図の言葉を、description に入れるとよい、としています。

### 7. 記憶を持たせる

Skill の中にデータを保存して、記憶にできます。追記専用のテキストログ、JSON、あるいは SQLite データベースまで、形は問いません。たとえば、朝会の投稿の Skill が、投稿のたびに `standups.log` に書き残せば、次回は、Claude が自分の履歴を読み、昨日からの変化を言えます。

保存先は、環境変数 `${CLAUDE_PLUGIN_DATA}` で、安定したディレクトリを得られます。詳細は、原文が指す Claude Code ドキュメントの「persistent data directory」の項にあります。

### 8. スクリプトを入れ、コードを生成させる

Claude に渡せる最も強力な道具の1つはコードです。スクリプトやライブラリがあれば、Claude は、定型の記述の再構築ではなく、何をするかの組み立てに、手数を使えます。たとえば、データ分析の Skill に、イベント元からデータを取る関数群を入れておきます。Claude は、「火曜に何があった？」のような依頼に対し、その場でヘルパーを組み合わせた使い捨てのスクリプトを書いて、より進んだ分析をします。原文の図では、落とし穴を、関数のドキュメント文字列に書き込んだ小さなライブラリを渡しています。

### 9. 必要なときだけ効くフックを使う

Skill は、呼ばれたときだけ有効になり、セッションの間だけ続くフックを持てます。常時は要らないが、時々、非常に役に立つ、こだわりの強いフックに向いています。原文の例は2つです。

- `/careful`: `rm -rf`、`DROP TABLE`、強制プッシュ、`kubectl delete` を、PreToolUse のマッチャーで、Bash に対して止める。本番を触るときだけ使う。常時だとうんざりする。
- `/freeze`: 特定のディレクトリ以外への Edit と Write を止める。デバッグ中に、ログを足したいだけなのに、無関係なコードを「直して」しまう事故を避ける。

### 結び: 書き足しながら育てる

9つの見出しとは別に、原文の結びが述べていることです。最良の Skill の多くは、数行と1つの落とし穴から始まり、Claude が新しい端のケースに当たるたびに、人が書き足して良くなりました。ベストプラクティスはまだ進化中で、始めて、試して、何が効くかを見るのが近道だと述べられています。

## 配り方、組み合わせ、測り方

### 配る

方法は2つです。リポジトリの `./.claude/skills` に入れる方法と、プラグインを作り、Claude Code のプラグイン市場（マーケットプレイス）で、利用者が投稿、取り込みできるようにする方法です。

原文の判断基準は規模です。少人数で、リポジトリが少ないなら、リポジトリに入れる形で十分です。ただし、入れた Skill は、そのぶんモデルのコンテキストを少し使います。規模が大きくなったら、社内のプラグイン市場で、各人が入れる Skill を選べるようにし、初期設定の流れも付けられます。

### 市場の運営

Anthropic には、採用を決める中央のチームがありません。役に立つものを、自然に見つけます。試してほしい人は、GitHub の砂場のフォルダにアップロードして、Slack などで周知します。反響が出たら（その判断は持ち主）、PR を出して市場に移します。

### 組み合わせ

Skill 同士に依存関係を持たせたい場合（ファイルをアップロードする Skill と、CSV を作ってアップロードする Skill など）、市場や Skill には、依存の管理がまだ組み込まれていません。ただし、名前で他の Skill を参照すれば、入っているときにモデルが呼び出します。

### 測る

社内では、PreToolUse のフックで、Skill の使用をログに残しています。人気のある Skill、期待より発動が少ない Skill（description の見直し候補）が見つかります。

## ゲーム制作での使いどころ

ここからは Wiki の考えです。原文はゲームには触れていません。

### まず作るのは検証用 Skill

原文で、製品の検証用 Skill が、出力の質に最も大きな影響を与えたとされています。ゲームでも、最初の1つはこれが妥当です。原文が挙げる、動画の記録や、状態への表明（アサーション）を、ゲームに置き換えると、次の構成です。

```text
.claude/skills/verify-game/
  SKILL.md           # いつ使うか、手順、報告の形式
  scripts/
    run-bot.mjs      # 固定 seed でボットを60秒動かし、状態を JSON で出す
    shoot.mjs        # Playwright で起動し、場面ごとに shots/ へスクリーンショット
  references/
    gotchas.md       # このゲームの落とし穴
  config.json        # 起動のポート、画面サイズ
```

仕組みは [検証ループ](/agent-dev/verification-loop/) にあります。Skill にまとめると、毎回の指示が短くなり、手順が揺れません。

### 9種類をゲームに置き換える（推測）

| 原文の種類 | ゲームでの例 |
|---|---|
| ライブラリ・API の参照 | 使うエンジンやライブラリの、はまりどころの一覧（Phaser のシーン遷移など） |
| 製品の検証 | 上の verify-game |
| 雛形の生成 | 新しい敵、アイテム、ステージを、データと実装と検証の3点セットで追加する |
| コードの品質とレビュー | 別のコンテキストで遊び心地を採点させる批評役 |
| 手順書 | 「フレームレートが落ちた」から、計測、原因の切り分けまでを順にたどる |
| 業務の自動化 | リリース前の確認（ビルド、容量、公開用ページの確認） |
| インフラの運用 | 生成した素材の孤立ファイルの整理（消す前に一覧を見せ、確認を取る） |

データ取得や CI/CD の種類は、小さな個人制作では、必要になってから考えれば足ります。

### 落とし穴の節は、失敗の2回目で書く

同じ失敗を2回見たら、落とし穴に1行足します。例は次のようなものです（推測の書き方です）。

```markdown
## Gotchas
- ヒットストップ中は `dt` が0になる。タイマーを `dt` で進めるとフリーズする。実時間の `realDt` を使う。
- `shots/` の画像は、ゲーム起動直後ではなく、タイトル画面のアニメが終わる2秒後に撮る。
```

指示ファイルの育て方（[指示ファイル](/agent-dev/project-instructions/)）と、同じ運用です。短く始めて、失敗のたびに足すという原文の結びは、個人制作に向いています。

### 配り方は、リポジトリで足りる

一人で作るなら、`.claude/skills` に置けば足ります。マーケットプレイスは、人数が増えてから考えます。置いた Skill は、そのぶんコンテキストを使うので、使わなくなった Skill は消します（[コンテキスト管理](/agent-dev/context-management/)）。

### 必要なときだけ効くフック

原文の `/careful` と `/freeze` の考え方は、ゲーム制作にも使えます。

- 素材のフォルダを整理する前だけ、`rm -rf` と `git clean` を止める。
- 敵のバランス調整の間だけ、`data/enemies.json` 以外の編集を止める。

常時だと邪魔になるので、必要なときだけ、というのが原文の趣旨です。

## AIの活用ポイント

Skill の下書きは、AIに作らせ、人は落とし穴の節だけを育てるのが、現実的な分担です。

```text
このリポジトリの検証用 Skill（.claude/skills/verify-game/）の SKILL.md を作ってください。
- description は、発動の条件を書く。「検証」「確認して」「動作チェック」などの言葉を含める。
- 手順は、目標と制約だけを書き、1コマンドずつは書かない。
- 詳細は references/ に分け、SKILL.md から指す。
- Gotchas の節は空の見出しだけ作る。私が失敗のたびに足す。
```

失敗が起きたら、AIに、落とし穴の候補を出させます。

```text
今回の失敗（タイマーがフリーズした）の原因を、1〜2行の落とし穴として書いてください。
コードを読めば分かる一般論は書かず、このプロジェクト特有の事実だけにしてください。
```

description の見直しにも使えます。

```text
次の Skill の description を、「いつ発動するか」の書き方に直してください。
発動してほしい依頼の言い回しを5つ挙げ、それが含まれるようにしてください。
```
