## 概要

この記事は、Claude Code 公式ブログ（claude.dev）の「What a task costs on Opus 5.5」を、読まなくても使えるところまで掘り下げたものです。連載の入口は [Claude Code 公式ブログの連載](/claude-blog/) です。

- 原文: [What a task costs on Opus 5.5](https://claude.dev/blog/what-a-task-costs-on-opus-5-5/)
- 公開日: 2026年9月25日。著者: Addy Osmani 氏。読了時間: 21分（原文の表示）
- 扱う内容: Claude Code のタスク1件の費用が何で決まるか、Opus 5.5 で何が変わったか、effort・モデル・キャッシュ・圧縮をどう使うと費用が下がるか、自分の費用をどう測るか

原文はトークン単価の話だけではありません。「同じ単価でも、タスク1件の費用は大きく違う」が主題です。リトライ（やり直し）1回が、節約したトークンより高くつく、という考え方で全体が組まれています。
原文の数字には、API の定価をそのまま使ったものと、定価から作った説明用の例（イラストレーション）があります。原文もそう断っており、この記事でも、どちらの数字かを区別して書きます。

料金の全体表やサブスクリプションの枠、並列エージェントの費用は [コストと利用枠の管理](/agent-dev/cost-management/) にまとめています。この記事は、そこにない「1タスクの費用の分解」「effort とモデルの使い分けの根拠」「キャッシュを壊す操作」を補います。

## 費用は、トークン単価ではなくタスクで決まる

原文は、冒頭でこう整理します。人が欲しいのは機能の完成や移行の完了であり、トークンの数は、そこに着くためにモデルが必要とした量にすぎません。

同じ単価のモデル2つでも、片方はコードを1回読んで直し、もう片方は読んで、直しを試して、また読みます。この1歩ずつが「ターン」で、ターンごとに、それまでの会話が全部送り直されます。ターンが多いモデルは、同じ単価でも高くつきます。

この記事のもう1つの前提が、トレードオフです。effort を下げる、小さいモデルを使う、コンテキストを減らす。どれもトークンは減らせますが、タスクが終わらなければ、リトライの費用が節約分を上回ります。原文は、この各選択に値段を付けるのが狙いだと書いています。

## タスク1件の費用を決める4つの要素

Claude Code のタスクは、ループです。モデルが会話を読み、ツールを呼び、結果を読み、また回ります。1周が1リクエストです。原文は、ループの費用を決めるものを4つ挙げます。

| 要素 | 内容 |
|---|---|
| ターン数 | 毎ターン、会話全体が再送される。ターンが減れば、処理する入力が減る |
| キャッシュ読み出し | 再送する内容の大半は前のターンと同じ文章で、入力単価のごく一部で課金される |
| 出力トークン | 入力の5倍の単価。思考（thinking）も出力として課金される |
| モデル | モデルごとに単価が決まり、全トークンの値段を決める |

以降の例は、Opus 5.5 の API 定価で計算されています。100万トークンあたり、入力が4ドル、出力が20ドル、キャッシュ読み出しが0.20ドルです（2026年10月時点。出典: [Pricing](https://platform.claude.com/docs/en/about-claude/pricing)）。キャッシュ読み出しは入力単価の5%（0.05倍）と、公式の料金ページにも書かれています。例では、キャッシュ済みの入力を読み出し単価、それ以外を入力単価で課金し、キャッシュ書き込みは省いています。トークン数は説明用の仮の値です。

### ターン数

例の条件はこうです。タスクの開始時に20K（2万）トークンのコンテキストがあり、ファイルやツール結果を読むうちに120Kまで増えます。40ターンかかると、1ターンあたりの平均は約70Kを送ります。

- 40ターン: 入力の総量は約2.8M（280万）トークン。会話の大きさは120Kを超えないのに、送った総量はこうなります。9割がキャッシュ読み出しなら、入力の費用は約1.62ドル
- 25ターン: 同じタスクで、入力の総量は約1.75M、入力の費用は約1.02ドル

1ターンは、足したトークンより高くつきます。それまでの全部を送り直すからです。原文の結論は、「いちばん安いターンは、要らないターン」です。

ターンを減らす習慣として、原文は2つ挙げます。1つは、モデルが自分の作業を確かめる手段（テスト、ビルド、エンドポイントを叩くスクリプト）を与えること。確かめられるモデルは、間違いを早く見つけます。もう1つは、必要な情報を1回で集め、ツール呼び出しをまとめるモデルは、再送の支払いも少なくなる、という点です。

### キャッシュ読み出し

同じ2.8Mの入力でも、キャッシュがまったく効かなければ11.20ドル、ヒット率90%なら1.62ドル、96%なら約0.99ドルです。原文は、入力の費用をこれほど動かす設定は他にない、と書いています。安定したセッションは、ヒット率が自然に高く保たれます。壊れる場面は、後ろの節にまとめて書きます。

### 出力トークン

Opus 5.5 では、出力1トークンの値段は、キャッシュ読み出しの100倍です。典型的なタスクの出力60Kトークンは1.20ドルで、これはキャッシュから6M（600万）トークンを読むのと同額です。出力には思考が含まれ、Claude Code が要約しか見せなくても、思考の全部に課金されます。effort が費用を大きく動かすのは、effort が主に思考の量を変えるからです。

### モデル

原文の整理は短いものです。キャッシュ読み出しが安いモデルは長いセッションに効き、出力が安いモデルは、推論の多いタスクに効きます。

## Opus 5.5 で何が変わったか

変わったのは、単価と、モデルがする仕事の量の2つです。

### 単価

下の表は、原文の図の数字です（API 定価、100万トークンあたり、2026年10月時点）。

| | Opus 5 | Opus 5.5 | 下がった割合 |
|---|---|---|---|
| 入力 | 5ドル | 4ドル | 20% |
| 出力 | 25ドル | 20ドル | 20% |
| キャッシュ読み出し | 0.50ドル | 0.20ドル | 60% |

キャッシュ読み出しの単価は、入力単価の10分の1から20分の1に下がりました。長い自律セッションは、入力の大半がキャッシュ読み出しなので、この値下げが効きます。原文の例では、1セッションの明細で、キャッシュの行が1.00ドルから0.40ドルに下がり、明細でいちばん大きな減少です。

サブスクリプション（Pro、Max、Team）では、Opus 5.5 の安い単価が、キャッシュ済みコンテキストも含めて利用枠に反映され、枠はOpus 5より約25%長持ちする、と原文は書いています。キャッシュ読み出しの追加の値下げは、API の価格だけの変更です。別件として、Pro、Max、Team、席課金の Enterprise で5時間の枠が増え、対象の購読者には、好きなときに使える枠のリセットが付きます。設定は、ウェブか Claude Desktop の Settings > Usage にあり、ターミナルの Claude Code にはありません。リセットはアカウント全体に効きます。

どれだけ安くなるかは、作業の形で決まります。ほぼキャッシュ読み出しのセッションなら、入力で最大60%安くなります。キャッシュなしで長い答えを書く短い質問は、出力が支配するので最大20%です。Claude Code のタスクの大半は、その間にあります。

### 「40%安い」の意味

原文は、「Opus 5.5 は Opus 5 より40%安く動く」という話を見かけたかもしれない、と断った上で説明します。これは、標準設定でトークン課金される典型的な作業負荷についての、Anthropic の見積もりです。Opus 5.5 は標準の medium で、タスクあたりのトークンも少ない、という前提が入っています。つまり、トークン単価が40%下がったという意味ではありません。単価の変更だけの効果は、次の図 B が示します。

### モデルの仕事の量

Opus 5.5 は、返答の前に必ず考えるので、1回の答えで使うトークンが増えることがあります。原文は、Opus 5.5 でより多くを終わらせられると期待しているが、タスクによるので、自分の作業で測ってほしい、としています。

- 範囲のはっきりしたタスクでは、両モデルのターン数はほぼ同じで、効果は値下げ分だけ
- 差が最も開くのは、範囲の曖昧なタスク。間違った案に何ターンも使う余地があるからです
- 長い作業の終わりに、Opus 5.5 は、変更したこと、見つけたこと、人に必要なことを報告します。何が起きたか分かれば、セッションを再実行する回数が減り、それも費用の節約になる、と原文は書いています

## 同じトークンで比べる（図 B と図 C）

図 B は、1セッションを、同じトークン数で2つのモデルに当てはめた明細です。違いは単価だけです。トークン数は説明用です。

| 行 | トークン | Opus 5 | Opus 5.5 |
|---|---|---|---|
| キャッシュ読み出し | 2.0M | 1.00ドル | 0.40ドル |
| 新規の入力 | 200K | 1.00ドル | 0.80ドル |
| 出力 | 60K | 1.50ドル | 1.20ドル |
| 合計 | | 3.50ドル | 2.40ドル（約31%減） |

Opus 5.5 の列の数字は、原文の単価（上の表）から、このWikiが計算したものです。合計の3.50ドルと2.40ドル、約31%減は、原文にあります。
明細の3行は、`/usage` が出す3行と同じです。トークン数でいちばん大きいのはキャッシュ読み出し、いちばん小さいのは出力ですが、費用でいちばん大きいのは出力です。新規の入力は、各ファイルの最初の読み込みと、新しいツール結果です。

図 C は計算機で、入力トークン、キャッシュの割合、出力、1日のタスク数を動かせます。月は22営業日で計算し、API 定価、キャッシュ書き込みは含まず、バッチや大口の割引もありません。サブスクリプションでは請求額ではありません。計算機の初期値は、入力2.2M、キャッシュ91%、出力60K、1日10件で、Opus 5 は月770ドル、Opus 5.5 は月528ドル（約31%減、月242ドル減）です。

原文の3つのプリセットの値は次のとおりです（原文のページに埋め込まれた値）。右の2列は、この値と上の単価から、このWikiが計算した1タスクあたりの費用です。

| プリセット | 入力 | キャッシュ | 出力 | 1日の件数 | Opus 5 | Opus 5.5 |
|---|---|---|---|---|---|---|
| 小さな修正 | 150K | 80% | 5K | 30 | 約0.34ドル | 約0.24ドル（約27%減） |
| 大きなリファクタリング | 6M | 92% | 250K | 3 | 約11.4ドル | 約8.0ドル（約30%減） |
| 長い自律実行 | 20M | 96% | 600K | 1 | 約28.6ドル | 約19.0ドル（約33%減） |

キャッシュの割合が高く、1回が長いほど、値下げの効果が大きく出ています。計算機のスライダーのうち、最後の1つは「Opus 5.5 で、タスクあたりのトークンが何%増減するか」の自分の仮定です。単価だけの効果を見るなら0%のままにします。実際の値を決めるには、同じタスクを Opus 5 と Opus 5.5 で1回ずつ走らせ、ターン数と出力トークンを比べます。

## 費用を下げる手順

原文の中心です。単価は下がりましたが、トークンの使い方で費用は決まります。

### 1. モデルを変える前に、effort を上げる

effort は、1ターンごとにモデルが使うトークン（思考、書く文章、ツール呼び出し）の総量の構えを決めます。低いと、ツール呼び出しは少なく短くなります。Opus 5.5 には low、medium、high、xhigh の4段階と、1セッションだけ使える max があります。

| 水準 | 使いどころ（原文） |
|---|---|
| low | 機械的な作業。名前の変更、既知のパターンを複数ファイルに適用 |
| medium | 範囲のはっきりした日々の作業。ここから始める |
| high | medium で詰まったとき。モデルを上げるより安い |
| xhigh | 難しい問題 |
| max | 1セッションだけ |

設定は `/effort medium` のように書き、現在の値は `/effort status` で見ます。タスクの途中で変えられ、次のリクエストから効きます。

注意点が2つあります。まず、Opus 5.5 の既定は medium で、Opus 5 の既定（high）より1段階低いこと。同じ水準名でも、Opus 5.5 は Opus 5 より1ターンで多く考えます（特に xhigh と max）。Opus 5 で選んだ水準を持ち越さず、medium から始め、xhigh と max は、効果を測れた作業にだけ使う、と原文は言います。

次に、effort の変更とキャッシュの関係です。Opus 5.5 を API キーか Claude のサブスクリプションで使う場合、effort を変えてもキャッシュは保たれます。難しい1手だけ上げて、また下げることができます。Amazon Bedrock、Google Cloud の Agent Platform、Claude apps のゲートウェイでは、変更でキャッシュした会話が消え、次のリクエストで全体にキャッシュ書き込みの単価がかかります。Opus 5.5 は思考が常にオンなので、思考の設定はありません。

#### effort の元が取れる計算

原文の概算です。high が、タスク全体で思考を2万トークン余計に使うとします。Opus 5.5 では0.40ドルです。10ターンのリトライのループ（キャッシュ済みコンテキスト100K、出力は合計10K）も、約0.40ドルです。つまり high は、リトライを1回減らせるタスクなら元が取れ、medium で最初から終わるタスクには無駄です。

#### medium が1層だけ直す例

effort を上げるべきサインとして、原文は「直しが1つの層で止まる」を挙げます。API ハンドラーのフィールド名を変える場面です。medium では、ハンドラーを直し、ハンドラーのテストは通りますが、クライアントは古いフィールド名を送ったままです。頼まれたことはしたのですが、2つ目の呼び出し元を見つけるところまで読んでいません。high は、書く前に呼び出し元を読むターンが増え、2層を1回で直します。

同じバグは、チェックでも捕まります。クライアントを通るテストを実行できれば、古いフィールド名は、medium でも書いたターンに失敗します。そこで、effort を上げる前に、モデルが確かめる手段を持っているかを確認します。テスト1回の費用は、1ターンと出力です。effort を上げると、全ターンに思考が足されます。effort とチェックの両方を試して駄目なら、大きいモデルに切り替えます。

### 2. 仕事に合うモデルを選ぶ

モデルは全トークンの単価を決めるので、effort より費用を大きく動かします。サブエージェントがメインのモデルを引き継ぐと、単価も引き継ぎます。原文は、ふだんの作業に3つのモデルを使い分けることを勧めます。調べもの用の小さいモデル、人が見ている作業用の Opus 5.5、最も難しい作業用の大きいモデルです。

- Opus 5.5 を日常の主力にする: 数ファイルにわたる機能、デバッグ、レビューの後の修正。人が読んで、ずれたら介入する、短いループの作業
- Fable 5.1 に上げる: 結果が単価より重要なとき。人が見ない長時間の実行、コードベースに前例のない問題、多数のサブエージェントを調整する大きな変更。原文は、3回失敗するのを待たず、xhigh の Opus 5.5 で同じ問題に2回ぶつかったら切り替え、解けたら戻す、としています。対話的な作業には、遅延が低く安い Opus 5.5 が向きます
- 調べもの用に下げる: 小さいモデル（Sonnet か Haiku）は、検索と要約をするサブエージェント、ログとテスト出力の読み取り、「これはどこで定義されているか」の質問に使います。コードを書く作業には使いません。多数のファイルへの機械的な編集は、Opus 5.5 のまま effort を low にします

Fable 5.1 の定価は、入力10ドル、出力50ドルで、Opus 5.5 の2.5倍です。キャッシュ読み出しは0.25ドルで、Opus 5.5 の1.25倍にとどまります（入力単価の0.025倍で課金されるため）。差が最も小さいのは、キャッシュ中心の長い実行で、最も大きいのは、たくさん書くタスクです（以上、2026年10月時点）。

切り替えは、区切りのよいところで行います。キャッシュは前のモデルのものなので、新しいモデルの最初のターンは、会話全体にキャッシュ書き込みの単価を払います。先に `/compact` するか、短い計画を書いて新しいセッションを始めると、その1ターンが小さくなります。`/model` に別名かモデル名を渡して切り替えます。`/model` は選んだものを新しいセッションの既定にも保存するので、難所が終わったら戻します。

サブエージェントを小さいモデルにするには、定義に `model: haiku` か `model: sonnet` と書きます。全サブエージェントを1つのモデルにするなら、環境変数 `CLAUDE_CODE_SUBAGENT_MODEL` を使います。定義に書いたモデルは、この変数より優先されます。model の指定がないサブエージェントは、変数がない限りメインのモデルで動きます。サブエージェントは、自分のコンテキストの窓で動き、要約だけを返すので、ファイルの読み込みがメインの会話に入りません。それでも、自分のトークンには課金されます。

エージェントチーム（実験的な機能）は、この費用を倍にします。各メンバーは別々の Claude Code で、終了するまでトークンを使い続けます。原文が引くコスト管理のドキュメントでは、メンバーが計画モードのとき、チームは通常のセッションの約7倍のトークンです。チームは小さく、各タスクは独立させ、終わったメンバーは止めます。

トレードオフもあります。小さいモデルが検索結果を読み違えると、メインが間違ったファイルへ向かい、その回り道の費用をメインが払います。小さいモデルには、間違いが見つけやすい作業（ファイル探し、テスト実行、ログ読み）を任せます。判断はメインのモデルに残します。`opusplan` という別名は、計画を Opus、実行を Sonnet に分ける設定で、コードの編集を Sonnet に置くため、上の勧めと逆です。既定にする前に、自分のタスクで測ります。

### 3. 移行したら、プロンプトを点検する

古いモデル向けの指示は、Opus 5.5 に、書きすぎと同じツール呼び出しの繰り返しをさせることがあります。Claude Code で `/claude-api prompt-audit` を実行すると、スキルや CLAUDE.md が、こうしたアンチパターンを含んでいないかを調べます。Claude Platform で作ったアプリのコードも調べます。

原文は、社内のカスタマーサポート用ベンチマーク（44件のチケット）で試した結果を載せています。プロンプトには、この種のパターンがいくつも入っていました。Opus 4.8 から Opus 5.5（effort は low）への移行で、ベンチマークの費用は約18%減りました。prompt-audit をさらに実行すると、そこから約9%減り、Opus 4.8 の開始時より約25%安くなりました。除かれたのは、6段階の手順の義務づけ、スクラッチパッドの規則、2回確認する規則、互いに矛盾する指示など、書きすぎと繰り返しの原因になる「儀式的な指示」です。
原文は、これは1つのベンチマークの結果で、期待してよい数字ではなく例だと断っています。実行したら、実際のタスクで前後の `/usage` を比べるよう勧めています。

### 4. キャッシュと圧縮

キャッシュも圧縮も Claude Code が自動でやりますが、セッションの進め方が節約量を決めます。

#### キャッシュの仕組み

Claude Code は、リクエストのうち繰り返す部分（システムプロンプト、ツールの定義、ここまでの会話）をキャッシュします。Opus 5.5 のキャッシュ読み出しは、新規入力の5%です。書き込みは、新規入力より高く、5分のキャッシュで入力単価の1.25倍、1時間のキャッシュで2倍です（2026年10月時点。出典: [Pricing](https://platform.claude.com/docs/en/about-claude/pricing)）。ヒットのたびに、寿命は無料でリセットされます。

Claude Code での寿命は、支払いの方法で決まります。Claude のサブスクリプションなら1時間、API キーやクラウドプロバイダーなら既定で5分です。サブスクリプションでも、使用クレジットを使い始めると5分になります。

120Kトークンのコンテキストで、Opus 5.5 の5分キャッシュの書き込みは約0.60ドル、読み出しは約0.02ドルです。書き込み1回は読み出し25回分です。API キーなら、6分のコーヒー休憩で、次の0.02ドルの読み出しが、0.60ドルの書き込みになります。同じ大きさの1時間キャッシュの書き込みは約0.96ドルで、API では、この上乗せを払って1日の空白をカバーできます。

#### キャッシュが書き込みになる場面

キャッシュは「先頭から一致する部分」だけを再利用できます。安定したセッションは、会話の末尾に足していくので、ヒット率が高く保たれます。ツール定義を変えるとキャッシュ全体が消え、システムプロンプトを変えると、そこから後ろ、つまりほぼ全部が消えます。原文が挙げる、書き込みが起きる場面は次のとおりです。

- キャッシュの寿命より長く休んだ
- Bedrock、Google Cloud の Agent Platform、ゲートウェイで effort を変えた（水準がキャッシュの一致条件に含まれる）
- 会話の中で、初めて fast mode をオンにした
- MCP サーバーをつないだ、または外した（各リクエストの先頭に読み込まれる内容が変わりうる）
- モデルを切り替えた（新しいモデルのキャッシュは空）
- 会話を圧縮した（キャッシュが一致していた履歴が書き換わる）

だから、これらはセッションの開始時に決め、作業中は触らないのが原文の勧めです。

#### 長いセッションほど1ターンが高い

毎ターンがコンテキスト全体を送るので、キャッシュが温まっていても、コンテキストが伸びるほど1ターンが高くなります。Opus 5.5 のキャッシュ読み出しは、コンテキスト20Kで1ターン約0.004ドル、150Kで約0.03ドルです。150Kのまま30ターンなら読み出しだけで0.90ドル、20Kのまま30ターンなら約0.12ドルです。Claude 4.6 以降のモデルでは、大きな窓にしてもトークン単価は変わらないので、費用は、会話を送り直すことだけから生まれます。送り直される内容の多くは、1時間前のスタックトレース、終わったファイル、直し終えたテストの出力のような、過去の作業の残りです。

#### 圧縮、`/compact`、`/clear`

コンテキストの上限に近づくと、Claude Code は古い履歴を要約します。`/autocompact` にトークン数を渡すと、どこまで埋まったら圧縮するかを変えられます。自分で使えるコマンドは2つです。

- `/clear`: 会話を空にする。費用はかからない。無関係な作業に移るときに使う
- `/compact`: 連続性を保ち、費用は1リクエスト。要約のために会話を読む。`/compact keep the failing test names and the schema change` のように、残すものを指示できる

150Kトークンでの圧縮の費用は、約0.25ドルと概算されています（読み出し、数千トークンの要約の出力、短くなったコンテキストの新しいキャッシュ書き込み）。その後の各ターンが約0.025ドル安くなるので、約10ターンで元が取れます。終わる直前の圧縮は、節約より高くつきます。

この概算は、キャッシュが温まっていることが条件です。温まっていれば、要約のリクエストは会話をキャッシュから読むので、休憩の前に圧縮します。キャッシュの寿命を超えた休憩の後だと、同じ `/compact` が会話全体をもう一度読み、書き戻します。150Kで5分キャッシュなら、入力だけで約0.75ドルです。捨てたい道に入ったときは、`/rewind` で前のターンに戻ります。キャッシュが温かいうちは、すでにキャッシュにある先頭部分に戻れます。要約は詳細を落とすので、デバッグの途中の圧縮が、肝心のログ1行を落とすこともあります。区切りのよいところで圧縮し、次の手が特定の情報に依存するなら、`/compact` の指示に書きます。

#### 入力する前に読み込まれるもの

CLAUDE.md は、毎セッションの開始時にコンテキストに入るので、その1行1行が毎ターンの再送に含まれます。コスト管理のドキュメントは、200行未満を勧めています。MCP のツール定義は遅延読み込みで、開始時に入るのはツール名とサーバーの指示だけです。完全な定義は、使うときに読み込まれます。`/mcp` で、つながっているサーバーを確認し、使っていないものはオフにします。指示ファイルの書き方は [プロジェクト指示ファイルの書き方](/agent-dev/project-instructions/) にあります。

### 5. 請求に効くそのほかの規則

原文の表を、言い換えてまとめます。

| 項目 | 内容 |
|---|---|
| キャッシュの寿命 | 上で説明したとおり。API には、書き込み単価が高い1時間のキャッシュもある |
| キャッシュの書き込み | 5分は入力の1.25倍、1時間は2倍 |
| 思考 | 出力として課金。返ってこない思考も含む |
| effort | 出力の全トークン（文章、ツール呼び出し、思考）に効く |
| 自動圧縮 | 窓が上限に近づくと走る。`/autocompact` で閾値を変える |
| サブエージェントとエージェントチーム | サブエージェントは自分の窓で動き、要約を返す。計画モードのチームは通常の約7倍 |
| Batch API | 入力と出力が半額（非同期。2026年10月時点） |
| 実際の支出 | 企業での平均は、開発者1人、稼働日あたり約13ドル。90%のユーザーは、稼働日あたり30ドル未満（現行のモデルの数字） |

fast mode は、Opus 5.5 が最大2.5倍速くなる代わりに、標準の2倍の単価です（入力8ドル、出力40ドル。2026年10月時点。出典: [Pricing](https://platform.claude.com/docs/en/about-claude/pricing)）。サブスクリプションでは、利用枠ではなく使用クレジットに請求されます。オンにした最初のリクエストは、会話全体を、キャッシュなしの fast mode の入力単価で払います。だから、セッションの途中ではなく、開始時にオンにします。

## 自分の費用を測る

原文は、図の数字は例であって、コードベース、プロンプト、習慣は人ごとに違うので、自分のタスクで測ることを勧めます。方法は次のとおりです。

- セッション中に `/usage` を実行する（`/cost` も同じ）。Session の欄に、トークン使用量と、定価での推定費用が出ます。プロンプトキャッシュの行は、入力のうちキャッシュから来た割合を示します。費用は手元のマシンで定価から計算された値で、サブスクリプションでは請求額ではなく、仕事量の目安です
- 同じタスクを2回走らせる。Opus 5.5 は Claude Code v2.1.280 以降が必要なので、先に `claude update` します。おもちゃの例ではなく、バックログの実際の仕事を選び、`/model` で Opus 5 と Opus 5.5 を切り替えます。ターン数、出力トークン、費用を控え、結論を出す前に3、4個のタスクでやります
- チームなら、使用量と費用のレポートを使う。Claude Code Analytics API はユーザーごとの推定費用、Usage and Cost API はモデル別、キャッシュ別の支出を出します
- effort の階段を試す。難しい1つを medium と high で、機械的な1つを low で走らせます

### セッションの読み方

終わったあとの `/usage` では、3つを見ます。

- キャッシュの割合: 長いセッションなら高いはず。低いなら、長い休憩、モデルの切り替え、途中でつないだ MCP サーバー、クラウドやゲートウェイでの effort の変更を探します。プロンプトキャッシュの行は、直近のミスの原因の見当を示すことが多いです
- 入力に対する出力: 小さな変更に出力が多いなら、effort が高すぎるか、モデルがリトライしています
- 会話の大きさに対する入力の総量: 総量が会話の大きさの何倍もあれば、ターンが多かったということで、会話を読んで、ループが繰り返した箇所を探します

基準は、先の約13ドルと30ドルです。自分のふだんの水準を大きく超えるセッションは、見直す価値があります。

## 原文のまとめ（Keep in mind）

原文の最後の要点を、順に言い換えます。

1. 範囲のはっきりした日々の作業は medium で
2. モデルに確かめる手段を与える。複数ファイルにまたがる変更は、計画モードから始める
3. medium で詰まったら high に。API キーかサブスクリプションならキャッシュは保たれる。クラウドやゲートウェイでは、区切りで変える
4. xhigh で同じ問題に2回ぶつかったら Fable 5.1 に。解けたら戻る
5. 検索とログ読みのサブエージェントは Sonnet か Haiku に。コードの編集は Opus 5.5 に
6. 長いセッションは動かし続け、キャッシュを温めておく
7. 無関係な作業の間は `/clear`、区切りでは、残すものを書いた `/compact`
8. いちばん大事なのは、実際のタスクを両方のモデルで1回ずつ走らせ、`/usage` を比べること

## ゲーム制作での使いどころ

原文はゲームに触れていません。以下は、このWikiの考えで、小さなブラウザゲームを1人で作る場面に当てはめたものです。

### 作業を3つに分けて、水準を決める

個人のゲームでは、タスクの種類が、小さな修正、横断的な直し、長い自律実行にだいたい分かれます。上のプリセットの数字（API の定価での、このWikiの計算）を使うと、1件は次の目安になります。

| ゲームの作業 | 原文のプリセット | Opus 5.5 の1件あたり | 初期の effort |
|---|---|---|---|
| 敵のHPや速度の数値調整、UIの文言の直し | 小さな修正 | 約0.24ドル | low か medium |
| セーブデータの形式変更、入力処理の作り直し | 大きなリファクタリング | 約8ドル | medium、詰まれば high |
| 「このGDDどおりに1面を作って」の長時間実行 | 長い自律実行 | 約19ドル | medium から。人が見ないなら Fable 5.1 も候補 |

これは、原文のプリセットの値に当てはめただけで、実際のゲーム制作の費用を測った値ではありません。自分のプロジェクトでは、`/usage` の値を使ってください。

### 「1層だけ直す」バグを、チェックで捕まえる

原文の「フィールド名の変更で、ハンドラーだけ直る」は、ゲームでは、セーブデータの項目名を変えたのに、タイトル画面の読み込み処理が古い名前を読んでいる、という形で起きそうです（推測です）。effort を上げる前に、セーブとロードを通すテストを1つ置きます。原文の理屈では、テスト1回は1ターンで済み、effort は全ターンの思考を増やします。

```md
## 検証（CLAUDE.md の抜粋）
- セーブデータの項目を変えたら、`npm run test:save`（保存して読み込み、同じ状態に戻るか）を必ず通す
- 画面の確認は `npm run shot`（Playwright でタイトルとプレイ画面を撮る）
```

テストや画面確認の仕組みは [検証ループ](/agent-dev/verification-loop/) にあります。

### サブエージェントの単価を決める

素材の検索、ログの読み取り、「この関数はどこで呼ばれているか」を、小さいモデルに任せる定義の例です。原文の説明（`model: haiku`）に沿っています。

```md
---
name: finder
description: ファイルや関数の場所を探して、要約だけ返す
model: haiku
---
該当するファイルのパスと、関連する関数名、役割の1行説明だけを返す。コードは書き換えない。
```

並列の使い分けは [サブエージェントと並列開発](/agent-dev/parallel-agents/) を参照してください。原文のとおり、エージェントチームは約7倍のトークンなので、個人の小さなゲームでは、まず1つのセッションで足ります（推測です）。

### 日々の運用の目安

- 作業の開始時に、モデルと effort を決め、途中で変えない。変えるなら、`/compact` を挟む区切りで
- 無関係な作業（バグ修正から新しい敵の追加）に移るときは `/clear`
- コーヒー休憩の前に、`/compact keep the current bug and the failing test` のように、残すものを指示して圧縮する
- 使わない MCP サーバー（たとえば、画面確認用）は、使わない日はオフにする。CLAUDE.md は200行未満。方針は [長期プロジェクトのコンテキスト管理](/agent-dev/context-management/) を参照
- 週に1回、`/usage` を見て、入力に対して出力が多い日、キャッシュの割合が低い日を探す

ブラウザゲームの構成の選び方は [Webゲームの技術スタック](/agent-dev/web-game-stack/)、ほかのコーディングツールの料金は [AIコーディングツール](/dev-env/ai-coding-tools/) にあります。

## AIの活用ポイント

Claude Code 自身に、費用の点検を頼めます。次のようなプロンプトが使えます。

- 「直前のタスクの `/usage` の結果を貼ります。キャッシュの割合、入力に対する出力、ターン数を見て、どこに無駄があったか、3つ挙げてください」
- 「`/claude-api prompt-audit` を実行して、CLAUDE.md とスキルの、書きすぎや繰り返しを招く指示を直してください。直す前後で、同じタスクの `/usage` を比べられるよう、タスクを1つ決めてください」
- 「このバグの修正は、medium で足りるか、high にすべきか。呼び出し元が複数の層にあるかを調べてから、理由と一緒に答えてください」
- 「このタスクで、モデルが自分で確かめるために使えるテストやスクリプトを、先に1つ作ってください」
