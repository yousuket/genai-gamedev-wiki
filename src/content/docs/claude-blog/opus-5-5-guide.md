## 最初に試す3つ

原文は、Opus 5.5 を使う最初のセッションで試すことを、3つ挙げています。

1. 仕事全体を渡す。何をもって完了とするか、どんなときに止まって質問してほしいかを言い、あとは任せる。
2. 「よく考えて」という行を消す。Opus 5.5 は、返答の前にすでに考えている。
3. 長い作業が終わったら、まず、自分に求められていることを読む。

## 1. 頼み方

### 完了の姿を書き、任せる

- やること: 仕事全体を1つのメッセージで渡します。「テストが通る」「すべてのエンドポイントを移行した」のように、ゴールラインを名づけます。
- 効く理由: Opus 5.5 は、長い複数部分の仕事を、Opus 5 より粘り強く続けます。以前の Opus との比較で最も伸びたのは、大きなリポジトリで変更をテストが通るまで通し切るような、複数ステップの仕事です。早期のテスターは、数時間かかるコーディング作業を、ほとんど見守らずに走らせました。ゴールラインがあるので、終わりを自分で判断できます。
- やり方: 原文の Claude Code の例です。
  ```text
  決済のエンドポイントを、古いクライアントから新しいクライアントへ移行して。
  完了の条件: すべてのエンドポイントが新しいクライアントを使い、古いクライアントは削除され、テストが通ること。
  止まって質問するのは、説明できない理由でテストが落ちたときだけ。
  ```
  （原文の英語の例の意味を日本語にしたものです。）

### 「よく考えて」を消す

- やること: プロンプトや保存した指示から、「注意深く考えて」「ステップごとに考えて」などの行を消します。
- 効く理由: Opus 5.5 は、返答の前に必ず考え、考える量も自分で決めます。頼む必要がありません。原文は、チャット製品での検証で、「注意深く考えて」の行を消すと、品質の目立った低下なしに、返答が早く始まった、と書いています。
- やり方: 行を消します。簡単な質問に素早く答えてほしいなら、「直接答えて」と言います。Claude Code で考える量を変えたいときは、effort を変えます（[effort の記事](/claude-blog/spending-your-effort/)）。

### 作業中に追加する

- やること: 途中で思い出したことは、作業中でもメッセージで足せます。
- 効く理由: 作業が長くなったので、やり直しの損が大きいからです。
- やり方: Claude Code で、Claude が動いている間にメッセージを入力して Enter を押します。たとえば「古いエンドポイント名も、別名として残して」です。

### デザインでは、使ってほしくない型を名づける

- やること: ページ、アプリ、アーティファクトを頼むときは、避けたいデザインの癖を列挙します。
- 効く理由: デザインの方向を示さないと、Opus 5.5 は、いくつかの既定の型に戻ります。「ありがちな見た目を避けて」のような一般的な指示は、1つの既定を別の既定に替えるだけのことが多いです。具体的なパターンを並べる方が、ずっと効きます。
- やり方: 原文の例は、個人サイトを作る依頼で、クリーム色や白に近い背景、見出しの斜体の強調語、「01 / 02 / 03」のような番号つきの節ラベル、等幅フォントのラベル、丸薬型のボタンを、使わないよう指定しています。そのうえで、選ばれた代わりの案を見て、気に入らなければそれも列に足して、頼み直します。

## 2. Claude Code で長い作業を見守る

### 止まる場所を指定する

- やること: 「いつ止まって聞くか、いつ続けるか」の短い規則を、CLAUDE.md に書きます。
- 効く理由: Opus 5.5 は、作業中に状況をよく知らせます。長い作業では、続けずに止まって報告することがあります。次の手を名づけるだけで実行しない要約、続けてよいかの確認、作業を止めない選択肢の列挙です。止まる場所を名づけた指示には、従います。
- やり方: 原文が示す、CLAUDE.md に足す規則です（自分のプロジェクトに合わせて直します）。
  ```text
  入力が要らない手順は、続ける。状況のメモは、次の作業と同じメッセージに書く。
  止まって質問するのは、私なしでは続けられないときと、破壊的な作業の前だけ。
  破壊的な作業とは、データの削除、force-push、このリポジトリの外の変更。
  ```
  （原文の意味を日本語にしたものです。）

運用上の補足が3つあります。
- 「Want me to continue?」で止まったら、「continue」と返します。頻繁に起きるなら、上の規則が効きます。
- 続ける規則は、止まる回数を減らします。取り返しがつかない作業の前の確認は、自分で残します。上の規則の最後の行が、それです。破壊的なコマンドの権限確認も、オンのままにします。
- ペアプログラミングのように見守りたいなら、逆の規則も書けます。作業の前に1行の計画、終わりに短い振り返りです。Opus 5.5 は、どちらにも従います。

### 大きな作業は、サブエージェントに分ける

- やること: 大きなコードベースの監査、移行、レビューでは、サブエージェント（仕事を受け持つ別のエージェント）に分けて、結果を確かめさせます。
- 効く理由: 早期のテスターは、Opus 5.5 に、長い監査や移行で、並列のサブエージェントを、ほとんど見守りなしに調整させました。
- やり方: 原文の例です。
  ```text
  リンク先の issue にある、再試行のバグが、services/ の各サービスにあるか監査して。
  各サービスを、それぞれ別のサブエージェントに渡す。サブエージェントが戻ったら、受け入れる前に、その証拠を確かめる。
  最後に、サービス名、影響の有無、証拠の1つの表にまとめる。
  ```
  （意味を日本語にしたものです。）

### タスクの一覧を、ファイルに置く

- やること: 時間のかかる作業では、タスクの一覧をファイルに持たせ、進めるごとに更新させます。進み具合は、スクロールバックではなく、そのファイルで確かめます。
- 効く理由: 長い作業では、コンテキストウィンドウが埋まり、Claude Code が古いターンを要約します。ファイルの一覧は、その影響を受けず、終わったことと残りが一目で分かります。
- やり方: 「TASKS.md にチェックリストを作って。項目が終わるごとにチェックして、新しく見つけたことは足して」と頼みます。

## 3. 結果を確かめる

### 自分に求められていることを先に読む

- やること: 長い作業が終わったら、まず、Claude が自分を待っていること（残された決定、承認してほしい変更）を探します。要約の残りはそのあとです。
- 効く理由: Opus 5.5 は、Opus 5 より、作業の報告が明快です。途中の報告も最終の要約も、何をしたか、何を見つけたか、自分に何が必要かを、平易な言葉で書きます。
- やり方: 要約の形を変えたいなら、CLAUDE.md に書きます。たとえば「毎回の終わりに、『私待ち』『変更』『発見』の3つの見出しをつける」です。

### コードをレビューさせる

- やること: 人が見る前に、差分やプルリクエストのレビューを、Opus 5.5 に頼みます。
- 効く理由: 原文は、あるテスターの話として、最も低い effort の Opus 5.5 が、high の Opus 5 より多くのバグを見つけ、誤報も少なかった、と書きます。変更を平易な言葉で説明するので、プルリクエストの説明も、レビューしやすくなります。
- やり方: 原文のプロンプトの趣旨です。
  ```text
  このブランチの、main に対する差分をレビューして。
  マージを止めたくなる問題だけを挙げる。各問題について、ファイルと行、なぜ間違いか、失敗を示す方法を書く。
  ```

### 確かめられなかったことを、印として残させる

- やること: 調査や分析では、見つけられなかったことや確認できなかったことを、言わせます。
- 効く理由: 「見つからなかった」は読む価値があり、頼んでおけば見つけやすくなります。
- やり方: 「確認できなかったことに印をつけ、どこを探したかを書いて」と足します。Claude の調査レポートでも、Claude Code でも使えます。

## 4. Claude アプリでの使い方

最初に、モデルの選択欄が Opus 5.5 になっているかを確かめます。

| 場面 | やること | 原文が挙げる理由と例 |
|---|---|---|
| 図や画面 | チャート、図、スクリーンショット、スライドをそのまま添付する。数字を打ち直さない | 図の読み取りが Opus 5 より正確で、追加の手順がいらない。矢印がどの箱をつなぐか、2つの版の図の差、カレンダーの画面で会議の開始と終了が、位置で決まる意味もよく分かる。「この中で、請求の API を直接呼ぶサービスはどれ？」のように具体的に聞く |
| 長い文書の確認 | 長い計画、報告、スライドを渡し、間違いを探させる | 細部への注意が、以前の Opus より強い。検証では、長い計画のやり取りで、曜日の合わない日付と、スライドの数字と合わないグラフを見つけた。「数字、日付、名前の矛盾を探して。各問題を引用して、場所を書いて」 |
| 完成したファイル | アウトラインではなく、ファイルを頼む | 作られる表や文書が、共有する前の手直しが、Opus 5 より少なくて済む。「共有できるスプレッドシートにして。1行に1社、費用、契約終了日、担当者の列で」 |
| プロジェクトでの決着 | 長いチャットで、後の質問への返答が遅いなら、前の答えは決着済みと指示する | 長いチャットで、短い追加の質問のときに、考えながら前の答えを見直すことがあり、返答が遅れる |

最後の行の指示は、プロジェクトの指示に、次の趣旨で書きます。

```text
一度答えたことは、決着済みとして扱う。いまの質問に集中し、私が尋ねたり問題を指摘したりしない限り、前の答えを見直さない。
```

ただし、長い分析のプロジェクトには入れません。後の手順で、前の手順の誤りが見つかることがあるからです。

## 5. メッセージにフラグが立ったとき

原文によると、Opus 5.5 は、Fable 並みの生物とサイバーの防護つきで公開される、最初の Opus です。Claude アプリと Claude Code では、フラグが立ったメッセージの多くは、古いモデルに切り替わり、作業はそこで続きます。ソースコードのセキュリティ上の脆弱性を見つける作業は許可され、日常の健康や教育の質問は、引き続き使えるはずです。防護は、正当な作業にフラグを立てることがあり、誤ったフラグを減らす調整が続けられています。

### Claude アプリ

- 見えるもの: 「Switched to」で始まる通知と、古いモデルの名前です。そのモデルが答え、チャットはそこに留まります。
- Opus 5.5 に戻すには、モデルの選択欄で選びます。前のメッセージがチャットに残っていると、また立つことがあるので、新しいチャットを始めると避けられます。
- 先に尋ねてほしいなら、設定の「Capabilities」で、「Switch models when a message is flagged」をオフにします。「paused」のカードが出て、選択肢が示されます。
- 検査は、会話の全体（ファイルや検索の結果を含む）に及びます。最後のメッセージだけでなく、以前の内容が原因のこともあります。

### Claude Code

- 見えるもの: 古いモデルの名前を示す通知で、セッションはそのモデルで続きます。
- 対処: `/model` で戻す、Esc を2回押して最後のメッセージを直して試す、`/config` で「Switch models when a message is flagged」を変えて先に尋ねてもらう、フラグが誤りなら `/feedback` を使う、の4つです。

### 推論を、返答に書き出させない

プロンプトや指示から、「内部の推論を返答に再現して」という頼みを消します。再現の要求は、断られることがあり、フラグの分類の1つです。必要なことは、別の形で頼みます。たとえば、「この方針を選んだ理由を3文で説明して」です。

## 6. 速さ: fast mode

- やること: Claude Code で、返答を読んでから次のメッセージを送る、行き来の作業に、fast mode を使います。
- 効く理由: Opus 5.5 の fast mode は、公開時にリサーチプレビューとして使えます。同じモデルで、文章が早く届きます。追加の使用量（extra usage）をオンにする必要があり、標準のモードより、1トークンあたりの費用が高くなります。
- やり方: `/fast` と入力します。

| 区分 | 項目 |

## ゲーム制作での使いどころ

原文はゲームに触れていません。以下は、このWikiの考えです。モデルの使い分けは、原文が述べる範囲（慎重な判断が要る長い仕事は Opus 5.5）にとどめます。

### 長い作業を任せるときの CLAUDE.md

ゲームの試作で、「敵の種類を5つ増やして、全部遊べる状態にして」と任せるなら、完了の条件をゲームの言葉で書きます。

```text
完了の条件:
- 5種類の敵が data/enemies.json にあり、各敵が1ステージで出現する
- npm test と npm run smoke（ヘッドレスで60秒、ボットを動かす）が通る
- 既存のセーブデータが、そのまま読み込める
止まって聞くのは、バランスの数値を私が決める必要があるときと、セーブの形式を変えるときだけ。
```

止まる場所の規則は、ゲームなら、「ゲームの面白さに関わる判断（難易度、手触り、報酬の量）で止まる」と書けます。手触りは、人が遊んで決める工程です（[手触り](/agent-dev/game-feel/)）。確認の仕組みは [検証ループ](/agent-dev/verification-loop/)、プロンプトの型は [プロンプトの型](/agent-dev/prompt-patterns/)、指示ファイルの全体像は [プロジェクト指示ファイル](/agent-dev/project-instructions/) にあります。

### 大きな整理をサブエージェントに分ける

小さなゲームでも、コードが増えると、「全シーンで、解除されていないイベントリスナーを探して」のような横断の調査が出ます。原文の監査のプロンプトを、ゲームの言葉に置き換えられます。

```text
scenes/ の各シーンについて、シーン終了時に解除されていないイベントリスナーとタイマーを探して。
各シーンを別のサブエージェントに渡し、戻った結果は、該当する行を確かめてから受け入れる。
最後に、シーン名、問題の有無、該当の行の表にまとめて。
```

分け方や、分けない方がよい場面は [並列エージェント](/agent-dev/parallel-agents/) にあります。

### 長い作業の進捗は TASKS.md に

ポン出しのように数時間走らせる作業では、`TASKS.md` に、機能の一覧とチェックを持たせます。コンテキストが要約されても残り、進み具合を見る場所が1つになります。要約や進捗ファイルの考え方は [コンテキスト管理](/agent-dev/context-management/) にあります。

### レビューと、確認できなかったことの印

ゲームの自分の変更を、マージする前に、「マージを止めたくなる問題だけ」を挙げさせる使い方ができます。たとえば、当たり判定の変更、セーブの形式、フレーム時間に響く処理です。「確認できなかったことに印をつけて」は、ブラウザの実機で動かしていない箇所を、はっきり出すのに使えるはずです（推測です）。

### スクリーンショットを添付する

ゲーム画面の不具合は、文章より、スクリーンショットを添付する方が伝わります。原文は、画像の読み取りを、Claude アプリでの使い方として挙げています。Claude Code にも画面を見せる方法については、原文は触れていません。

### ゲームの UI で避ける型を名づける（原文の例の応用）

原文の個人サイトの例を、ゲームのメニュー画面に置き換えるなら、避けたい型を列挙します。

```text
タイトル画面とメニューのモックを作って。仮の文言でよい。
使わないもの: 紫から青のグラデーション背景、丸薬型のボタン、等幅フォントのラベル、すべて同じ大きさのカード。
```

選ばれた代わりを見て、気に入らなければ、その型も列に足します。

## AIの活用ポイント

- 依頼の最初に、完了の条件と、止まる場面を書きます。それだけで、Opus 5.5 は、長い作業を自分で進めます。
- 作業が終わったら、「私待ち」の項目を先に読みます。要約の形は、CLAUDE.md で決めておきます。
- 人に見せる前に、レビューを頼みます。「マージを止めたくなる問題だけ」と範囲を絞ると、報告が読みやすくなります。
- 調査や分析には、「確認できなかったことに印をつけ、どこを探したかを書いて」を足します。
- 古いプロンプトの「よく考えて」を消します。速さを求める場面では、fast mode と、「直接答えて」を使えます。
- 「推論をそのまま書いて」ではなく、「理由を3文で説明して」と頼みます。
