## 概要

この記事は、Claude Code 公式ブログ（claude.dev）の「How we made claude.ai 3x faster in two weeks」を掘り下げたものです。連載の入口は [Claude Code 公式ブログの連載](/claude-blog/) です。

- 原文: [How we made claude.ai 3x faster in two weeks](https://claude.dev/blog/how-we-made-claude-ai-faster/)
- 公開日: 2026年9月23日。著者: Raymond Wang 氏、Sam Attard 氏、Issac G. 氏。読了時間: 15分（原文の表示）。分類は Engineering

原文が扱っているのは、Anthropic が自社の Web アプリ（claude.ai）とデスクトップアプリを、2026年8月の2週間のスプリントで速くした経緯です。ゲーム制作の記事ではなく、ゲームにも触れていません。Claude を Slack の全スレッドに常駐させ、計測、ベンチマーク作り、修正、デプロイの監視までを任せて進めた報告です。
そこから、ゲーム制作者（特にブラウザゲームを作る人）が持ち帰れるものは、手法の部分です。測れる数字を先に作る、数字を悪化させない柵を CI（コードを変更するたびに自動で走るテスト）に置く、人は目標とセンスと方向を決める、という3点です。この記事では、原文の内容を先に書き、このWikiの考えは「ゲーム制作での使いどころ」にまとめます。

## 結果と進め方の全体像

原文の冒頭の数字です。ユーザーの活動の95%を占める4つの動線（ジャーニー）を対象にしました。75パーセンタイル（p75、遅い方から数えて4分の1の位置）の値です。

| 動線 | 前 | 後 |
|---|---|---|
| claude.ai を新規に読み込み、入力できるようになるまで | 3.1秒 | 0.55秒 |
| Claude Code のセッションを新しく始める | 0.8秒 | 0.3秒 |
| Claude Cowork のクラウドセッションを読み込む | 2.6秒 | 0.73秒 |

原文の図のキャプションによれば、これは実ユーザーの計測（RUM、Real User Monitoring）を、8月13日と8月27日で比べたものです。待ち時間は全体で、1日あたり数万ユーザー時間分短くなったと、原文は見積もっています。

進め方は次のとおりです。

- 全体を1つの Slack チャンネルで運営し、各スレッドに Claude が入る
- 使ったのは、Claude Tag（ベータ）と、Opus 5.5 とおおよそ同等の社内の研究用モデル
- Claude が、ボトルネックの発見、ベンチマークの作成、改善の投入、デプロイの監視をする。人は、目標を決め、トレードオフを決め、すべての変更を承認する
- 3,000件を超える変更を、顧客に見える障害もロールバックもなしで取り込んだ

## 最初の指示（The brief）

スプリントの前に、Slack チャンネルを作り、Claude への常設の指示を置きました。原文に載っている指示の要旨はこうです。claude.ai の Web サイトとデスクトップアプリの性能に関するすべてを担当する。デプロイが性能を悪化させていないかの監視、既存のテレメトリ（計測の仕組み）が正確で漏れがないかの評価、見やすい監視ダッシュボードの維持、見つけた問題と取りやすい改善を自分から実装すること、性能の案件の提案、人間のチームメイトとの連絡が含まれます。最終目標は、できるだけ自律的になることだが、今はまだそれが無理なことは分かっている、とも書かれています。

### 4つの動線と13の測定

Claude に、Datadog の MCP サーバー（外部ツールを Claude につなぐ仕組み）を通じて利用データを分析させ、最も影響の大きい動線を選ばせました。次の4つです。

1. アプリを起動する
2. 会話を始める
3. 既存の会話を読み込む
4. メッセージを送る

Web とデスクトップ、各プロダクトを合わせると、13の測定になりました。ベースラインを作るため、測定どうしを比べられるまで計測を足しています。各測定は、ユーザーの操作で始まり、結果が描画されたところで終わり、クライアント側とサーバー側の作業を区別するように揃えました。

### 約20の案件と、最初の3日

スプリントの開始時に、手作業で選んだ約20の案件を用意しました。それぞれが1つの動線を狙っています。Claude が各案件の効果をミリ秒で見積もり、その合計をスプリントの目標にしました。13の目標のうち12を、3日目までに達成しています。

予定の案件の例は次のとおりです。

- 起動を速くする: 静的な入力欄（composer、入力ボックス）を HTML に焼き込み、React が初期化している間も入力できるようにした。デスクトップのシェルは、V8 のコードキャッシュを事前にコンパイルし、メインプロセスが毎回ゼロから再コンパイルしないようにした
- 画面の移動を速くする: 会話の間で入力欄をマウントしたままにする。マウスを乗せたセッションを先読みする。サイドバーの再描画を90%減らす

予定の案件が早く終わったので、残りの余地を Claude に使わせました。Claude が機会を見つけて新しい作業を提案し、それが独立した案件に育ちました。目標を立て直し、さらに測れるものを探しました。人の指示は、ほぼすべての案件に資金を出したので、まだ手を付けていないところ、登れるところ、いちばん機会が大きいところを洗い直そう、突飛な案でもよい、というものでした。

## 「何でも山登りにできる」

原文の中心の節です。山登り（hill climbing）は、1つの数字を決め、それを良くする変更を繰り返し探すやり方です。

### ラボで測れるもの

デプロイの頻度より速く繰り返したい、というのが出発点です。Claude は何時間も、夜通しでも非同期に動けるので、実際のユーザーのデータを待たずに、試作を検証させたかったのです。そのために、ラボ（手元の実験環境）で性能を測る方法を探しました。

壁時計の時間（実際にかかった時間）は、ユーザーが感じるものですが、ばらつきが大きく、ミリ秒の値は CI のゲートに使えません。そこで Sam 氏が見つけた糸口が、命令数の計測でした。決定的（毎回同じ値になる）だからです。原文のスレッドの再現では、Claude が次のように答えています。

- 純粋な JavaScript の処理: Valgrind の下でベンチマークを `node --predictable` で動かし、リポジトリに置いたベースラインと比べる。1回の実行で足りる。統計は要らない
- ブラウザ内の処理: Chromium では命令数は数えられないが、決定的な数が他にもある。操作あたりの React のコミット数、V8 の精密なカバレッジによる関数呼び出し回数、レイアウトとスタイル再計算の回数、DOM の変更回数

11分後には、5つのスレッドが動いていました。命令数、V8 の呼び出し回数、React のコミット、スタイル再計算、DOM の変更が、1スレッドずつです。

### ベンチマークへの疑い方

新しいベンチマークは、疑って扱いました。各ベンチマークには2つの役割があります。1つは、Claude がラボで動かせる指標になること。もう1つは、CI のガードレールになり、値が下がる方向にしか動かないこと（ラチェット）です。不安定なもの、ユーザーの遅延と相関しないものは、Claude に間違った山を登らせないために捨てました。

Claude には、これらに対する山登りが壁時計の改善につながることを証明するよう頼み、証明できない候補のベンチマークは外す、と伝えています。

証明のため、2つの処理を選びました。会話のメッセージ木を組み立てる処理と、Claude Code の出力のステータス行を探すスキャナーです。Claude は両方を Valgrind でプロファイルし、最初の処理で、命令の4分の1が、同じメッセージIDを3回別々に引く辞書の検索（megamorphic、型がばらばらで最適化されにくい検索）だと見つけました。1時間後には、2つの処理の命令数をそれぞれ48%と31%減らし、壁時計の時間は78%と44%減っていました。

つまり、命令数は時計と連動していました。この2つのパスに、ラチェットを入れました。以後、命令数を上げる PR（変更の提案）は CI で落ち、毎日の定期ジョブが、数が下がっていれば上限を下げます。

### スプリントの中心的な教え

原文は、これを「Claude と一緒なら、測れるものは扱える」とまとめます。以前は、測定は第0段階で、指標を足し、データが来るのを待ち、それから問題を理解し始めました。Claude がいると、測定は登りの第1歩です。超えるべき数字があれば、すぐ最適化を始められます。だから、いちばん効果が大きいのは、測れるものを増やすことでした。

## スレッドごとのループ

全部が同じ Slack チャンネルで、複数のエンジニアと Claude がスレッドごとに議論しながら進みました。ループは次の形に落ち着きました。

1. 誰かが、動線のどこかが遅い、とスレッドを立てる（スクリーンショットや録画付きが多い）
2. Claude が流れを追い、問題を示すベンチマークを探すか作る
3. ラボで有望な結果が出たら、Claude が PR を出す。リスクとレビューのしやすさに合わせて分け、ユーザーに見える変更はフラグ（機能フラグ）の裏に置く
4. 出荷後、Claude がデプロイを監視し、実際のデータを読む
5. 改善していれば、ベンチマークのラチェットを下げて成果を固定する。改善していなければ、フラグをオフにして繰り返す
6. 同じ動線で、次の遅い箇所を探す

### 例: 画面のガタつき（レイアウトシフト）

誰かが、ページの読み込み後にサイドバーの行が後から現れる画面録画を共有しました。チャットと Cowork の行が別々のタイミングで決まり、ページがぎこちなく感じられます。既存のモニターでは検知できていませんでした。最も近い CLS（Cumulative Layout Shift、レイアウトのずれの指標）では、1回のずれが約0.008で、「良い」の閾値0.1の範囲内でした。

Issac 氏が、Layout Instability API（ブラウザが出すレイアウトのずれの記録）を直接見ることを思いつきました。Claude は、各ずれの原因を、領域（サイドバー、会話の記録など）と段階（最初の描画の前、入力できるようになった後）に対応づけるテレメトリのイベントを作りました。さらに、サイドバーのデータを最初の描画の後まで止めてページを開き、名前の付いた領域でずれが起きたら失敗する結合テストを書きました。修正の証明にも、このテストを使いました。main では20回中20回が失敗（赤）、修正の PR では20回中20回が成功（緑）です。

イベントのデプロイ後、実データを読むと、Web のページ読み込みの31%で、ユーザーが何もしないのに、入力できる状態になった後で何かが動いていました。Claude は、原因を名前で順に潰しました。遅れて来るヘッダーの行、ユーザー名の読み込み後に横へずれるキャレット（文字カーソル）、スクロールバーの出現で動くリストなどです。上位の原因をまとめて直し、消えたら次の一群を見つけました。

## 水平にスケールする

ループが1スレッドで動いたら、あとはスレッドを開くだけです。要求が満たされてもスレッドを閉じずに、Claude は続けました。1つのスレッドが、50件、時には100件の最適化 PR を出しました。人ではなく Claude が、別の調査や夜間のジョブで見つけた機会を追う新しいスレッドを立てることも増えました。同時に150を超えるスレッドが動いていたと、原文は書いています。

測るたびに、何かが見つかりました。

| 測ったもの | 見つかったこと |
|---|---|
| React の hook の数え上げ | 入力欄の入力経路に、hook が6,900個、ストアの購読が900個あり、キー入力のたびに再描画されていた |
| スタイル再計算の回数 | 1つの `:root:has()` セレクターが、DOM の変更のたびに24ミリ秒を足していた |
| 最初の描画以降のコードパス | 残っていた `location.reload()` が、1日に50万回の見えない再読み込みを起こしていた。どの読み込み指標にも映らなかった |
| 放置したタブのプロファイル | 同じキャッシュのスナップショットが、毎分2回、メインスレッド上で IndexedDB に複製されていた |

### 例: 長音のダッシュが1秒止める

CPU のひっかかりを探す掃引で、Claude は、終わったコードブロックのハイライトが、ページを約1秒止めることがあるのに気づきました。ラボで原因を探すと、エムダッシュ（—）でした。返信の Markdown に、エムダッシュや曲がった引用符のような、Latin-1（西欧の基本文字）の範囲外の文字が1つでもあると、V8 は文字列全体を UTF-16（1文字2バイト）で持ちます。すると、構文ハイライトの正規表現がすべて、遅い2バイトの経路を通ります。20行ほどの変更で、各コードブロックを1バイト文字列にコピーしてからハイライトすることで直しました。

### 規模の様子

2週目には、日々の報告にまとめきれないほどになり、最も忙しい日には200を超える変更が入りました。Claude は新しいベンチマークを提案し続け、PR の約3分の1に、追加のテレメトリかガードレールが含まれました。新しい計測のたびに、新しいスレッドと機会が生まれます。全部が1つのチャンネルで公開されて進んだので、他のチームが自分の変更を性能のレビューに持ち込むようになり、ガードレールと導入された Claude のスキルのおかげで、新しい案件は性能を意識した書き方になりました。

## ガードレール

ほぼすべてが、最初の描画、入力欄、会話の記録という、よく通る経路（ホットパス）でした。そこで、安全の仕組みを先に作っています。

- すべての PR は、自動レビューと、少なくとも1人の人間の承認を通す
- 最適化の前に、必ず単体テストを書く
- ユーザーに見える問題を起こしうる変更は、短命の機能フラグの裏で出荷する

フラグが溜まったら、ロールアウトと片付けを調整するスレッドを立てました。Claude は、すべてのフラグを、キルスイッチ（異常時に止める）か、ランプ（段階的に広げる）かに分類し、安全になり次第、撤去しました。2週間で約200のフラグを導入し、終わりの時点で半数以上が片付いています。

### 成果の劣化を防ぐ

速いコードベースの中では、性能の成果は劣化します。Anthropic ではコードの出荷が速いので、勝ちが証明された案件には、保護のための投資をしました。例が、静的な入力欄です。ページの HTML コピーをほぼ即座に見せ、その真上に React が描画します。React の描画が1ピクセルでもずれると、効果が消える、壊れやすい仕組みです。Claude は、何十ものガードレールを作りました。

- 静的なマークアップは、本物の React コンポーネントを jsdom（ブラウザなしで DOM を扱うライブラリ）で描画して生成し、両者がずれないことをテストで保証する
- 結合テストで、静的ページと React の描画を、14種類のビューポートの大きさで比べ、1ピクセル以内の一致を確認する
- キー入力のテストで、引き継ぎの途中で打ち続け、欠けた、または順序の入れ替わったキーがあれば失敗させる
- 実際のユーザーの環境では、引き継ぎごとに、ずれを0.1ピクセル単位で報告させ、動きがゼロでないイベントごとに Claude がスレッドを立てる

ラボで捕まらないものには、最も古いガードレール、段階的なロールアウトも使いました。高リスクの変更は、社員、次にユーザーの1%、最後に全員の順です。静的入力欄を社内に出して4時間後、同僚が、どの指標にも映らないレイアウトのずれの録画を共有しました。新しいタブで claude.ai を開くと、入力欄が下に落ちるのです。しかし原因は自社のコードではありませんでした。

Claude の調査の結果は次のとおりです。

- 新しいタブのページでは、Chrome が56pxのフッター（「Managed by anthropic.com」など）を、ページの下に描いている。claude.ai に移ると、そのフッターが消えてページが56px高くなるが、それは最初の描画の約100ミリ秒後
- `/new` は、あいさつと入力欄をページの高さの18%の位置に置くので、0.18 × 56で約10px落ちる。録画の測定値も10px
- 起きるのが「ときどき」なのは、アドレスバーに入力中に Chrome がページを先読みして描画（prerender）し、その隠れたページが、現在のタブの高さ（フッターで少し低い）で組まれ、表示後に初めて引き伸ばされるため
- 静的入力欄から本物への引き継ぎは、その日の49回の読み込みすべてで0pxだった
- 以前から潜在していたが、ページがここまで早く描画されることがなかった。ヘッドレスの Chrome にはブラウザの UI がないので、レイアウトテストでは見えない

Claude は、Chrome の先読みの端のケースまでたどり着き、リサイズをまたいでレイアウトを固定し、先読みの流れを模擬するテストを足しました。

## 人の役割: Steering

ループは生産的でしたが、自律ではありませんでした。速く、安全に、道を外さず進めるのが人の仕事で、3つに分かれます。

### 野心（Ambition）

Claude は、既定では範囲に慎重です。見つけたことをチケットにし、実現性に保険をかけ、見積もりに余裕を持たせます。しかし、人はガードレールに自信があったので、特に序盤は、Claude にもっと大胆になるよう促すことが多い、と原文は書いています。スレッドの再現では、Claude が「今週中に小さな PR を1つ出します」と答えたのに対し、Raymond 氏が、今出せばすぐマージしてデプロイする、もっと大胆に、と返しています。Claude は1時間以内に PR を出すと答え直しました。目標に達するとスレッドが鈍るので、Sam 氏は、目標は止まる場所ではない、次は何か、野心的に、という趣旨の同じ一文を全スレッドに書いて回りました。

### センス（Taste）

どのスレッドにも、名前の付いた人間の担当者がいます。Claude は、ユーザーに見える変更を、前後のスクリーンショットや録画で示し、担当者に判断させました。原文が挙げる問いは次のとおりです。

- 表は、セルごとに埋めるか、行がそろうまで待つか
- 読み込み中の骨組みの表示（スケルトン）は、すぐ出すか、半秒後か
- ストリーミングの文章に、1語ずつのフェードを付ける価値はあるか（フレーム予算の5分の1を使う）

Claude はミリ秒を削る方法を探し、人がトレードオフを秤にかけます。

### 方向（Direction）

スレッドは、意図的に狭く保ちました。1つのベンチマークか動線に絞り、その範囲での改善だけを探させます。原文は、150本の「釘を探すハンマー」にたとえています。人の判断の多くは、順序と、ユーザーへの影響です。どの画面を優先するか、互いに邪魔するスレッドをどうまとめるか、見返りが減ったスレッドをいつ閉じるか。900行の PR には、1行の返事が付きました。送信あたり2ミリ秒のために、このビルドプラグインを維持する複雑さには見合わない、という判断です。

## 8ミリ秒の予算

寄り道の1つが、全体の動きをよく示しています。ライブのシンタックスハイライトの正規表現の最適化を示すため、Claude は、長い返答がラボでストリーミングされる画面録画を添え、隅にフレームレートの表示を足していました（ページ内で、アニメーションフレームのタイムスタンプから計算）。

Raymond 氏が、60fps で頭打ちなのか、スクロールとストリーミングを120に上げられるか、と尋ねました。Claude は、今の環境が60Hz なのは、ヘッドレス Chromium の既定だからで、120にもできるはずだと答え、25分後に報告しました。DevTools のフレーム制御（begin-frame）で、ヘッドレス Chrome を決定的な120Hz で刻めたのです。240回の begin-frame で、ちょうど240フレーム、各8.33ミリ秒。これで「このフレームは120Hz の予算に収まったか」が、ノイズのない正確な読みになります。

1フレームの予算が8.33ミリ秒になったので、Claude は、長い返答をフレームごとに進め、各フレームの時間を測って遅い箇所を見つけました。実際にやったことは次のとおりです。

- チャンクごとの、メッセージの長さに比例する処理（O(message length)）を、終わったブロックのメモ化でなくす
- 伸びていくコードフェンスのトークン化を、ワーカー（別スレッド）に移す
- 表を、セルごとに表示する

このスレッドだけで、60本近くの PR が入りました。長い返答がメインスレッドを止める時間は、合計で約750ミリ秒から約200ミリ秒に、CPU 使用は約3分の1に、120Hz の MacBook で、最初から最後まで120fps を維持しました。120Hz の実験環境は、夜間ジョブになり、Claude が劣化を見ています。原文に引用されている公式アカウントの投稿（2026年8月24日）は、ストリーミングが約4倍なめらかになり、遅いノートPCで長い返答の停止が9分の1、最悪のひっかかりが4.5分の1になったと述べています。

当初、ストリーミング中のフレーム間のミリ秒を山登りの対象にするとは計画していませんでした。数えられるなら、Claude は登れる、というのが原文の結びの感触です。

## 今後

原文は、claude.ai とデスクトップアプリは、8月初めより約3倍速く、ラチェットがそれを保つはずだとしています。残りは、95パーセンタイル、他の動線、非常に長い会話です。別の記事で、スプリント中の寄り道（[Electron](https://www.electronjs.org/)、Chromium、Node.js などへの貢献）にも触れる予定です。

## ゲーム制作での使いどころ

原文はゲームに触れていません。以下は、このWikiの考え（推測）で、ブラウザで動く小さなゲームに当てはめたものです。原文の内容ではありません。

### 手法のうち、持ち帰れるもの

| 原文の手法 | ブラウザゲームでの当てはめ（推測） |
|---|---|
| 最初に、動線ごとの測定を揃える | 「タイトル画面で操作できるまで」「ステージ開始まで」「ボタンを押してから反応まで」を、始点と終点を決めて測る |
| 壁時計ではなく、決定的な数で CI の柵を作る | 敵100体の更新、衝突判定、経路探索などの処理の、呼び出し回数や処理した要素数を数え、基準値を超えたらテストを落とす |
| ラボのフレーム予算 | 60fps なら1フレーム約16.7ミリ秒、120fps なら約8.3ミリ秒。1フレームの処理時間を測り、予算を超えたフレームの数を指標にする |
| ひっかかり（p99）を見る | 平均 fps ではなく、最悪に近い1%のフレーム。[Webゲームの技術スタック](/agent-dev/web-game-stack/) の事例も、p99 と最悪のフレームを見ていた |
| 成果をラチェットで固定する | 一度速くした箇所の基準値をファイルに置き、遅くなる変更をマージさせない |
| 変更は小さく、機能フラグの裏で、段階的に出す | 個人のゲームでは、設定の定数で新旧を切り替え、公開前に自分と友人で試す |

特に、起動の話は、ブラウザゲームに近いと思われます。原文の静的入力欄は、JavaScript が起動する前に、画面の見た目を HTML で先に出して入力を受け付ける手です。ゲームなら、ローディング画面やタイトル画面を、アセットの読み込みの前に素の HTML で出す、という発想に当たります（推測です）。ただし、原文の数字（3.1秒から0.55秒）は claude.ai のもので、ゲームの値ではありません。

### Claude Code に任せる手順

原文の Slack 常駐とは違い、個人のゲームでは、Claude Code と、リポジトリ内のスクリプトで足ります。次の順で進めるのが、この記事から言えることです。

1. 「測れるもの」を先に作らせる。CLAUDE.md に、性能の指標とその測り方を書く
2. ベースラインを、リポジトリにファイルとして置く
3. 改善のたびに、指標が下がったか、見た目が変わっていないかを確かめさせる
4. 改善したら、基準値を更新し、後戻りを CI で止める

CLAUDE.md の断片の例です。

```md
## 性能（予算）
- 1フレームの更新+描画は、p95 で 8ms 以下、最悪値で 16ms 以下（`npm run perf` で測る）
- 敵 200 体のステージで、衝突判定の呼び出し回数が `perf/baseline.json` を超えたら失敗する（`npm run perf:count`）
- 性能の変更は、前後の `npm run perf` の出力と、`npm run shot` のスクリーンショットの差分を PR に貼る
- 速度が上がったと確認できた場合のみ、baseline.json の値を下げる（上げてはいけない）
```

測り方の具体例（ロックステップなしのフレーム時間の集計、画像の差分）は [検証ループ](/agent-dev/verification-loop/) にあります。原文の、DevTools の begin-frame で120Hz のフレームを決定的に進める話は、そこの「乱数の seed と固定刻み」と同じ考えです（推測です）。

命令数の測定（Valgrind）は、純粋な JavaScript の処理が対象です。ゲームなら、描画と切り離した、ロジックだけの関数（ダメージ計算、経路探索など）が当たります。原文は、Valgrind を動かす環境には触れていません。自分の環境で使えるかは別に確認が要りますが、呼び出し回数や処理した要素数を数える方法なら、環境を選ばずに作れます（推測です）。

### 原文から、そのまま持ち帰れる姿勢

- 数字がなければ、Claude に「速くして」と頼んでも、良くなったかを判断できない。まず測る
- 測定の指標が、本当にユーザーの体感と連動するかを確かめ、連動しないものは捨てる。原文は、命令数と壁時計の連動を、2つの処理で確かめてから採用しています
- 1つのスレッド（会話）は、1つのベンチマークか動線に絞る。範囲を広げすぎない
- Claude は、既定では慎重なので、目標に達したら「次は何か」と促す。一方で、見合わない複雑さの変更（原文の、900行で2ミリ秒の PR）は、人が閉じる

並列の進め方は [サブエージェントと並列開発](/agent-dev/parallel-agents/)、測って改善する考え方は連載の [eval と山登りの記事](/claude-blog/eval-hillclimbing/) を参照してください。

## AIの活用ポイント

次のようなプロンプトで、原文の進め方を小さなゲームに移せます。

- 「このゲームの、遅いと感じる場面を3つ挙げ、それぞれ始点と終点を決めて、Playwright で時間を測るスクリプトを書いてください。まず測るだけで、直さないでください」
- 「`npm run perf` の結果を `perf/baseline.json` に保存し、基準値を超えたら失敗するテストを足してください。基準値は下げる方向にしか更新しないでください」
- 「この関数の呼び出し回数を、再現できる条件（seed固定、フレーム数固定）で数えるベンチマークを作り、壁時計の時間と連動するかを確かめてください。連動しなければ、その指標は使わないと報告してください」
- 「画面が読み込み後に動く（ガタつく）場所を探すため、`PerformanceObserver` で layout-shift を記録し、どの要素が動いたかを一覧にしてください」
- 「見つけた改善案は、ひとまとめにせず、1つの指標に対する1つの PR（1つのコミット）として出してください。ユーザーに見える変更は、定数で切り替えられるようにしてください」
