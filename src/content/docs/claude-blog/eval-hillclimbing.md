## 概要

- 原題は「Automating eval design and hillclimbing with Claude」です。公開日は2026年9月28日、著者は Lance Martin 氏、読了時間は12分です（[原文](https://claude.dev/blog/automating-eval-design-and-hillclimbing/)）。

## eval を作る前に: 良い eval の4つの条件

原文は、うまく設計された eval に共通する要素として、次の4つを挙げます。

| 条件 | 中身 | 満たさないときの兆候 |
|---|---|---|
| 本番を映している | 実際に使われる場面から、タスクを選ぶ。作りやすい、採点しやすいという理由だけで選ばない | 点数は上がるのに、実際の利用では良くならない |
| 強いモデルや高い effort ほど点が上がる | 能力の高いモデルや、長く考える設定の方が、点が高くなるはず | 上がらないなら、曖昧なタスクか、採点者のずれが足を引っ張っている |
| 最上位でも満点にならない（余地がある） | 最も強いモデルを最も高い effort で動かしても、点数がかなり低い | 満点に近いと、変更の効果を見分けられない |
| 実行ごとのばらつきが小さい | 同じ条件で何度か回しても、点が大きく動かない | 曖昧なタスク、採点者の判定のぶれ、effort が毎回同じに効いていない、前の試行の残り物（ファイルや git の履歴）が答えを教えてしまう、などが原因になる |

2つ目と3つ目には、見分け方の補足があります。余地がある理由が「解けないタスク」や「曖昧なタスク」であってはいけません。目印は、何回繰り返しても毎回失敗するタスクです。良いタスクとは、2人の専門家が同じ結論を出せて、採点者が確認する内容がタスクの文面にすべて書いてあるものです。

effort（モデルがどれだけ考えるかの設定）は、このシリーズの [Spending your effort の記事](/claude-blog/spending-your-effort/) で扱っています。eval は、effort やモデルの選び直しを、勘ではなく点数で決めるための道具でもあります。

### 敵対的サンプリングの落とし穴

原文は、「今のモデルが落とすケースだけを選ぶ」ことを戒めます。モデルの能力には凹凸があり、今のモデルが落とすケースを集めると、そのモデルの谷だけを標本にすることになります。測っているのは、そのモデルの失敗の癖であって、アプリにとって本当に難しいこと、価値のあることではなくなります。

代わりの選び方は次のとおりです。
- 人が「難しい」と判断した理由を言えるケースを選びます。難しい理由を言葉にできることが、入れてよいかの目安です。
- 本番の失敗（バグ報告、問い合わせのチケット）から作ったケースを入れます。
- ただし、利用者のログをそのまま信じてはいけません。利用者は「うまくいきそうなこと」を試すので、ログだけから作ると易しい方に偏ります。

## /claude-api build-eval: eval を作る手順

`/claude-api build-eval` を Claude Code で実行すると、Claude が質問しながら、コードベースの中に eval を作ります。要所で止まって、人の承認を求めます。

### 事例（入力）の集め方

事例は、次の順で集めます。
1. 本番の会話記録（保存期間や機微な情報について確認してから）
2. バグ報告やサポートのチケット
3. 自分で手書きする5〜10件
4. コードベースから合成した事例

本番のデータを優先しますが、少数の本物の例を起点にした合成データも作れます。Claude は、すべての入力を一覧するページを作り、人が確認するまで先に進みません。原文は、メールの振り分けアプリを例に、そのページの図を載せています。

### 採点者を決めて、検証する

次に、出力の形に合わせて、最も安い採点者を提案します。

| 出力の性質 | 採点者 | 中身 |
|---|---|---|
| 答えの形が限られる | コードによる判定（programmatic verification） | 完全一致、決まったラベルのどれか、スキーマに合う JSON、テストの合格など |
| 答えが自由で、正解が複数ある（質の基準は明確） | LLM-as-judge（別のモデルが採点） | 入力、出力、採点基準を読ませ、点と理由を返させる。基準は1〜5の尺度ではなく、確かめられる主張の形で書く |

LLM-as-judge には、補足が3つあります。
- 比較の基準（ベースライン）があるときは、2つの出力を順番をランダムにして読ませ、どちらが基準かを伏せて、良い方を選ばせます。
- 採点者のモデルは人が選びます。テスト対象のモデルと同じものにはしません。
- Claude は数件を採点し、「自分なら違う点をつけたものがあるか」を人に尋ねます。原文は、採点された記録を実際に読んでから評価者を信じるべきだと強調します。採点の失敗は、eval の設定ミスで最も多いものの1つだからです。

採点者を検証し終えると、事例数 × 繰り返し数 × モデル数という規模と、おおよその所要時間を示し、ベースラインを実行して、信頼区間つきの点数を出力します。成果物は、事例、採点者、実行用のコード、1事例につき1行の JSON と全記録、各事例の点数と記録へのリンクを並べた簡素なページです。グラフなどが欲しければ、追加のページを頼めます。追加のページは、ローカルで開ける静的ファイルで、ネットワークからは何も読み込みません。

### 診断チェック

ベースラインを回す間に、Claude は3つを確かめます。
- 採点者: 同じ出力を2回採点して、判定が変わるかを報告します。
- 配管（plumbing）: タイムアウト、API エラー、途中で切れた回答を確かめ、基盤のノイズがモデルのばらつきに見えないようにします。
- 余地（headroom）: ベースラインがすでに約95%以上なら、警告します。その場合、hillclimb の狙いは、品質ではなく費用や遅延に置くよう促します。

## hillclimbing: 点数を上げる作業の原則

信頼できる採点ができたら、アプリを改善できます。hillclimbing は、effort やプロンプトのように、費用と性能を引き換えにするパラメータを調整するのに向きます。どこに適用するかの目安が3つ書かれています。

- 安く反復できる: 変える場所が、時間、費用、手間の面で安いこと。多くの社内の取り組みや顧客は、プロンプトや Skill のようなテキストに絞っています。直しやすく、戻しやすいからです。ハーネス（モデルの周りのコード）への自由な変更は、大きなコード変更になりえます。
- 点数の変化を、変えた場所に結びつけられる（attributable）: 例として、Skill が正しく呼ばれるかの改善があります。指標（呼び出し率）が、変更する Skill の説明文に直結しているからです。
- 目的が絞られている: 「性能を上げて」という漠然とした依頼は、eval の余地を考えていないため、止まりやすい失敗の型です。飽和した eval や、「ハーネスを直して」のように範囲が広すぎる対象も止まりやすくなります。多くの取り組みで有効だった目的は費用です。eval が飽和していても、同じ性能のまま費用を下げる、という頼み方ができます。

### 過学習（overfitting）を防ぐ

どれだけ良い eval でも、本番の分布とぴったり一致することはまれです。そのため、eval では点が上がるのに、本番では良くならない過学習が起きやすくなります。

原文は、eval の情報がハーネスに染み込む経路を挙げます。たとえば、eval のタスクに OCR（画像の文字読み取り）が有利で、本番ではほとんど効かない場合、eval の都合でアプリに OCR のツールが足されると、ベンチマークだけが上がり、本番には何も効きません。同様に、改善の過程で、eval の個別事例の特殊な場合に対処する機能がハーネスに足されることがあります。

対策は3つです。
1. 事例を分ける: 改善役が読んでよい学習用（train）と、一度も見せないテスト用（test）に分けます。学習用の点だけが上がり、テスト用が横ばいなら、過学習の典型的な兆候です。
2. 失敗の中身をプロンプトに貼らない: 改善役が失敗した記録を読んでも、その内容をそのままプロンプトに貼りません。
3. 答えをモデルの手の届かない所に置く: モデルは、eval の答えを直接探し出す「報酬ハッキング」をすることがあります。

## /claude-api hillclimb: 改善を自動で回す

`/claude-api hillclimb` は、上の原則を手順にしたものです。変更してよい対象は人が選びます。

- システムプロンプト
- Skill や指示ファイル
- ツールの説明
- モデルの選択、effort、その他の API パラメータ
- ハーネスのコード

### 始める前

最初に、何を最適化するか（性能、または性能を保ったまま費用を下げる）を尋ね、eval の事例を、ランダムに学習用とテスト用に分けます。費用が目的なら、よくある費用の要因を調べます。プロンプトキャッシュ（同じ前置きを安く読み直す仕組み）、選んだモデルとプロンプトの相性の点検、モデルと effort の選択が挙がっています。

最初のラウンドの前に、eval のノイズ（偶然だけで点数が動く幅）が、人が行動に移したい最小の改善より小さいかを確かめます。小さくなければ、そう伝えて、繰り返し数や事例を増やすよう提案します。

### 1ラウンドの流れ

1. 前のラウンドの学習用の記録を読み、1つだけ変更をパッチとして提案します。ノイズを超えて効果が見える変更を狙います。言い換えで済ませず、失敗する挙動を根本から直します（原因の節を書き直す、足りない規則を足すなど）。
2. パッチを当てて eval を実行します。
3. 学習用が上がり、テスト用が横ばいなら、過学習を疑ってパッチを戻します。悪化したときも戻します。学習用もテスト用も上がったときだけ、パッチを残します。

### 止まったとき

2〜3ラウンド点数が止まると、残った学習用の失敗を1件ずつ読み、原因で分類します。1つの修正でもノイズを超えて点が上がらない見込みのときは、早めに同じ分類をして、小さすぎる変更に回数を使わず、繰り返しや事例を増やすよう提案します。この段階で、曖昧な eval の事例、ハーネスの誤り、実行ごとのばらつきが見つかります。以降のラウンドには、本物の失敗だけを使います。

### 終わり方

終了時には、コードを、目的に対してテスト用で最も良かった版に置きます。ベースラインとの比較を、信頼区間つきで報告します。改善が誤差の範囲なら、その旨を言い、マージしないよう勧めます。

## 実例1: 費用を下げる（サポート問い合わせの eval）

社内のカスタマーサポートのベンチマーク（チケット44件。30件を探索に、14件を未見のテスト用に）で、`/claude-api hillclimb` を、費用の削減と性能の向上を目的に実行しました。出発点は、Opus 4.8、既定（high）の effort で、探索用の判断の正答率が74.4%、1件あたりの費用が4.6セントです。

| 段階 | 変更 | 正答率（探索用） | 1件あたりの費用 |
|---|---|---|---|
| 出発点 | Opus 4.8、high | 74.4% | 4.6セント |
| プロンプトの整理後に Opus 5.5 の low | 必須のツール呼び出しの儀式、書き出しの段階、矛盾する規則を削り、モデルを替えた | 87.8% | 1.9セント |
| 1段階下のモデル | Sonnet 5 の low | 約88.9% | 約1セント |
| プロンプトの改善 | 振り分けの規則と、返金上限への相互参照を追加 | 98.9% | ほぼ同じ |

Opus 5.5 への切り替えで費用が下がった一因は価格です。入力と出力のトークンが Opus 4.8 より20%安く、キャッシュ読み出しが60%安い、と原文は書いています。Opus 5.5 が基準を超えたので、改善役はさらに安いモデルでも超えられるかを確かめて、Sonnet 5 に下りました。最終構成は、探索に使っていない未見の14件で、正答率が元の構成の78.6%に対して90.5%、費用は約5分の1でした。

読み取れる点は3つあります。
- 最初の一手は、モデルの変更ではなく、プロンプトの掃除でした。不要な儀式と矛盾を除いただけで、後の段階の土台ができています。
- モデルを下げる判断を、「基準を超えたか」という eval の点数で決めています。「安いモデルは精度が落ちるはず」という思い込みでは決めていません。
- 成功は、探索用の98.9%ではなく、未見の90.5%で報告されます。探索用と未見用の差が、過学習の余地を示しています。

## 実例2: 性能を上げる（claude-api Skill 自身の eval）

もう1つの例は、claude-api Skill 自身です。この Skill は、Anthropic の API の使い方や、Claude を使う一般的なコツを案内します。Skill が API を使うコードを正しく書けるかを確かめるため、公式ドキュメントから eval を作りました。Skill の点数は最初66%です。改善役にドキュメントと SDK を読める権限を与え、誤りを見つけて直させました。

| 段階 | 内容 | 点数 |
|---|---|---|
| 1 | Skill に、8つの機能の説明が欠けていると判明。その節を追加 | 74% |
| 2 | C# と Java の型の表の誤りを修正 | 77% |
| 3（反省の段階） | 失敗を原因で分類。モデルが、古い API の形を書いていた。古い形から現在の形への対応表を、Skill の冒頭に追加 | 80% |
| 4 | 改善しないタスクを調べ、eval 側の誤りを修正。Skill の編集も追加 | 約88%（図では87.9%） |

3つ目の段階が、原文で最も示唆の大きい部分です。2ラウンド点数が止まった後、改善役は、1回の編集もせず、残りの失敗を原因別に分類しました。その結果、Skill に正しい内容はあるのに、モデルが訓練で覚えた古い API の形を書いてしまう、という原因が分かりました。たとえば、固定のトークン予算を指定する拡張思考（extended thinking）は、最近の Opus では API に拒否されるようになり、適応型の思考（adaptive thinking）に置き換わっています。古い版の web 検索や web 取得のツールにも同じことが起きていました。改善役は、覚えている形から現在の形への対応表を Skill の先頭に置きました。さらに、C# と Java の、固定予算の思考への警告を、適応型の例より前に移しました。

4つ目の段階は、「明らかな不足を直しても改善しないタスクは、事例か採点者がおかしい兆候」という教えです。実際、1つのタスクは、1種類のエラーを捕まえるコードを求めているのに、採点者は3つ以上の連鎖を求めていました。Claude はタスクの文面を直しました。もう1つの採点者の指示は、公式ドキュメントと矛盾していて、実際の API で試すと、ドキュメントの方が正しいと分かりました。

## はじめかた

原文の手順は短いものです。claude-api Skill は Claude Code に同梱されているため、まず更新します。

```shell
claude update
```

そのうえで、Claude Code の中で次を実行します。

```text
/claude-api build-eval
/claude-api hillclimb
```

- `build-eval` は、特定の問題の eval を作りたいときに使います。トレース（実際の記録）などの例を渡して方向づけられます。事例と採点者は、必ず人が承認します。
- `hillclimb` は、eval がすでにあり、目的（性能向上、または性能を保った費用削減）を指定して改善させたいときに使います。過学習の確認と、eval 自身のバグ（正しく見える答えを不正解にする採点者、ハーネスの誤り）の確認を、最初のラウンドの前と、点数が止まったときに行います。

## ゲーム制作での使いどころ

原文はゲームに触れていません。以下は、このWikiの考えと推測です。

### ゲームの中でモデルを呼ぶ機能（原文の想定に近い使い方）

NPC の会話、プレイヤーの入力文の判定、クエストの生成のように、ゲームの実行中にモデルを呼ぶ機能は、そのまま原文の対象です。たとえば、入力文を「攻撃」「会話」「無関係」に分類する機能なら、答えが決まったラベルなので、コードによる判定で足ります。NPC の返答の質のように答えが自由なものは、LLM-as-judge になります。その場合、基準は「口調が設定から外れていない」「ゲーム世界にない固有名詞を出していない」のような、確かめられる主張の形で書きます。

事例は、次の優先順で集める形が合います。
1. プレイテストの会話記録（同意と、個人情報の扱いを確かめてから）
2. バグ報告
3. 自分が手書きする5〜10件
4. 世界観の設定資料から合成した事例

### 自分の Skill や指示ファイルの改善

原文の対象には、指示ファイルと Skill が含まれています。ゲーム開発では、たとえば「CLAUDE.md の規則を守ったか」を eval にできます。次のようなテスト用のタスクを5〜10件作ります。

```text
- 敵を1種類追加する（data/enemies.json に追記し、ハードコードしない）
- セーブデータに項目を足す（旧バージョンのセーブを読めるまま）
- 効果音を差し替える（assets/sfx/ 以外を触らない）
```

採点は、コードで判定します。たとえば、変更されたファイルの一覧と、テストの合否で見ます。そのうえで、`/claude-api hillclimb` に、指示ファイルを変更対象として渡し、「指示ファイルを短くしながら、合格率を保つ」ことを目的にできます。原文が、費用の削減を強い目的の例として挙げている点と合います。指示ファイルの作り方は [プロジェクト指示ファイル](/agent-dev/project-instructions/)、コンテキストの扱いは [コンテキスト管理](/agent-dev/context-management/) にあります。

### 検証の仕組みと組み合わせる

eval の採点者は、ゲームでは [検証ループ](/agent-dev/verification-loop/) の仕組み（ヘッドレス実行、状態の公開、seed の固定）と相性がよいはずです。採点者が、ゲームの状態を読んで合否を決められるためです。

### バランス調整のボット（推測）

ボットを使う難易度調整（[バランス調整](/design/balancing/)）にも、原文の過学習の考えが当てはまるかもしれません。ボットに合わせて数値を詰めると、人間が遊んだときにずれる可能性があります。学習用とテスト用で、乱数の seed やステージを分けると、原文の「事例を分ける」と同じ形になります。ただし、これは原文の主張ではなく、このWikiの推測です。

## AIの活用ポイント

- eval を作る前に、Claude に、自分のアプリの「本番の場面」を質問させます。
  ```text
  この機能が実際に使われる場面を、5つの質問で私から聞き出してください。
  その答えをもとに、評価用の事例を10件の案として出し、各件に「なぜ難しいか」を書いてください。
  ```
- 採点者の検証では、自分の目で採点記録を読みます。Claude が採点した数件について、自分が違う点をつけるものがないかを確かめます。
- 点数が止まったら、「新しい編集をせず、残った失敗を原因ごとに分類して」と頼みます。事例や採点者の誤りが見つかることがあります。
- 費用の削減を目的にすると、eval が飽和していても使えます。「性能は同じまま、費用を下げる」と頼みます。
- 改善後は、未見のテスト用の点数と、信頼区間で判断します。誤差の範囲なら、マージしません。
