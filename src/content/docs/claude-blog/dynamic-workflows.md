## 概要

Claude Code の動的ワークフロー（dynamic workflows）を、開発チームが使い込んで得た知見としてまとめた記事です。Claude がその場で書いたスクリプトが、多数のサブエージェントを組み合わせて動かします。この記事は、仕組みと、効く理由、6つの組み合わせパターン、使い道、使わない場面、コツを、原文の順に整理します。

- 公開日: 2026年6月2日。著者: Thariq Shihipar 氏と Sid Bidasaria 氏（どちらも Anthropic の技術スタッフで、Claude Code を担当）。読了時間: 11分
- 原文: [A harness for every task: dynamic workflows in Claude Code](https://claude.dev/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code/)
- 原文はゲームに触れていません。「ゲーム制作での使いどころ」は、この Wiki の考えです。
- この機能を、実物と見比べる批評役に使った例が [Gauntlet Loop](/agent-dev/gauntlet-loop/) です。この記事は、元になった公式ブログの側を詳しく扱い、Gauntlet Loop の手順とは重ならないようにしています。

用語を補います。サブエージェント（subagent）は、メインの会話とは別のコンテキストで動く作業者です。ハーネス（harness）は、モデルに道具を渡し、作業の流れを制御する外側の仕組みです。

## 何が新しいのか

標準の Claude Code のハーネスは、コーディング向けに作られています。多くの作業は、コーディングに似ているので、それで足ります。ただし、調査、セキュリティの分析、複数エージェントのチーム、コードレビューのように、性能を出すために、Claude Code の上に専用のハーネスを自作してきた種類の作業がありました。

動的ワークフローは、そうした専用のハーネスを、作業ごとに Claude が作れるようにする機能です。作ったワークフローは、他の人と共有して再利用できます。原文は、機能を出した直後の、著者の最初の経験と学びをまとめたものです。ベストプラクティスは発展の途中で、トークンを多く使うため、複雑で価値の高い作業に向く、とも書いています。

## 原文が挙げる、8つのプロンプト例

原文は、詳しい説明の前に、可能性を考えさせるプロンプト例を8つ並べています。内容を、自分の言葉で表にしました。

| 例 | 頼んでいること |
|---|---|
| 不安定なテスト | 50回に1回失敗するテストについて、競合する複数の仮説を立て、証拠に耐えた仮説が1つ残るまで続ける |
| 自分の修正の傾向 | 直近50セッションから、繰り返している修正指示を探し、繰り返すものを CLAUDE.md の規則にする |
| 障害の記録 | Slack の障害チャンネルを半年分調べ、チケットのない繰り返しの根本原因を見つける |
| 事業計画の批評 | 計画を、投資家、顧客、競合の3つの立場の別々のエージェントに批判させる |
| 応募書類の順位づけ | 80通の履歴書を役割に対して順位づけし、上位10通を再確認する。基準は、質問ツールで本人に聞いて作る |
| 名前決め | コマンドラインツールの名前を、多数出して、トーナメントで上位3つに絞る |
| 一括の改名 | ユーザーを表すモデルの名前を、コードベース全体で変える |
| 記事の事実確認 | ブログ記事の下書きの技術的な主張を、コードベースと照らして、すべて確認する |

プログラミング以外（事業計画、履歴書、障害の記録）が含まれていることに気づきます。原文は、ワークフローは非技術的な作業のほうが役立つ場合すらある、とも書いています。

## 仕組み

動的ワークフローは、JavaScript のファイルを実行します。そのファイルは、サブエージェントを起動し、まとめて動かす、いくつかの特別な関数を使えます。

| 関数 | 役割 |
|---|---|
| `agent()` | サブエージェントを1体起動する |
| `parallel()` | 複数を並べて動かす |
| `pipeline()` | 複数の処理を連ねる |

ほかに、JSON、Math、Array のような、標準の JavaScript の関数も使えます。

原文が強調する点が2つあります。1つは、各エージェントが使うモデルと、専用の worktree（作業用の独立したコピー）で動かすかどうかを、ワークフロー側で決められることです。必要な知能の水準と、隔離の程度を、Claude が選べます。もう1つは、途中で中断されたとき（ユーザーの操作、ターミナルの終了など）、セッションを再開すれば、続きから動くことです。

### 公式ドキュメントで確認できる、仕組みの補足

公式ドキュメントで確認できたことです（2026年10月時点、[Orchestrate subagents at scale with dynamic workflows](https://code.claude.com/docs/en/workflows)）。原文にない情報です。

- ワークフローは、会話とは分けた隔離環境で実行されます。途中の結果は、スクリプトの変数に残り、Claude の文脈には、最後の答えだけが入ります。
- 1回の実行で、同時に動くエージェントは、標準で最大16体（CPU が少ない環境では減ります）、1回の実行で合計1,000体までです。`parallel()` と `pipeline()` の1回の呼び出しは、4,096件までです。
- 進捗は `/workflows` で見られます。フェーズごとのエージェント数、トークン数、経過時間が表示され、一時停止や中止もできます。
- 25体を超える、または見積もりが150万トークンを超える実行には、進捗行に「Large workflow」の警告が出ます。警告は助言で、実行は止まりません。
- スクリプト内では、`Date.now()` や `Math.random()` は使えません。再開したときに、同じ呼び出しを繰り返すためです。

## なぜ動的ワークフローなのか

標準のハーネスでは、計画と実行を、1つのコンテキストウィンドウの中で行います。多くのコーディングには効果的です。ただし、長く続く、極端に並列な、構造の強い、敵対的な作業では破綻することがあります。複雑な作業を1つの文脈で長く続けるほど、次の3つの失敗が起きやすいからです。

| 失敗 | 意味 | 例 |
|---|---|---|
| agentic laziness（途中で終わらせる） | 複雑で多部分の作業を、一部だけ進めて「終わった」と宣言する | セキュリティの確認の50項目のうち、35項目だけ対処する |
| self-preferential bias（自分の結果をひいきする） | 自分の結果や発見を好む傾向。特に、基準に照らして検証や判定をさせるときに出る | 自分が書いた修正を、自分で採点して合格にする |
| goal drift（目標のずれ） | 何ターンも続けるうちに、元の目的への忠実さが少しずつ失われる。圧縮（コンパクト）のあと、特に起きる。要約のたびに情報が欠け、境界条件や「これはしない」という制約が落ちる | 最初に決めた禁止事項が、後半では忘れられる |

対策は、それぞれ独立したコンテキストと、絞った目標を持つサブエージェントを組み合わせることです。作業を分けると、1体が覚えておくことが減ります。判定の役を別にすると、ひいきが入り込みにくくなります。

### 静的なワークフローとの違い

以前から、Claude Agent SDK や `claude -p` を使って、複数の Claude Code を組み合わせる静的なワークフローを作れました。ただ、静的な仕組みは、あらゆる境界条件に対応しなければならないので、汎用的になりがちです。原文は、Claude Opus 4.8 と動的ワークフローの組み合わせで、Claude が、その作業のためだけの専用のハーネスを書けるほど賢くなった、と説明しています。同じ手順を毎回回す仕組みではなく、目の前の問いに形を合わせる仕組みです。

## 6つの組み合わせパターン

原文は、Claude が組み合わせて使う、よくあるパターンを6つ挙げます。「ワークフローを作って」と頼むだけでも、`ultracode` という語を入れても始められます。ただ、パターンの理解があると、いつ使うか、どう誘導するかが分かります。

| パターン | 中身 | 使いどころ |
|---|---|---|
| 分類して振り分ける（classify-and-act） | 分類役がタスクの種類を決め、種類ごとに別のエージェントや動作へ振る。最後に出力の種類を決める使い方もある | 種類によって処理が違う依頼 |
| 分割して集約する（fan-out-and-synthesize） | 作業を小さな段に分け、各段にエージェントを走らせ、結果をまとめる。まとめる段は、全部が終わるのを待つ関門になる | 小さな段が多い。または、段ごとにきれいな文脈が要り、互いに混ざらないほうがよい |
| 敵対的な検証（adversarial verification） | 起動した各エージェントに、別のエージェントを付け、基準に照らして出力を疑う | 品質を保証したい出力 |
| 生成して選別する（generate-and-filter） | アイデアを多数出し、基準や検証で絞り、重複を除き、質が高く、確かめたものだけを返す | 案出し |
| トーナメント（tournament） | 作業を分けず、同じ作業に N 体を競わせる。方法を変えて試させ、判定役が2つずつ比べ、勝者が残るまで続ける | 正解が1つに決まらない作業 |
| 終わるまで繰り返す（loop until done） | 仕事の量が分からないとき、固定回数ではなく、停止条件（新しい発見がない、ログにエラーがない）を満たすまで、エージェントを起動し続ける | 量の見えない探索 |

## 使い道

原文は、10の使い道を、具体的な指針とともに挙げています。ここでは、判断の根拠になる部分を残して整理します。

### 移行と整理

Bun を Zig から Rust に書き換えた作業が、ワークフローで行われたと書かれています（原文は、Jarred 氏のスレッドと、100万行規模の移行の記事を参照）。コツは、作業を、呼び出し箇所、失敗するテスト、モジュールなどの、処理の単位に分けることです。修正ごとに、worktree でサブエージェントを起動し、別のエージェントが敵対的にレビューし、マージします。並列を最大にしたいときは、重い処理のコマンドを使わないよう指示すると、手元のマシンの資源が尽きません。

### 深い調査

Claude Code には、ワークフローで動く調査用の Skill（`/deep-research`）が公式に入っています。ウェブ検索を並べ、出典を取得し、主張を敵対的に確かめ、出典つきのレポートにまとめます。調査の対象はウェブに限りません。Slack の内容から状況報告を作る、コードベースの機能を深く調べる、といった使い方もあります。

### 深い検証

報告書の事実の主張を、すべて確かめたい場合です。1体が主張を全部拾い出し、主張ごとにサブエージェントが詳しく確かめます。確かめる側の出典の質を、さらに別のエージェントが監査する構成も取れます。

### 並べ替え

質的な基準（サポートの問い合わせを、不具合の重大さで並べる、など）で、1,000行以上を並べ替えたい場合です。1つのプロンプトに全部入れると、質が下がり、文脈にも収まりません。そこで、2つずつ比べるエージェントの連なり（トーナメント）を使うか、並列で区分ごとに順位をつけてから合わせます。原文は、比較して判断するほうが、絶対評価で点数を付けるより、信頼できると書いています。比べるたびに新しいエージェントを使うので、並びの途中経過だけがスクリプト側に残ります。

### 記憶と規則の遵守

CLAUDE.md に書いても、Claude が守り損ねる規則がある場合です。規則の一覧を渡し、規則1つにつき検証役を1体付けます。さらに、懐疑的な役のエージェントが、検証役の指摘を見直すと、誤検出が減ります。逆向きもできます。直近のセッションやレビューのコメントから、繰り返している修正を拾い、並列のエージェントで分類し、各候補を敵対的に確かめ（「この規則があれば、実際の誤りを防げたか」）、残ったものを CLAUDE.md にまとめます。

### 原因の調査

デバッグは、独立した複数の仮説を立てて確かめると上手くいきます。ただ、1つの文脈だと、自分の仮説をひいきします。ワークフローは、これを構造で防げます。ログ、ファイル、データのように、重ならない証拠ごとに別のエージェントが仮説を作り、それぞれの仮説に、検証役と反論役の一団が当たります。コードに限らず、売上が3月に落ちた理由、データの処理が失敗した理由、事後の振り返り全般に使えます。

### 大量の振り分け（トリアージ）

サポートの待ち行列やバグ報告のように、人が処理しきれない積み残しの場合です。1件ずつ分類し、すでに追跡中のものと重複を除き、対応します。修正を試みる、人にエスカレーションする、といった対応です。有用な型が隔離（quarantine）です。信頼できない公開の内容を読むエージェントには、強い権限の操作を禁じ、操作は、要約だけを受け取る別のエージェントが行います。`/loop` と組み合わせると、継続的に回せます。

### 探索と好み

デザインや名前のような、好みが絡む探索の場合です。たくさんの解を探索させ、レビュー役に、良い解の基準（採点表）を渡します。レビュー役が基準を満たしたと感じたら終わりです。採点表に基づいて、トーナメントで選ぶこともできます。

### 簡易な eval

作業用のコピーで別々のエージェントを走らせ、比較役が出力を基準で採点します。作った Skill を、ある基準で評価して直す、といった使い方です。

### モデルと知能の振り分け

タスクに合わせた分類役のエージェントが、使うモデルを決めます。実行の前に調べることで、最適なモデルが分かる場合に効きます。例では、認証モジュールの仕組みを説明させるとき、ファイルの数やコードベースの形で最適なモデルが変わるので、分類役が調べ、予想される複雑さに応じて Sonnet か Opus に振ります。

## 使わないほうがよい場面

原文は、ワークフローは新しく、大きな成果が出る場面がある一方、すべての作業に必要ではなく、トークンを大幅に多く使いかねない、と注意します。いつもの方法では届かない作業に、創造的に使うのがよいとのことです。普通のコーディングでは、「本当にもっと計算が要るか」を自問します。たとえば、普通のコーディングに、5人のレビュー役は要りません。

さらに一段上の話として、マルチエージェントか単一かの選択も、同じ論理だと書かれています。並列と専門化は、調整の費用に見合う必要があります。

## 使いこなすコツ

| 項目 | 原文の内容 |
|---|---|
| 具体的に頼む | 上のパターンの名前を使って、詳しく頼むと結果が良い |
| 小さい作業にも使う | 「簡易のワークフロー」を頼める。仮定を敵対的に確かめる軽いレビューなど |
| `/goal` と `/loop` | 繰り返す作業（トリアージ、調査、検証）には `/loop` を付けて定期的に動かし、`/goal` で、終わりの条件を強く指定する |
| トークンの予算 | 「1万トークンを使う」のように頼むと、上限になる |
| 保存と共有 | ワークフローのメニューで `s` を押して保存する。`~/.claude/workflows` に置くか、Skill として配る |
| Skill での配り方 | Skill のフォルダに JavaScript のワークフローを置き、SKILL.md から参照する。台本としてそのまま実行させるより、雛形として柔軟に使わせるよう頼むとよい |

### 公式ドキュメントで確認できる、運用の補足

次も、原文にない、公式ドキュメントの記述です（2026年10月時点）。

- プロンプトに `ultracode` を入れるか、「ワークフローを使って」と書くと、その依頼だけがワークフローになります。`/effort ultracode` を使うと、セッション全体で、意味のある作業ごとに、Claude がワークフローを計画します。使うトークンが増えるので、利用枠に早く届きます。
- 保存先は、プロジェクトの `.claude/workflows/`（リポジトリを取得した人と共有）か、個人の `~/.claude/workflows/` です。保存すると `/<名前>` で呼べます。
- 実行の前に、計画の段階（フェーズ）を示す承認の確認が出ます。スクリプトの本文も見られます。
- 費用が分からないときは、まず小さな範囲（1ディレクトリ、狭い問い）で試すよう勧めています。
- 作る数の目安は、`/config` の「サイズの指針」で選べます（small は5体未満、medium は10体未満、large は50体未満）。

## ゲーム制作での使いどころ

ここからは、この Wiki の考えです。原文にはゲームの例がありません。小さな個人ゲームで、本当に要るかを先に問う、という原文の注意に合わせて、使う場面を絞ります。

### 使うかどうかの目安

| 作業 | 向き不向き | 理由 |
|---|---|---|
| 敵を1体足す、UI の色を変える | 向かない | 普通のコーディング。5人のレビュー役は要らない |
| 巨大な `game.ts` を機能ごとに分ける、名前を一括で変える | 向く | 移行と整理。修正の単位が多く、機械的に確かめられる |
| まれにしか起きないバグの原因調査 | 向く | 仮説が複数あり、自分の仮説をひいきしやすい |
| 敵や技の名前、アイテムの案 | 向く | 好みの探索。生成して選別する |
| 指示ファイルの規則を守れているかの確認 | 向く | 規則ごとの検証役 |
| 手触りの調整 | 向かない | 人が遊んで決める工程（[ゲームフィール](/agent-dev/game-feel/)） |

### 大きな分割や改名

次のような依頼になります。結合の強い部分（描画、光、物理など）は、1体にまとめて順に直させます。Gauntlet Loop の事例で、結合した部品を担当者に分けたところ、互いの前提を壊し続けて、点数の伸びが小さかった、と報告されています（[Gauntlet Loop](/agent-dev/gauntlet-loop/)）。

```text
ワークフローを使って、src/game.ts（3,000行）を機能ごとのモジュールに分けてください。
手順: まず、依存の少ない順に、分け方の案を1つ作る。私に見せるために、いったん止める。
承認後、モジュールごとに別の worktree でサブエージェントを動かし、
別のエージェントが敵対的にレビューしてから、順にマージする。
描画と物理のように結合の強い部分は、並列にせず、1体が順に直す。
各マージの後に npm run verify を通す。重いコマンドは、並列では使わない。
```

公式ドキュメントでは、ワークフローの実行前に、計画のフェーズを確認する画面が出ます。上の「いったん止める」は、その確認とは別に、分け方の案そのものを見たいときの書き方です。

### まれに起きるバグの原因調査

物理のすり抜け、まれなクラッシュ、フレーム時間の突発的な悪化などです。

```text
ワークフローを使って、「ボスの攻撃の後に、まれにプレイヤーが壁をすり抜ける」原因を調べてください。
証拠の種類ごとに別のエージェントを付けてください:
(a) docs/logs/ のログ、(b) 当たり判定のコード、(c) seed 固定のボットを100回走らせた結果。
各エージェントは、他の証拠を見ずに、仮説を2つまで出す。
その後、各仮説を、検証役と反論役が、再現するテストで確かめる。
証拠に耐えた仮説が1つ残るまで続け、最大で3ラウンドで止める。
```

[検証ループ](/agent-dev/verification-loop/)にある seed 固定とボットが、証拠の1つになります。

### 名前や案を選ぶ

```text
ワークフローを使って、敵キャラの名前を考えてください。
世界観は docs/world.md。最初に40案を出し、重複と、既存の有名作品に近い名前を除く。
その後、2つずつ比べるトーナメントで3つに絞る。基準は、短い、声に出しやすい、
世界観に合う、の3つ。最終の3案を、理由つきで見せてください。決めるのは私です。
```

好みの最終判断は人が行います。既存の作品や商標に近い名前でないかは、検索して人が確かめます（[著作権](/legal/copyright/)）。

### 規則を守れているかの確認

[指示ファイル](/agent-dev/project-instructions/)に、「ヒットストップは両者を止める」「`.tscn` は手で触らない」のような規則を書いていても、守られているか分からないことがあります。

```text
ワークフローを使って、CLAUDE.md の「ルール」の節にある各規則が、直近の10コミットで守られているかを確認してください。
規則1つにつき、検証役を1体。各検証役は、他の規則を知らない状態で、違反を探す。
その後、懐疑役が、各指摘が本当に違反かを見直し、誤検出を落とす。
結果は、規則ごとに、違反の件数と該当の場所を、表で。
```

### 費用の見方

ワークフローは、1回で多くのトークンを使います。個人の制作では、利用枠が先に尽きる可能性があります。まず1ディレクトリに絞って試し、`/workflows` の表示でトークンの量を見ます（[コスト管理](/agent-dev/cost-management/)）。並列の使い分けは [並列開発](/agent-dev/parallel-agents/) に、実物と見比べる批評役の使い方は [検証ループ](/agent-dev/verification-loop/) にあります。

## AIの活用ポイント

### 自分の作業が、ワークフロー向きかを判定させる

```text
次の作業を、ワークフローで進めるべきか、普通の会話で進めるべきか、判断してください。
作業: （例: 敵のデータ120件の名前とステータスの整合を取る）
判断の観点: 作業の単位がいくつあるか、各単位が独立か、結果を機械的に確かめられるか、
自分の出力をひいきする危険があるか。
ワークフローが向く場合は、使うパターン（分類、分割して集約、敵対的な検証、生成して選別、トーナメント、繰り返し）を挙げ、
エージェントの数と、トークンの見積もりの目安も書いてください。向かない場合は、その理由を書いてください。
```

### 採点表を作らせる

好みが絡む探索では、レビュー役に渡す採点表が出来を決めます。

```text
このゲームのメニュー画面の見た目を、レビュー役のエージェントが採点するための採点表を作ってください。
項目は5つ以内で、各項目は、スクリーンショットだけで判定できる文にする（「読みやすい」ではなく「最小の文字が画面幅の2%以上」など）。
各項目に、合格の目安と、不合格の例を1行ずつ付けてください。
```
