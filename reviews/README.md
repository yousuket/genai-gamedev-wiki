# レビューの運用

外部のレビュアー（Codex など）が出した修正提案を置き、どれを直したかを追えるようにするためのフォルダです。サイトには公開されません（`src/` の外）。

## 一覧を見る

```bash
npm run reviews
```

レビューファイルごとの状態の集計と、未対応・一部対応の項目が表示されます。記入漏れ、状態の書き間違い、存在しないコミットがあると、エラーで終了します。

## 流れ

1. **レビュアー**が、`reviews/<対象>-<YYYY-MM-DD>.md` を新しく作る（[TEMPLATE.md](TEMPLATE.md) をコピーする）。
2. **直す人**（Claude Code など）が、提案ごとに、次のことを行う。
   1. 提案の根拠を、自分で確かめる（再現する、公式の一次情報を読む）。
   2. 妥当なら修正する。修正が複数の提案にまたがっても、コミットメッセージに、レビューファイル名を書く。
   3. 修正のコミットのあとで、レビューファイルの「対応状況」の表を更新して、別のコミットにする。
3. 根拠が確認できない、方針に合わない提案は、**見送り**にして、理由を書く。黙って無視しない。

## 状態の正は「対応状況」の表だけ

各レビューファイルの冒頭（見出し `## 対応状況`）にある表が、状態の唯一の記録です。本文の中に「対応済み」などを書き足しません。

| 列 | 内容 |
|---|---|
| # | 提案の番号（本文の見出し `## N. 件名` の N と一致させる） |
| 件名 | 提案の件名 |
| 優先度 | 高・中・低 |
| 状態 | 下の4つのどれか |
| 対応コミット | 直したコミットの短いハッシュ。「対応済み」「一部対応」では必須 |
| 対応日 | YYYY-MM-DD |
| メモ | 何をしたか、しなかったか。「一部対応」「見送り」では必須 |

### 状態の値

| 状態 | 意味 |
|---|---|
| 未対応 | まだ手を付けていない（レビュアーが作った直後は、すべてこれ） |
| 対応済み | 提案の「完了条件」を満たして、修正した |
| 一部対応 | 一部だけ修正した。残りをメモに書く |
| 見送り | 修正しないと決めた。理由をメモに書く |

## レビュアーへのお願い

- 冒頭に、対象、作成日、**確認時のコミット**を書く。直す人は、対象のファイルがそれ以降に変わっていないかを見て、変わっていれば、読み直してから直す。
- 提案は `## N. 件名（優先度: 高）` の形の見出しで書く。番号は1から連番にする。
- 提案ごとに、「現状と根拠」「修正案」「完了条件」を分けて書く。根拠には、再現した手順、測った値、一次情報のリンクを付ける。
- 「対応状況」の表は、すべて「未対応」で作る。**状態は書き換えない**（直す人が更新する）。
- すでに直した提案を、再び出さない。同じ対象を再びレビューするときは、新しい日付のファイルを作る。

## 直す人へのお願い

- 提案に従う前に、根拠を確かめる。今回のように、再現できて、公式の資料と一致する提案は、そのまま採用してよい。
- 提案の範囲を超える問題を見つけたら、直したうえで、メモに書く。
- 直したら、サイトを再ビルドして（`npm run check`、`npm run build`、`npm run check:dist`）、公開後の表示も見る。
- 表を更新したら、`npm run reviews` を実行して、エラーがないことを確かめる。
